## Result-artifact extraction contract (normative for every task that reads a toolchain result)

The MCP PoshQC test tool returns neither test counts nor a coverage percentage. Every number in this plan that describes a Pester run is therefore extracted from the two result files the run writes, by the element and attribute paths recorded here. These paths were verified against the emitted artifacts, not assumed from convention. Never infer a value from a result file's name, and never report a figure whose element could not be located.

**Test counts — `artifacts/pester/pester-junit.xml`.** The root element is `testsuites`. It carries the attributes `name`, `tests`, `errors`, `failures`, `disabled`, and `time`. It carries **no** `passed` attribute and **no** `skipped` attribute. Each per-file child `testsuite` element carries its own `skipped` attribute. Therefore:

- Read `tests`, `failures`, and `errors` from the root `testsuites` element.
- Sum the `skipped` attribute across every per-file `testsuite` element.
- Derive the passed count by subtraction: `passed = tests - failures - errors - (summed skipped)`.

Arithmetic is permitted and expected; only the element and attribute naming is fixed.

**Coverage — `artifacts/pester/powershell-coverage.xml`.** The runsettings set `CodeCoverage.OutputFormat = 'CoverageGutters'`, which emits a JaCoCo-shaped document. The root element is `report`. It contains `package` elements, each containing `class`, `sourcefile`, and `counter` elements. There is **no** `coverage` element and **no** `line-rate` attribute anywhere in the document. Therefore:

- **Overall line coverage** is computed from the report-level `counter` element whose `type` attribute is `LINE` — the one that is a direct child of the root `report` element — as `covered / (covered + missed)`.
- **Per-file line coverage** is computed from the `counter` element whose `type` attribute is `LINE` on the `sourcefile` element whose `name` attribute equals the bare filename, selected **within the enclosing `package` element** whose `name` attribute ends with that file's directory. Never select a `sourcefile` by bare filename alone: `hook-command-scanner.ps1`, `enforce-orchestration-preimplementation-gate.ps1`, and `enforce-promotion-mcp-only.ps1` each appear under both the `.claude/hooks` package and the `.codex/hooks` package, so a filename-only lookup is ambiguous and will silently return the wrong side.

**Files that produce no coverage row.** `CodeCoverage.Path` is an explicit per-file allow list and contains zero entries under `extensions/drm-copilot/resources/`. Every bundle mirror is therefore outside the coverage denominator and can never produce a `sourcefile` element. A task that records coverage for a bundle mirror records the literal entry `outside the coverage denominator — bundle mirror, parity enforced by hash` and never a fabricated percentage.

**No threshold against the overall figure.** The allow list holds 83 entries, of which this change touches five at baseline. The runsettings set `CoveragePercentTarget = 0`, and the whole-allow-list aggregate measured approximately 61.6% at preflight. No task in this plan asserts a threshold against that aggregate, because this change cannot move a figure dominated by 78 files it does not touch. The 85% line-coverage gate is enforced **per changed-or-added production file** by [P7-T8], [P9-T9], and [P11-T7].

## Standing constraints carried into every phase

- **No Python leg anywhere.** Standing repository policy: enforcement hooks must not have a Python implementation, because a second implementation drifts. No `.py` production file is added or modified by this change. Phase 9 carries an explicit diff scan for an introduced Python leg. Consequence for coverage: this change has no Python changed-code denominator, so the Python coverage gate has no subject here; the only Python obligation is keeping `tests/scripts/dev_tools/test_push_down_claude_resource_contracts.py` at its baseline failed count.
- **500-line cap on every production, test, and reusable script file.** `tests/scripts/codex-hooks/legacy-codex-hook-contracts.Tests.ps1` sits at 494 lines and tolerates only the single-line `$script:SharedModuleNames` array edit; every new scenario for that side goes in a new sibling file. The new shared library `hook-command-scanner.ps1` is estimated at 250–350 lines; if it approaches the cap it splits into two sibling files, and each split file then needs its own six registrations. The same 450-line split threshold applies to every test suite this plan creates or extends, and it is checked mid-plan by [P4-T8], [P6-T14], [P7-T10], and [P8-T10] — at the end of the phase that creates or extends the suite — rather than only by the after-the-fact measurement in [P9-T4].
- **Three quote- and paren-abutted wrapper forms are ungated today and remain ungated after this change.** Preflight measured, against an explicitly not-ready checkpoint: `bash -c 'git add .'` resolves to `allow`, `sh -c "git add ."` resolves to `allow`, and `echo "$(git add .)"` resolves to `allow`, contradicting the version-1.0 claim that all three deny today. The cause is that the trigger anchors on whitespace or start-of-string, and a quote or a paren abutting the command name is neither; under the specified design these segments select raw text, so the non-match persists after the fix. Inserting a single leading space (`bash -c ' git add .'`) restores the boundary and the denial. The four remaining wrapper pins were measured `deny` as claimed: `xargs git add`, `env git add .`, `pwsh -NoProfile -Command "Invoke-Pester …"`, and a here-document fed into a shell wrapper. **Orchestrator ruling: accept the residual. The design is not extended to nested wrapper re-scanning in this change.** The reasoning, recorded here so it is not re-litigated: the three forms are allow today and allow after, so the net fail-closed conclusion is unchanged — they move from an incorrectly-recorded neutral to a correctly-recorded neutral, never from deny to allow. Closing them would require treating a wrapper's quoted argument as a nested command line and re-segmenting it, a design whose own fail-open analysis has not been done and which would newly over-match a wrapper argument that is data rather than a command; doing that design inside an already-large change is the same mistake issue #539 avoided by deferring. The three forms are therefore named **explicitly** — never folded into the obfuscated-respelling class of D4 residual risk 2 — in spec residual risk D4.4 ([P1-T10]), in the corrected D3 rows and the corrected D2 Piece 2 clause-2 sentence ([P1-T8]), in the wrapper pin inventory ([P1-T9], [P6-T4], [P6-T10]), and in the Phase 10 follow-up candidate ([P10-T1]).
- **The same boundary property governs D4.1's example.** `bash -c 'echo "pytest"'` measures as `allow`, not `deny`: the character preceding the tool name is a double quote, which the trigger's `(^|\s)` anchor does not satisfy. The unquoted variant `bash -c 'echo pytest'` measures as `deny` and makes D4.1's point — that over-match persists inside wrapper-led segments — with a true example. [P1-T11] substitutes it. This is the same class as the three wrapper forms above and is why version 1.2 sweeps every acceptance condition rather than patching named instances.
- **Coverage.** Pester line coverage must stay at or above 85% on every changed or added production PowerShell file. Pester measures no branch coverage, so no branch gate applies, and no production file may be excluded from the coverage denominator. `CodeCoverage.Path` is an explicit per-file allow list with zero entries under `extensions/drm-copilot/resources/`, so bundle mirrors produce no coverage row and are recorded with a literal outside-the-denominator entry rather than a percentage; their parity is enforced by hash instead. The MCP PoshQC test runner reads the installed extension's settings and cannot see newly added coverage entries, so coverage evidence for the new helper is produced by invoking the self-hosted PoshQC module directly.
