## Executive Summary

This branch delivers a provider-neutral orchestration handoff contract that lets prepared Claude work continue in Codex, and the reverse, without replaying completed lifecycle phases. The design is unusually disciplined for a change of this size. The contract layer is pure and does no I/O; every side effect in the materializer reaches disk, Git, and the destination authorities through one of six injected interfaces, with the concrete Node implementations quarantined in a single module. Path handling is canonicalized through a dedicated boundary that rejects absolute inputs, `..` traversal, non-normal separators, root-prefix collisions, and symlink or reparse escape for both existing and creatable targets. Plan identity is pinned to a normalized repository-relative path plus a raw-byte digest rather than rediscovered by directory scan, which is the specific defect the feature exists to eliminate.

The evidence reviewed was the full branch diff against the merge base, the refreshed PR-context summary and appendix, the three coverage artifacts, the feature's baseline and QA-gate evidence tree, and direct re-execution of the formatting, lint, type-check, and focused test stages. Every static gate is green on the branch head, and all three coverage languages exceed the uniform thresholds repo-wide, on changed lines, and per changed file. The reviewer independently recomputed all four pinned fixture digests and confirmed they match both the `fixture.json` values and the committed git blobs at `a7b80f2d`, which is the load-bearing claim behind AC2, AC3, and AC13.

The remaining findings are test-completeness and diagnosability items, not behavioral defects. The two that matter most are asymmetries between the Python and TypeScript runtimes, which is precisely the class of drift this feature was built to prevent: the Python destination-projection integrity guard has no negative test while its TypeScript counterpart does, and the Python failure-precedence tuple has no parity assertion against the shared registry while the TypeScript list does.

**What changed:**

Fifteen new TypeScript modules under `extensions/drm-copilot/src/lib/validate/`, `src/mcp-handlers/`, and `src/`, implementing the envelope contract, path boundary, provider adapters, materializer with its request, support, and production layers, workspace-explicit authority service, checkout context, and semantic MCP identity normalization; six existing TypeScript modules extended to route the three new MCP tools. Three new Python modules under `scripts/dev_tools/` implementing the same contract, its support primitives, and the provider adapters, plus modifications to the push-down and orchestrator-state validators. A shared JSON schema and semantic alias registry at `config/orchestration-handoff.schema.json` and `config/orchestration-handoff-registry.json`, published to consumers through `pack-manifests/core.json`. The Codex preparation-gate hook `.codex/hooks/enforce-epic-planning-only.ps1` rewritten to resolve its MCP allowlist from that registry rather than from a hardcoded hyphenated list. Ten committed fixtures under `tests/fixtures/orchestration-handoff/`, including the TaskMaster #469 pair in both directions with two `.gitattributes` entries pinning the fixture plan bytes against EOL normalization.

**Top 3 risks:**

1. Python and TypeScript can silently disagree about failure ordering. The two runtimes independently restate the `HANDOFF_*` precedence, and only TypeScript asserts it against `config/orchestration-handoff-registry.json`. A future edit to either list would produce two runtimes that select different primary failures for the same envelope, which is the exact failure mode AC11 exists to prevent, and no test would catch it.
2. The Python destination-projection integrity guard is unverified. `_validate_projection_facts` is the only thing stopping a caller from projecting a destination checkpoint whose plan, lifecycle, scheduler context, or history linkage differs from the envelope that was validated. None of its five rejection branches is exercised.
3. Materialization failure recovery is unproven. `stageMaterialization` performs three sequential writes and has five recovery branches for pre-existing or corrupt intermediate files. Exactly one success-path test exercises the method, so the AC10 guarantee that any failure leaves the source checkpoint intact holds by construction but is not demonstrated.

**PR readiness recommendation:** **Conditional Go** — No blocking finding exists, every mandatory gate is green, and the acceptance criteria are behaviorally satisfied; the two Major findings should be closed before or immediately after merge because both are cross-runtime drift guards rather than cosmetic gaps.

## Implementation Audit

### Python implementation audit

#### What changed well

- The contract module is pure. `orchestration_handoff_contract.py` performs no file I/O; the two functions that touch disk, `raw_file_sha256` and `resolve_pinned_plan_path`, live in the support module. This is what makes the 98.70% line coverage on the contract achievable without a filesystem, and it is the correct application of the separation-of-concerns priority.
- Vocabulary is closed rather than open. `WORK_MODES`, `COMPLEXITIES`, `ROUTE_INTENTS`, `HISTORY_STATUSES`, and `SUPPORTED_VOCABULARIES` are `frozenset` constants, and `REGISTERED_TRANSITIONS` maps each transition name to the frozen set of source states that may take it. An unrecognized value is rejected at the boundary rather than flowing into a comparison that happens to fall through.
- The legacy migration function refuses to guess. `read_legacy_v1` takes `source_provider`, `plan`, `lifecycle`, and `scheduler_context` as required keyword parameters typed `| None`, and raises with a specific field name when any is `None`. It returns the source bytes unchanged rather than a converted object, so the caller cannot mistake a migration check for a migration. This is the correct shape for AC12's prohibition on fabricating missing history.
- Test support was extracted, not duplicated. `orchestration_handoff_taskmaster_469_test_support.py`, `push_down_handoff_test_support.py`, and `validate_orchestrator_state_test_support.py` hold shared builders. The 349 lines removed from `test_validate_orchestrator_state.py` were relocated into two new files rather than deleted, keeping every file under the 500-line cap without dropping an assertion.

#### Typing and API notes

- Every added function carries full annotations including return types, `from __future__ import annotations` is used throughout, and the `collections.abc.Iterable` import is placed under `TYPE_CHECKING` so no runtime import exists for a typing-only need. `poetry run pyright` reports 0 errors, 0 warnings, and 0 informations.
- Frozen dataclasses model the envelope and its components, which gives structural equality for free and is what makes `facts.plan != envelope.plan` in `_validate_projection_facts` a meaningful comparison rather than an identity check.
- `Bindings = dict[str, object]` at line 37 and the matching parameter of `validate_bounded_scheduler_return` keep the scheduler-binding payload untyped. This is defensible: bindings vary by scheduler kind, and the function validates them by equality against a caller-supplied `expected_bindings` map rather than by attribute access, so no unchecked dereference occurs. The trade-off is that the payload's shape is invisible to the type checker. A `TypedDict` per scheduler kind would express it, at the cost of coupling the validator to the kinds.
- The re-export block at the top of `orchestration_handoff_contract.py` uses the `from X import Y as Y` form deliberately, which is the explicit-re-export idiom that keeps the names in the module's public surface under strict checking.

#### Error handling and logging

- Failure is always explicit. `_require` raises `HandoffContractError` with a field name and a reason on any failed invariant. There is no bare `except:` and no `except Exception:` anywhere in the added modules.
- `HandoffContractError` carries a `code` defaulting to `HANDOFF_UNSUPPORTED_VERSION`, so every raise site either accepts the default or names the specific code, and the primary-failure selector at line 350 picks the first match in `FAILURE_PRECEDENCE` order. The mechanism is sound. The gap is that the ordering it depends on is not asserted against the registry, which is finding G2 above.

### TypeScript implementation audit

#### What changed well

- Six injected interfaces isolate every side effect: `HandoffFileSystemBoundary`, `HandoffGitBoundary`, `HandoffTopologyBoundary`, `HandoffRoutingBoundary`, `HandoffValidatorBoundary`, and `HandoffClockBoundary`. The concrete Node implementations live only in `orchestration-handoff-materializer-production.ts`. This is why the materializer suites can drive real coordination logic against controlled seams without `jest.mock`, and why the clock is deterministic without fake timers.
- The check ordering in `prepare` is deliberate and matches AC11 exactly. Path resolution, then file read, then digest comparison, then envelope validation, then history presence, then source binding, then workspace binding, then destination provider, then archive and candidate path resolution, then topology authority, then routing authority, then projection, then projection validation, and only then the clean-worktree preflight. `HANDOFF_DIRTY_WORKTREE` therefore cannot mask an earlier contract or authority failure, which is the specific property the TaskMaster #469 fixture is designed to prove.
- The write sequence in `stageMaterialization` is genuinely atomic with respect to the canonical checkpoint. The candidate is written in the destination's own directory, so the final `replaceFile` is a same-filesystem rename; it is re-read and re-validated before the rename; and the source path is only ever read. A crash at any point leaves the canonical checkpoint untouched.
- Both archive and candidate writes use exclusive create, and on collision they read the existing file and compare digests rather than overwriting. This makes a retried transition idempotent instead of destructive, which matters because the archive is the only copy of the pre-handoff source bytes.
- The path boundary is a separate module with its own test suite covering root-prefix collision, missing-ancestor walk, separator normalization, case semantics, and both symlink and reparse escape for existing and creatable targets. Treating "resolve a path that must already exist" and "resolve a path that may be created" as two distinct operations is the right decomposition; conflating them is the usual source of traversal bugs.

#### Type safety and maintainability

- No `any`, `<any>`, or `as any` appears in any added handoff module, and no `eslint-disable`, `@ts-ignore`, or `@ts-expect-error` directive was introduced. `npm run typecheck` and `npm run lint` both exit 0.
- Every exported interface property is `readonly`, and array-valued properties use `ReadonlyArray` or `readonly T[]`, so a consumer cannot mutate a contract object it received.
- The three new `RepoAutomationService` methods are declared optional, which preserves every existing implementor. This is the right call for a service interface with multiple in-repo implementations.
- The one type-safety defect is the assertion at line 276, finding G5 above. It is the only place in the added TypeScript where a value crosses into a declared union without validation.
- The 13-module decomposition keeps every file well under the 500-line cap, with the largest at 497 lines. The split is by responsibility rather than by size, so the boundaries are meaningful.

#### Error handling and logging

- Every failure returns a structured `blockedResult` with a deterministic code, a `handoffId` where one is known, the last history digest, and the affected paths. Nothing is silently swallowed in the sense of producing a success result.
- The weakness is diagnostic. Eleven `catch` blocks discard the caught error entirely, and `HANDOFF_VALIDATOR_UNAVAILABLE` covers at least six distinct causes. This is finding G6.
- There is an internal inconsistency worth noting alongside G3. The candidate re-validation failure path at lines 411-424 explicitly attempts `removeFile` on the candidate and carries the comment "The blocked result names the retained candidate for explicit cleanup" for the case where removal itself fails. The subsequent `replaceFile` failure path at lines 427-433 makes no cleanup attempt and reports `destinationPath` rather than the retained candidate, so an operator recovering from a failed rename is not told which file to delete. The two adjacent paths should agree on the recovery contract.

### PowerShell implementation audit

#### What changed well

- The allowlist is now derived rather than declared. `Get-EpicPlanningRegisteredMcpTool` reads `config/orchestration-handoff-registry.json`, verifies that each semantic id is registered, that its `operation` field matches the trailing segment of the id, and that every declared transport alias matches `^mcp__(?:drm-copilot|drm_copilot)__<operation>$`, then returns the sorted unique alias set. This removes the hardcoded hyphenated list that caused the original #614 denial and makes the hook and the validators share one registry.
- The decision logic was inverted correctly. The old code allowed anything matching `mcp__drm-copilot__*` and then filtered; the new code builds an explicit allow set from the registry and denies everything else with a single reason string. That is the safer default, and the Pester cases assert the exact deny reason for a malformed id, an unrelated server, an unregistered operation, and an approximate operation.
- The regex escapes the interpolated operation with `[regex]::Escape($operation)` and anchors both ends, so a registry entry containing regex metacharacters cannot widen the alias pattern.
- Every path operation uses `-LiteralPath`, and the function carries `[CmdletBinding()]`, `[OutputType([string[]])]`, and `[Parameter(Mandatory)]` on both parameters.

#### API and safety notes

- `Get-EpicPlanningRegisteredMcpTool` is a pure function of its two parameters plus the file it reads, and it returns a value rather than mutating script scope. That is the right shape. The problem is the call site, not the function.
- `$script:EpicPlanningRepositoryRoot` was hoisted from the main body to script scope and is now reused at line 320, which removes a duplicated `Split-Path` computation. That refactor is sound.

#### Error handling and logging

- Inside the function, failures raise with a `EPIC_PLANNING_ONLY_BLOCKED:` prefixed message naming the specific registry defect, which is the right level of detail for a hook operator.
- The defect is placement. Because the assignment at lines 85-88 runs above both the dot-source guard and the top-level `try`, those four well-formed error messages never reach the `catch` at line 350 that would write them to stderr and `exit 2`. They surface as an unhandled PowerShell terminating error instead. This is finding G4.

### Quality assessment prompts

- **Determinism:** Strong. The clock is injected rather than read, no test calls `setTimeout`, `Date.now()`, or `time.sleep`, all identity is pinned to raw-byte SHA-256, and the two fixture plan files are exempted from EOL normalization by `.gitattributes` so their digests do not vary by platform. That last detail is the difference between a hash assertion that is deterministic and one that fails only on Windows checkouts.
- **Isolation:** Strong. Each test names one behavior and asserts one outcome; failure-code tests assert a single code rather than a set. Envelopes are built fresh per test from module-level helpers, and the TypeScript suites construct a fresh dependency set per test.
- **Speed:** Strong. 126 Python handoff tests in 0.69s, 221 TypeScript handoff tests across 11 suites in 1.172s, 46 push-down and validator tests in 0.30s. Nothing in the added surface is slow enough to discourage frequent runs.
- **Diagnostics:** Good, with one caveat. Contract errors carry a field name and reason; hook denials assert an exact reason string; parameterized suites interpolate the case id into the test name so a failure names itself. The caveat is that `HANDOFF_VALIDATOR_UNAVAILABLE` covers six causes with no diagnostic detail, so a production failure carrying that code would not tell an operator where to look. That is finding G6.

## Verdict

The change is ready for normal PR flow. The implementation is behaviorally complete against all fifteen spec criteria and all thirteen user-story criteria, every mandatory quality gate is green on the branch head, and the design decisions that matter most for a provenance-preserving handoff are correct: identity is pinned to raw bytes rather than paths, the write sequence is atomic with respect to the canonical checkpoint, path resolution is canonicalized through a dedicated boundary with a thorough negative suite, and every side effect is injected rather than reached directly. The fixture digests, which carry the weight of AC2, AC3, and AC13, were independently recomputed and verified against the committed blobs.

The two Major findings should be closed before or immediately after merge. Both are cross-runtime drift guards, and both concern the same underlying risk: the Python and TypeScript implementations of a shared contract are bound to the same registry in one direction only. A feature whose stated purpose is to keep two ecosystems in agreement should not ship with an asymmetric parity gate. Neither finding blocks the merge, because both lists agree today and both guards are implemented correctly; the exposure is to future edits rather than to current behavior. The four Minor and three Nit findings are appropriate for a follow-up cycle and are enumerated with concrete corrections in `remediation-inputs.2026-09-06T23-30.md`.
