## Mid-Execution Delta 2026-08-08T17-05 — 500-line relief for `_blast_radius_validation.py`

Execution halted on the 500-line verification task — the task numbered [P11-T10] before this delta and
renumbered to [P11-T21] by it — on a Hard Constraint 6 violation: `scripts/dev_tools/_blast_radius_validation.py`
is 510 lines. Baseline was 497 ([P0-T12]); the Phase 1 relief brought it to 465 ([P1-T10]); the Phase 3
addition of `config_root_surfaces` ([P3-T3]) consumed 36 of the 35 remaining lines. The Phase 1 relief
allocation was under-provisioned by 10 lines and no task between [P1-T10] and that verification re-measured the file.

The remedy is a second Python-only structural relief inserted as [P11-T10] through [P11-T20]. Old
[P11-T10] through [P11-T17] are renumbered to [P11-T21] through [P11-T28]. Tasks [P0-T1] through
[P11-T9] are complete and are unchanged.

**Relief design (constrained, not the widest available).** The relief moves exactly two symbols —
`CONFIG_OVER_BREADTH_FRACTION` and `config_over_breadth_fraction` — into a new leaf module
`scripts/dev_tools/_blast_radius_thresholds.py`. This is the only guard-independent cluster in
`_blast_radius_validation.py`, and it is chosen deliberately over the larger `config_*` cluster the
executor proposed. `config_string_list`, `config_root_surfaces`, and `config_modules` all call
`require_str_tuple`, `require_text`, or `require_mapping`, so relocating them would force the guards to
move as well; `scripts/dev_tools/_blast_radius_conflicts.py` would then import those guards from the new
module instead of from `_blast_radius_validation`, which would falsify the `conflicts` clause of the
import graph asserted by the completed [P1-T8] **and** by the already-checked acceptance criterion at
`spec.md` line 662. Moving only the threshold reader adds one leaf to the graph and falsifies no clause
of either assertion, so no `spec.md` amendment is required by this delta.

**Projected line counts.** `scripts/dev_tools/_blast_radius_validation.py` 510 → 484 (27 lines removed:
the constant at line 56 and the function block at lines 263-288; 1 line added: the new import).
`scripts/dev_tools/_blast_radius_thresholds.py` new at approximately 55 lines. No other production or
test file changes: `_blast_radius_conflicts.py`, `compute_blast_radius.py`, every `.psm1`, every bundled
mirror, and every test file are untouched, because none of them references the two moved symbols.

**Test coverage of the new module.** `config_over_breadth_fraction` is exercised through the
`compute_blast_radius` facade by `tests/scripts/dev_tools/test_blast_radius_validation.py`
(`test_v3_triggers_only_above_the_over_breadth_fraction` for the happy path and boundary,
`test_validation_rejects_a_malformed_over_breadth_threshold` for both `TypeError` branches, and
`test_validation_rejects_an_out_of_range_over_breadth_threshold` for the `ValueError` branch) and by
`tests/scripts/dev_tools/test_compute_blast_radius.py`. No test imports the symbol directly, so no test
file needs an import redirect and the new module inherits full line and branch coverage unchanged.

**PowerShell is deliberately untouched.** The two implementations are behaviourally byte-equivalent
today and remain so: `Get-ConfigOverBreadthFraction` in `.claude/lib/blast-radius/BlastRadiusConfig.psm1`
keeps its name, signature, exports, and behaviour. Which Python file hosts the reader is an internal
Python file-organization detail with no PowerShell counterpart obligation, and structural asymmetry
between the two languages is already established by this plan (Phase 1 created `_blast_radius_glob.py`
in Python while Phase 2 created no `.psm1` module). Editing the `.DESCRIPTION` attribution comment in
`BlastRadiusConfig.psm1` would require a mirror re-copy and a full PowerShell toolchain re-run for a
documentation-only change, and would put that 491-line file closer to the limit; [P11-T20] records that
decision rather than leaving it implicit.
