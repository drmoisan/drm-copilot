## Executive Summary

The branch corrects a published blast-radius truth table that stood stale after issue #489 corrected only the self-hosted copy, and adds a three-class key-partition gate in Python with a PowerShell mirror plus TypeScript pins. The production change is small and correct: one key deleted from one exported constant, one configuration document rewritten to a declared portable set, and 63 lines of rule text explaining why the two copies take different relations.

This review re-audits the whole branch and independently tests the six claims cycle 3 made. Findings are ordered by what the evidence supports.

**Three cycle-3 claims are verified and hold.**

1. The repaired non-vacuity floor discriminates all four states correctly. Driven through twelve cells — two committed copies, two keys, three failing states — every cell fails and every message names its own state. The `ContainsKey` and `$null -eq` guards sit ahead of the count measurement with `continue` after each, so the ambiguous `@($null).Count` idiom is unreachable for the absent-key and null-value states. This is the defect recorded in agent memory as `powershell-non-emptiness-assertions-cannot-fail`, and it is genuinely repaired.
2. The same block covers `modules`, correctly branching to `@($config[$key].Keys).Count` for the hashtable case. Verified in four of the twelve cells.
3. `SOURCE_BLAST_RADIUS` is bound to the on-disk bundled resource. The new Jest case fails under five independent drift classes including array reordering, because `toEqual` on parsed arrays is order sensitive. Divergence direction 18 is closed.

**One cycle-3 claim does not hold.** CR-3's remediation does not close the silent-pass direction it names. The three added `assert "<key>" in CLASS_*_KEYS` statements constrain removal of an already-consumed name, which the exhaustiveness gate already constrained; they do not constrain addition of an unconsumed name, which is the direction CR-3 described. There is no PowerShell counterpart at all. The complete residual path — adding `invented_key` to both committed copies, to `CLASS_TWO_KEYS`, to `$script:ClassTwoKeys`, and to `SOURCE_BLAST_RADIUS` — passes silently in all three languages.

**Cycle 3 introduced one new defect of the same class the branch exists to fix.** The Pester split moved two cases out of `BlastRadius.TruthTable.Tests.ps1` and left four pointers in the two `parallel-orchestration.md` copies still naming that file as their home. The same split makes acceptance criterion 11 literally false for the file it names.

The full toolchain passes in a single run for all three languages. Coverage is above threshold everywhere. There are **zero Blocking findings**.

## Verification of the Repaired Floor

The repair is correct and the correctness is a property of the ORDER, not only of the predicates. The block reads:

1. `if (-not $config.ContainsKey($key)) { ...; continue }`
2. `if ($null -eq $config[$key]) { ...; continue }`
3. `$count = if ($key -eq 'modules') { @($config[$key].Keys).Count } else { @($config[$key]).Count }`
4. `if ($count -eq 0) { ... }`

Steps 1 and 2 each `continue`, so step 3 is unreachable for an absent key and for a null value. That is what makes the `@(...)` wrapping safe: `@($null).Count` is `1` in PowerShell because the scalar `$null` wraps to a one-element array, and it was exactly that idiom, reached for the absent-key and null-value states, that made the previous floor unable to fail. The `ContainsKey` call is valid because `ConvertFrom-Json -AsHashtable` produces a `Hashtable`. The `modules` branch reads `.Keys` because an empty hashtable would otherwise wrap to one element.

The verification was behavioural, not textual. Twelve cells, twelve failures, twelve distinct state-naming messages, and one passing unperturbed state. Full table in `evidence/regression-testing/reviewer-perturbation-battery.2026-08-22T17-20.md` Group A.

## Restore-Mechanism Deviation

For two CR-3 perturbations the executor restored from an in-memory backup rather than `git checkout --`, because the perturbed files carried legitimate uncommitted edits from earlier tasks in the same cycle that a checkout would have discarded. The deviation was disclosed in both fail-before artifacts with a stated rationale, and byte identity was claimed via `diff`.

The judgement is that the evidence supports a genuine restore, and the strongest proof is independent of the executor's `diff` claim: the committed content of both files at head contains exactly the intended CR-3 change and no perturbation residue. `blast_radius_parity_test_support.py` at head declares `CLASS_THREE_KEYS = ("modules",)`, not the perturbed `()`, and `BlastRadius.KeyPartition.Tests.ps1` at head declares `$script:ClassThreeKeys = @('modules')`, not the perturbed `@()`. The full cycle-3 diff of both files was read line by line and contains no other change. The deviation was also the correct call: `git checkout --` on a file carrying uncommitted in-cycle work would have silently reverted that work, and the executor could not commit mid-cycle.

One caveat, recorded rather than escalated: an in-memory backup verified by `diff` inside the same process that made the perturbation is weaker evidence than an external hash, because a single logic error could both write the wrong backup and compare it against itself. The committed diff removes that doubt for this cycle. A future cycle facing the same constraint should prefer capturing a `Get-FileHash` or `sha256sum` of the pre-perturbation content and re-comparing it after restore.

## Positive Observations

- The repaired floor's inline comments explain why the state order matters rather than restating what each line does, which is what makes the repair auditable by reading as well as by perturbation.
- The `@remarks` block on `PAYLOAD_MODULES` states the granularity criterion, why removing `claude-runtime` does not weaken the relation below the path level, and why `config` is retained to keep `assertNoForbiddenGlob` non-vacuous. That last point is a floor on a guard that could otherwise pass because it was handed nothing to check, and it is the kind of reasoning this repository's rules ask for.
- The CR-4 case compares parsed structures rather than bytes, with the reason stated: both files are JSON text with independent formatting and key order. It is stronger than intended in one respect, since `toEqual` on arrays is order sensitive, and that strength was measured rather than assumed.
- The rule addition explains the surfaces-versus-modules asymmetry — an over-matching module glob costs concurrency on every pair, an unmatched surface entry is inert — which is the actual reason the two key groups take different relations and is the piece a future maintainer would otherwise have to re-derive.
