## Context
The push-down merges exactly one destination-relative path, the orchestration-routing file, and does not preserve destination content for any other published file. `config/blast-radius.json` is regenerated on every push, so any shared surface, glob, or module a destination added locally is destroyed the next time the payload ships.

Research correction to the issue premise: since #462/#472/#500 the TypeScript push-down no longer copies `config/blast-radius.json` verbatim. `BlastRadiusDeriveFileSystem` (`claude-blast-radius-derive.ts`) replaces the bundled `modules` map with one derived from the destination layout and carries the other keys from the bundled document. The derivation never reads the destination's existing file, so the defect stands: destination-local additions are discarded on each push. The Python push-down (`scripts/dev_tools/push_down_claude_customizations.py`) does not publish `config/` at all today; #507 adds it.

## Root Cause Analysis
The merge decorator was introduced for the routing file because destination-local routes must survive a push. The same argument applies to blast-radius entries, and the asymmetry is an omission rather than a decision. Issue #500 then corrected the shipped defaults on the assumption that a destination cannot durably override them, and the derivation added by #462/#472/#500 regenerates the file from the bundle and the destination layout without any destination-authored input. A direct merge of the destination main file cannot fix this, because after one push that file is itself push-down output: derived and shipped entries are indistinguishable from local ones, so union would keep stale entries indefinitely. The missing element is a destination-authored input with explicit provenance.


## Proposed Fix

### Design summary (what changes where):
Adopt research option (d). A destination-owned `config/blast-radius.local.json` is composed at push time onto the freshly generated base document, and the result is written to `config/blast-radius.json`. Consumers continue to read one file and are unchanged. The base is regenerated on every push, so stale shipped or derived entries clear; the overlay is authored only by the destination, so local entries persist.

- **Base document.** TypeScript: the derived document produced by `BlastRadiusDeriveFileSystem`. Python: the document the Python path publishes for `config/blast-radius.json` after #507 (no derivation exists in Python).
- **Per-key composition semantics** (research 6.1). Let `B` be the base and `O` the parsed overlay:
  1. Overlay absent: write `B` unchanged, byte-identical to the output without this change.
  2. Overlay unparseable, or its root is not a JSON object: raise `BlastRadiusOverlayError(path, detail)` naming the overlay path; `config/blast-radius.json` is not written.
  3. `version`: `B` wins. An `O.version` that is present and not equal to `B.version` raises `BlastRadiusOverlayError`; the main file is not written.
  4. String-list keys `shared_surfaces`, `shared_surface_globs`, `mandate_reads`, `mergeable_paths`, `path_roots`: ordered union; `B` entries in `B` order, then `O` entries not already present, in `O` order. A non-list value or a non-string member in `O` raises `BlastRadiusOverlayError` naming the key.
  5. `modules`: per module name. An `O` module absent from `B` is added; an `O` module present in `B` replaces that module's glob list. Module names are emitted in ordinal order (matching `assembleModules`). The forbidden-glob guard (`FORBIDDEN_GLOBS`: `**`, `docs/**`, `tests/**`) runs on the composed map, including overlay-authored modules, and raises `BlastRadiusGuardError` before any write.
  6. Object-valued keys (`conflict_tolerance`): recursive per member. Nested string lists (`append_only_paths`) take the ordered union; nested objects (`weights`, `band_durations`) merge per member; nested scalars take the `O` value.
  7. Scalar keys (`over_breadth_fraction`, `write_intent_extraction`): `O` wins when present.
  8. Keys present only in `O`: appended after `B`'s keys in `O` order. `B`'s fixed emission order is preserved.
  9. Shadowing: an `O` list entry equal to a `B` entry is deduplicated; an `O` module equal in name to a `B` module replaces it (rule 5).
  10. Serialization: 2-space indentation plus a trailing newline in both languages. TypeScript `JSON.stringify(v, null, 2) + "\n"`; Python `json.dumps(v, indent=2, ensure_ascii=False) + "\n"`. Integral floats (for example `1.0`) are a known serialization divergence class and are excluded from parity fixtures.
  11. Idempotence: `compose(compose(B, O), O) == compose(B, O)`, and `B` is never read from the destination, so two consecutive pushes produce identical bytes.
  12. Stale entries: shipped or derived entries removed upstream disappear from the output on the next push; overlay entries persist until the destination removes them.
  13. Shape validation beyond rules 2 to 5 remains with the consumer readers, which already fail fast on malformed values.

### Boundaries and invariants to preserve:
- The push never writes, modifies, or publishes `config/blast-radius.local.json`.
- With no overlay present, the bytes written to `config/blast-radius.json` are identical to the bytes written before this change.
- `claude-blast-radius-derive.ts` and `claude-blast-radius-derive-core.ts` are unchanged.
- `RoutingMergeFileSystem`, `BlastRadiusDeriveFileSystem`, `ROUTING_MERGE_RELATIVE_PATH`, and their error types remain exported from `claude-customizations.ts` (no breaking change).
- Every error is raised before the inner write, so the destination main file keeps its prior bytes on failure (routing-merge precedent).
- No pushed-down enforcement hook gains a Python leg; no hook file changes.
- No file exceeds 500 lines.

#### Data flow and validation changes:
- **TypeScript registry** (research 6.2): `DESTINATION_WRITE_DECORATORS: ReadonlyArray<{ relativePath: string; wrap(inner, destinationRoot, options): PushDownFileSystem }>`, composed innermost-first in the order routing merge, blast-radius overlay, blast-radius derive. `MERGED_RELATIVE_PATHS: ReadonlyArray<string>` is a literal array of the distinct `relativePath` values so the parity test can read it. The overlay decorator sits inside the derive decorator: the derive decorator calls `inner.writeTextFile(path, derived)`, and the overlay decorator reads `config/blast-radius.local.json` from the destination through its inner file system and writes the composed text. `ExcludingFileSystem` remains outermost.
- **Python registry** (research 6.2): frozen dataclass `DestinationMerge(relative_path, input_relative_path, merge)` with `merge(source_text, destination_input_text, path) -> str`; tuple registry `MERGED_PATHS`; one decorator whose `write_text` consults the registry. The routing entry reads the path it writes; the blast-radius entry reads the overlay path. When the input path is absent in the destination, the source text is written unchanged.
- **#507 reconciliation (decision 7).** The names above are #508's own. Implementation must reconcile with the Python merge registry and parity test that #507 lands on the integration branch by extending them (for example adding `input_relative_path` to #507's entry type), not by replacing them.

#### Error handling and logging updates:
- `BlastRadiusOverlayError(path, detail)` in both languages for: unparseable overlay, non-object root, `version` mismatch, non-list value or non-string member for a string-list key. The message names the overlay path and, where applicable, the offending key.
- `BlastRadiusGuardError` for a forbidden glob in the composed `modules` map, including overlay-authored modules.
- All errors are raised before the inner write. No new logging.

#### Rollback/feature-flag considerations (if applicable):
No feature flag. With no overlay file present, output is byte-identical to the prior behavior, so a destination is unaffected until it creates an overlay. Rollback is a revert of the PR.

### Technical specifications (interfaces/contracts):

#### Inputs/outputs and formats:
- Input: base document text (derived or published), optional overlay text read from `<destination>/config/blast-radius.local.json`.
- Output: UTF-8 JSON text, 2-space indentation, trailing newline, written to `<destination>/config/blast-radius.json`.
- Base key emission order is preserved: `version, shared_surfaces, shared_surface_globs, mandate_reads, mergeable_paths, conflict_tolerance, write_intent_extraction, path_roots, modules, over_breadth_fraction`, followed by overlay-only keys.

#### Required configuration keys and defaults:
- Overlay file is optional. Every overlay key is optional. An overlay of `{}` yields the base unchanged in content.

#### Backward-compatibility expectations:
- Existing TypeScript exports remain. Output without an overlay is byte-identical. A destination that hand-edited `config/blast-radius.json` loses those edits on the next push, as it does today. No migration step is provided (decision 3).

#### Performance constraints (latency/throughput/memory):
One additional small file read and one in-memory JSON composition per push. No measurable constraint is set.

  - Consumer readers already fail fast on unknown or malformed values, so a bad overlay key surfaces at read time rather than silently.
  - Reconcile by extension (decision 7).
