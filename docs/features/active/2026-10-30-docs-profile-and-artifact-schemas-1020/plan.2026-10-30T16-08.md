## Design Constraints From Existing Tests

These existing tests scan every file under `.claude/lib`, so they see the new modules without modification; each stays unchanged and must pass.

- `tests/scripts/claude-runtime/enforcement-hooks-no-python-invocation.Tests.ps1` (helpers `EnforcementHooksNoPythonInvocation.Helpers.ps1`, `Get-PythonInvocationFinding`): any `&` invocation whose command position is a variable that is not a `[scriptblock]`-typed parameter of the same file, any `&` of an expression, and any `Invoke-Expression` are reported fail-closed. Therefore the command function and the analyzer function are invoked through `[scriptblock]` parameters: `Invoke-DocsCommandCli` gains an optional `[scriptblock] $CommandFunction` and `Invoke-DocsAnalyzer` an optional `[scriptblock] $AnalyzerFunction`; when not supplied, each is assigned the `ScriptBlock` of the function named by the selected row (`Get-Command -Name <row Function> -CommandType Function`) and then invoked as `& $CommandFunction` or `& $AnalyzerFunction`. `-ImportModule` and the command-context members are `[scriptblock]` values. A command-context member is never invoked as `& $Context.<Member>` (a member expression in command position is reported as `DynamicInvocation`); it is passed to a `[scriptblock]`-typed parameter declared in the same file (for example `Read-DocsSchemaSet -ReadText` or a private helper parameter) and invoked there through that parameter variable. No `Invoke-Expression` is used.
- `tests/scripts/claude-lib/ClaudeLibModuleConvention.Tests.ps1`: every `.psm1` under `.claude/lib` carries the help sentence `imports its siblings with -ErrorAction Stop`, the strict-mode guard pair, and `-ErrorAction Stop` on each column-0 `Import-Module`. The suite discovers `*.psm1` only; `Invoke-DocsCommand.ps1` follows the same conventions by design and is checked in the self-review.
- `tests/scripts/claude-runtime/enforcement-hooks-checkpoint-path-explicit.Tests.ps1`: no new module calls a checkpoint reader.

- `tests/scripts/dev_tools/test_push_down_issue_824_follow_ups.py` (`SOLUTION_SCAN_ROOTS` includes `.claude/lib`): no new file names a solution file.

## Size Justification

- The plan has 44 tasks, above the 40-task guideline (it stays under 400 lines), because the feature creates eight production modules, each with its own Pester suite and evidence, plus eight schemas (six artifact schemas, the definitions-only common schema, and the D5 envelope schema) with seven examples, runtime and bundle copies, a manifest edit, and a tier edit, and because the owner rule requires a per-file artifact classification table (about seventy rows) and separate isolation, scope, token-scan, and CI tasks. The D3 and D5 amendment adds one task ([P1-T6]) for the envelope schema and example; merging it or the module tasks would bundle several binary outcomes into one task.
