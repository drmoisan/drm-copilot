## Executive Summary

This change adds a fourth context-free token-shape rejection to the blast-radius path classifier, in both the Python reference runtime and the PowerShell destination runtime. A whitespace-free inline-code token containing any of `<`, `>`, `${`, `$(`, or `%` is rejected as a repository-path claim, because a token carrying a placeholder or interpolation marker documents a command or artifact *shape* rather than naming a file. The defect it repairs is that two thematically unrelated work items whose plans both quoted the same mandated artifact shape — most often `<FEATURE>/spec.md` or the canonical evidence-path shape — acquired a `path_overlap` conflict edge on a string that resolves to nothing, and were then serialized by the cohort barrier for no reason.

The implementation is small, well-placed, and the reasoning behind every non-obvious choice is recorded at the point of the choice rather than only in the plan. Two new leaf modules hold the predicate (`scripts/dev_tools/_blast_radius_token_shapes.py`, `.claude/lib/blast-radius/BlastRadiusTokenShape.psm1`); the guard is wired into `classify_path_token` and `Get-PathTokenKind` after the root-surface test and before the separator guard; and the ordering is justified in *both* directions in a comment in each runtime. The new modules were not a stylistic preference: the two extraction modules stood at 497 and 498 lines against a hard 500-line limit, so an in-place guard was arithmetically impossible. The relocation of the pre-existing feature-corpus-span predicate into the same leaf is the right call — the two predicates are the same kind of thing — and the relocated PowerShell function is re-exported from its original module so no call site or test breaks.

Evidence reviewed: the full branch diff against `main`; both PR-context artifacts; all 47 feature evidence artifacts under `evidence/`; and independent re-execution of every toolchain stage plus two independent reproductions of the change's central empirical claims. Every stage is clean. Both changed Python production files and both changed PowerShell production files are at 100% line coverage. The reviewer re-derived radii over the 58 active plan folders with the guard active and with only the placeholder predicate stubbed off: path entries fell 3780 → 2473, and all 1307 dropped entries carried a marker character with zero marker-free drops — an exact reproduction of the positive control the spec pins as the fix's safety property. A separate scan established that **zero of 9685 tracked paths carry any of the five markers**, which is direct evidence for the amendment's "a marker-bearing token never matches a tracked path" claim rather than an appeal to its plausibility.

**Top 3 risks:**

1. **The measured throughput benefit on the current corpus is nil.** Edge count fell 1282 → 1267 (1.2%) and density 77.6% → 76.6%, but cohort count stayed at 32 and maximum cohort width stayed at 4. The fix removes a provably-spurious edge class, and the entry-count reduction is large (3729 → 2472, a 34% cut), yet the schedule did not move. At 76.6% density the graph still needs the same number of cohorts. This is not a defect in the change and the evidence artifacts state it openly rather than overclaiming, but a reader who expects concurrency to improve will not see it, and the remaining contention needs its own investigation.
2. **A `%`, `${`, `$(`, or a bare `<`/`>` used as an ordinary character in a genuine path would be silently dropped.** The predicate is purely textual and position-blind by design. The empirical answer here is strong — zero of 9685 tracked paths carry any marker — but the guard is silent by decision (no diagnostic, no finding rule), so a future repository that introduced such a filename would lose the claim with no signal. The mitigations are real and documented: the planner is obliged to append the concrete path explicitly, and `detect_escaped_paths` catches the write against observed diff evidence rather than prose.
3. **The AC-8 fixture clause is unsatisfiable, and the spec text still asserts it.** The withdrawal is correct on the evidence and the substance is discharged by strong tests, but `spec.md` continues to state that a file exists which does not. Left unreconciled, the next reader of that section has to re-derive the seam analysis to understand why the criterion is unchecked.

## Implementation Audit

### Python implementation audit

#### What changed well

- **The guard is one expression over one constant.** `return any(marker in token for marker in PLACEHOLDER_MARKERS)` is the whole predicate. No regex, no configuration lookup, no repository access, no positional logic. The simplest thing that works, and it is the correct thing: the question "was this token written to document a shape" is answered by the presence of a marker anywhere, and any additional structure would only introduce a way to get it wrong.
- **The placement decision is documented in both directions.** The 12-line comment above the guard explains why it runs *after* the root-surface test (exact ordinal equality against a configured surface name; a configured surface cannot contain a marker, so the two tests can never disagree, and a cheaper scan first would only add work to the common accepted case) and why it runs *before* the separator guard (a marker-bearing token usually does carry a separator, so it would sail past that guard and reach the extension rule, which accepts it — and an angle-bracketed leading segment with a real `.md` tail is exactly the dominant corpus shape). This is the part of the change a later editor would plausibly reorder, and the comment is the reason they will not.
- **The new module's existence is justified where a reader will look.** The header block states that the leaf exists "as a separate file rather than as a section of the extraction module, which had two lines of headroom against the 500-line limit when this shape rule was added," and that it "imports nothing from the blast-radius library, so it can be imported by the extraction module without any possibility of a cycle." Both facts are structural, not conventional, and both are verifiable from the file itself.
- **The decision *not* to make the marker set configurable is argued rather than assumed.** The Invariants block states that the set "describes what a path can never contain, not a policy choice a repository could tune, so there is nothing for an operator to configure and no truth-table key to read." This is the right call and the reasoning is what makes it reviewable.
- **The cross-subsystem duplication is addressed by test, not by comment.** `PLACEHOLDER_MARKERS` is asserted character-identical to the tuple of the same name in `scripts/dev_tools/plan_gate_coverage.py`, with a docstring explaining why: two independently maintained copies would drift silently, and the drift would be invisible because each subsystem's own tests would keep passing.
- **The relocation is clean.** `spans_multiple_feature_folders` moved with its two constants and its full docstring intact, and the extraction module's Responsibilities block was updated to name the new leaf and describe what belongs in it. Nothing was left behind and nothing was silently rewritten during the move.

#### Typing and API notes

Fully annotated and clean under Pyright strict: `PLACEHOLDER_MARKERS: tuple[str, ...]`, `contains_placeholder_marker(token: str) -> bool`, `spans_multiple_feature_folders(token: str) -> bool`. `from __future__ import annotations` present. No `Any`, no `cast`, no `# type: ignore`, no `# noqa` anywhere in the diff.

No new public API surface. `classify_path_token`'s signature, return type, and `PathTokenKind` values are unchanged; only its documented rejection set grew, and the docstring was updated to say so. The two new functions are importable but are not part of a published contract — no CLI flag, no MCP input-schema property, no artifact type, no finding-rule literal, and no `config/blast-radius.json` key was added or changed.

#### Error handling and logging

The predicates are total by design: documented as accepting every `str` including the empty string, a marker-only token, and a bare bracket pair, and asserted so by test. This is the correct choice rather than a suppression, and the reason is recorded: the classifier runs over every inline-code span in a document, so a raise on one stray span would abort an entire derivation. The one genuine invariant violation in the touched call chain — an `observed`-source radius reaching `normalize_declared_radius` — still raises `ValueError` before any other work, with a message that states both what was rejected and why.

The rejection is silent: no log line, no diagnostic, no finding. The decision is explicit and its reasoning is sound — a shape citation is not an author error, and reporting one would fire on nearly every plan in the corpus, which is exactly how a diagnostic becomes noise that gets filtered and then ignored. The trade is that a genuine path containing a marker character would be dropped with no signal. That is acceptable here on the measured evidence (zero of 9685 tracked paths carry a marker) and because two independent backstops exist: the planner's explicit-enumeration obligation, and `detect_escaped_paths` comparing the declared radius against what a diff actually touched.

### PowerShell implementation audit

#### What changed well

- **The double-quoting hazard is handled as a correctness requirement, not a style preference, and the reasoning is at the definition site.** The two dollar markers are assembled by character concatenation (`'$' + '{'`, `'$' + '('`) and the header records that "a double-quoted PowerShell string expands the subexpression form and the delimited-variable form, so a double-quoted marker literal would silently define a DIFFERENT vocabulary than the Python reference and the parity would fail on exactly the two members that matter most." This is not hypothetical: the original defect report was itself invalidated by a double-quoted probe, where `"${VAR}/y.cs"` interpolated to `/y.cs` and was then rejected by the leading-separator guard, producing a false "already rejected" reading that survived into `issue.md` and had to be retracted. The countermeasure is applied consistently — every probe in `BlastRadiusTokenShape.Tests.ps1` is single-quoted or concatenated, each case asserts the probe's literal content and length before classification, and the single-quote constraint is stated as a comment inside the test file.
- **Ordinal comparison is chosen deliberately and the reason is recorded.** `IndexOf($marker, [System.StringComparison]::Ordinal)` "keeps the result culture-independent and byte-wise, so it agrees with Python's 'in' operator on every input." A culture-sensitive default would be a plausible source of a parity divergence that no fixture would catch on an en-US machine.
- **The relocation is source-compatible by design.** `Test-MultipleFeatureFolderSpan` is re-exported from `BlastRadiusExtraction.psm1` alongside the new `Test-PlaceholderMarker`, following the module's pre-existing re-import-and-re-export pattern for a relocated ordinal-sort helper — and the comment says so, which is how a reader knows the pattern is established rather than invented here. AC-34's module-export assertion pins it.
- **The `$script:` scope consequence of the relocation is stated.** The header notes that "the two module-scoped documentation-corpus variables it reads travelled with it because `$script:` scope is per module." That is the non-obvious part of moving a PowerShell function and it is the detail a hasty relocation gets wrong.
- **The prose is a faithful port, not a paraphrase.** The ordering comment inside `Get-PathTokenKind` matches the Python comment sentence for sentence. A future editor who changes one and not the other will see the divergence immediately.

#### API and safety notes

Both functions are advanced functions with `[CmdletBinding()]`, `[OutputType([bool])]`, and `[Parameter(Mandatory = $true)] [AllowEmptyString()] [string] $Token`. `AllowEmptyString()` is load-bearing rather than decorative: without it the empty-string totality contract the tests assert would throw at the parameter binder. `Set-StrictMode -Version Latest` is set. Both use approved verb-noun naming with the `Test-` verb and return a plain `[bool]`. Neither needs `ShouldProcess` — both are read-only predicates with no side effect. `Export-ModuleMember` is explicit and lists exactly the two functions.

PSScriptAnalyzer reports 0 diagnostics across all five changed PowerShell files, and `Invoke-Formatter` under `scripts/powershell/PoshQC/settings/pssa.settings.psd1` reports all five already formatted.

#### Error handling and logging

Same design as Python and correctly mirrored: total predicates, silent rejection returning the same `$null` the four sibling rejections return, and the reason recorded in the `Get-PathTokenKind` help text ("there is no diagnostic channel and no finding rule, because a shape citation is not an error on the author's part and reporting one would fire on almost every plan").

It corrects "three token shapes" to "four" on a single line, adds a `### Placeholder-shape rejection (issue #502)` subsection with the marker set in a fenced block, cross-references `.claude/rules/plan-acceptance-gates.md` as the set's origin, and records five distinct arguments as substantive paragraphs rather than mentions: the never-matches-a-tracked-path rationale including the Windows-reserved-character argument; the mandated-artifact origin of the dominant token (which is why the exposure was corpus-wide rather than incidental, and the observation that admitting the token "made compliance with the evidence-path scheme a source of contention" is the sharpest sentence in the amendment); the planner's obligation to append a concrete path, tied to the same `detect_escaped_paths` backstop the mandate-read exclusion uses; the accepted fail-open trade with its measured-empty corpus exposure and an explicit obligation on any future widening to re-take the measurement; and the whitespace-split residual, recorded as a known residual rather than presented as complete coverage.

## Test Quality Audit

The test work is the strongest part of this change. Six test files and three fixtures were added or extended, and the recurring pattern is that every rejection assertion is paired with a control that would fail if the guard were too broad. That pairing is what makes the suite discriminating rather than merely green.

Three examples worth naming:

- **The pair-level regression test** (both runtimes) asserts that the un-normalized pair conflicts *before* asserting that the normalized pair does not. Its docstring explains why both halves are required: `conflicts` never calls the classifier, so a hand-authored pair contends on a shared placeholder whether or not the guard exists — asserting the raw pair proves nothing — and without the pre-normalization control, a construction error that left the pair disjoint from the start would satisfy the post-normalization assertion vacuously. This is the test that carries AC-8's substance, and it is stronger than the withdrawn fixture would have been, because its second assertion routes through the classifier and therefore fails on a tree where the guard is absent.
- **The fail-open trade test** is paired with `test_concrete_shared_surface_glob_match_is_still_reported`, whose docstring states the reason plainly: without the control, the companion "could be satisfied by a change that stopped resolving shared-surface globs altogether, which would be a far larger regression than the trade it documents."
- **The positive control** `test_real_path_on_same_task_line_survives_placeholder_rejection` deliberately asserts survival only and makes no claim about the placeholder token, so it holds both before and after the guard exists. Its docstring explains that duplicating the rejection assertion there "would turn the positive control into a second copy of the same negative assertion and it could no longer show that the guard's scope stayed narrow across the change." That is a subtle and correct piece of test design.

Determinism and hygiene are clean throughout. Every input is an in-memory literal; `computed_at` and `tracked_file_count` are supplied rather than read; no temporary file, filesystem write, subprocess, network call, wall-clock read, or `Start-Sleep` appears in any new test. Fixture truth tables are per-fixture literals precisely so a change to the committed `config/blast-radius.json` cannot silently change what a test exercises.
