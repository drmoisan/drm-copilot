## Design Decisions (fixed by this plan)

1. **Matcher contract.** `Test-WorktreeRunRecordedPathMatchesTarget -RecordedPath -TargetPath -BaseRoot <string[]>` returns `$true` when the recorded path is rooted and `Test-WorktreeRunPathEqual` holds against the target, or when the recorded path is relative and safe and `Test-WorktreeRunPathEqual` holds for the join of the recorded path to at least one non-blank base root. A relative recorded path is unsafe, and matches nothing, when it is blank, is `.` or `..`, has a `.` or `..` segment after separator normalization, or contains `:`. A blank target matches nothing. The rooted test is applied after backslash-to-slash normalization and uses the same pattern as `$script:AbsolutePathPattern` in `WorktreeRunResolution.psm1`, which already admits drive-letter roots, single-slash roots, and `//` roots; a drive-relative value such as `c:x` is not rooted and is rejected by the `:` rule. The function is pure.
2. **Main checkout root.** `Get-WorktreeRunMainCheckoutRoot -SessionRoot` returns the first live root from `Get-WorktreeItemLiveRoot -SessionRoot` whose `<root>/.git` entry is a `Directory` per `Get-WorktreeResolutionGitEntryKind`, and `$null` when none is. It is the module's only filesystem seam and is called at most once per resolution or gate decision.
3. **Base roots (D1).** Every site passes `@(<main checkout root>, <root that holds the checkpoint being read>)`, with blank entries dropped. Run resolution calls `Get-WorktreeRunMainCheckoutRoot` only when `RecordField` is `worktree_path`, so pull-request-number and slug resolution, and every hook suite that exercises them, make no new call.
4. **Optional parameter, safe default.** Every matcher-family function gains an optional `-BaseRoot [string[]]` parameter defaulting to an empty array. With no base roots, a relative record matches nothing and an absolute record matches exactly as before, so every existing direct caller and helper test keeps its behavior.
5. **Case rule.** The family adopts the `Test-WorktreeRunPathEqual` rule (ordinal for single-slash POSIX roots, ordinal-ignore-case for drive-letter and `//` roots). At the gate `Find-*` sites this is not observable for a POSIX case variant, because run resolution already applies the ordinal rule before any checkpoint is read. At `Test-CleanupManifestCheckpointCoversPath` a POSIX case variant names a different directory on a case-sensitive file system, so not treating it as covered is correct.
6. **Skill heading budget.** `test_orchestrate_skill_first_thirteen_headings_match_required_layout` pins exactly sixteen `##` headings and `test_agent_body_contains_exactly_the_nine_required_headings` pins nine agent `##` headings. `Run Closing` is therefore a `### Run Closing` subsection, at the end of `## Worktree Cleanup` in the skill and at the end of `## Completion Requirements` in the agent.
7. **Scratch-worktree safety (D5).** The closing step runs the `cleanup-merged-worktrees` report first and runs its `--apply` form only when every row the report marks delete-eligible is a worktree this run created (an item worktree or a planner scratch worktree named in the run's records). Otherwise it applies nothing and reports each scratch worktree as a deferral. Reason: `--apply` is repository-wide and can classify a concurrent session's clean, zero-commit worktree as merged.
8. **Out of scope:** the merge-gate hooks (`enforce-epic-merge-gate*.ps1`), the #670 authorization branch, the `epic_mode` merge prose, every `.codex`, `.agents`, and `.github` file, the Codex bundle, the pre-implementation, pr-author, and merge gate exemptions, and the execution-environment brief (it states no fact this plan changes; `test_execution_environment_brief_contracts.py` is re-run to confirm).

- Evidence: Three behaviors cannot be shown before merge, and the plan treats them as deferral behaviors, not acceptance facts. LV3: `Agent(pr-author)` from the forked `parallel-orchestrator` with a `branch:` label and no issue number may fail the model-routing receipt check; the closing step reports that the records pull request needs manual authoring. LV4, the fresh two-cohort rerun, is post-merge. No acceptance criterion asserts any of the four outcomes, and [P6-T13] confirms the spec labels them that way.

## Size Justification

The plan carries more than 40 tasks because the spec requires one task per matcher-family site, one task per bundle mirror pair (nine pairs), a separate landing task for the earlier run's leftover records, and per-step evidence tasks for both PowerShell and the one changed Python contract test. Merging those tasks would remove the per-site and per-pair acceptance conditions the spec's risk mitigations depend on.
