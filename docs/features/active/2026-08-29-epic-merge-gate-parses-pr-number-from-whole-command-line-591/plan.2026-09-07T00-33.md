## Line-counting method

Every line count in this plan is the count an editor reports: the number of lines including a final line that carries no trailing newline. Obtain it with `awk 'END{print NR}'` naming the file. Do not use `wc -l`, which counts newline characters and therefore reports one fewer line for a file whose final line carries no trailing newline. `.claude/hooks/enforce-epic-merge-gate.ps1` is such a file: its final line is `exit ([int]$entryPointResult[-1])`, the editor-reported count re-derived while authoring this plan is 452, and `wc -l` reports 451. ## Diff-form rules used throughout this plan

The anchor ref for every diff assertion is `origin/epic/cleanup-merged-worktrees-hardening-integration`. No `git diff` in this plan is written without a ref operand.

Two forms are used, deliberately and for different reasons:

- **Three-dot (`origin/epic/cleanup-merged-worktrees-hardening-integration...HEAD`).** This is the form `spec.md` mandates for AC11, AC18, AC19, and AC20. It compares the merge base against the `HEAD` commit and therefore **cannot observe staged or unstaged work**. Every task in this plan that runs a three-dot diff is preceded by a commit that puts the work in `HEAD`: [P4-T5] and [P5-T5] each commit their own owned paths before their diff, and [P6-T1] is a dedicated commit task that puts every remaining owned path in `HEAD` before the Phase 6 and Phase 7 gates run.
- **Two-dot (`origin/epic/cleanup-merged-worktrees-hardening-integration -- <path>`).** Compares the ref against the **working tree**, so it observes uncommitted edits. Used where the assertion must observe the working tree before a commit exists, specifically [P3-T7] and [P7-T5]. It carries a ref operand and is not a name-listing diff. No commit is required before either of those two tasks, and neither is affected by the commit ordering above.

Every name-listing diff (`--name-only` or `--name-status`) in this plan is paired with an explicit `git add --` span naming the owned paths and a `git status --porcelain` span in the same task, because a diff anchored to a ref enumerates tracked changes only and cannot observe a path the task creates. No task in this plan uses `git add -A`: `-A` stages paths outside the owned set, which would then enter the listing the owned-set gate asserts against, and `.claude/hooks/enforce-orchestration-preimplementation-gate-helpers.ps1` models `git add` positively at lines 230 through 279, where a dash-leading token on the `add` subcommand returns false at line 258 and denies the bookkeeping exemption. Every staging command in this plan is `git add --` followed by the explicit owned paths present in the working tree.

Three diff assertions in Phase 6 are written with `git diff --exit-code`, which returns 0 when the diff is empty and 1 when it is not. A bare `git diff` exits 0 whether or not it printed a diff, so an `EXIT_CODE: 0` assertion over the bare form cannot fail; `--exit-code` is what gives that assertion a source.

## Pester invocation form used throughout this plan

`Invoke-Pester -Path <file> -Output Detailed` does **not** set the process exit code on failure, because `Run.Exit` is a setting of `scripts/powershell/PoshQC/settings/pester.runsettings.psd1` and is not applied by a direct `-Path` invocation. An acceptance condition gated on the exit code of such a run therefore cannot fail. Every Pester task in this plan consequently uses `-PassThru`, captures the result object, and gates on `PassedCount` and `FailedCount` read from that object. Every Pester invocation in this plan is therefore written in one wrapped form, `pwsh -NoProfile -Command "$r = Invoke-Pester -Path <file> -Output Detailed -PassThru; exit $r.FailedCount"`, so the process exit code has an explicit source: it **is** the run's failed count. `EXIT_CODE:` in each Pester artifact is that failed count and nothing else, and the artifact states that derivation. The wrapped form makes the exit code falsifiable in both directions — 0 on a clean run and non-zero on a failing one — which a bare `Invoke-Pester -Path` invocation cannot do, because it applies no `Run.Exit` setting and returns 0 whatever the tests did. Per-`It` evidence is produced by projecting the result object's test collection, for example `$r.Tests | Where-Object { $_.Name -in @('name one','name two') } | Select-Object Name, Result | Format-Table`, rather than by a name-filter parameter, because a filter that matches nothing yields a failed count of 0 and would satisfy a bare failed-count clause. Every acceptance condition in this plan that reads a filtered or projected result therefore asserts an exact row count alongside each row's `Result` value, so an empty projection fails rather than passes.

## Dependency: the `hook-command-scanner.ps1` helper (issue #545)

This feature **consumes** a shared helper that issue #545 delivers and that **does not exist in the working tree today**. A glob over `**/hook-command-scanner*` executed while authoring this plan returned no files, and `.claude/hooks/enforce-epic-merge-gate.ps1` contains no reference to it.

No concrete PowerShell function name for that helper is pinned anywhere in issue #545's committed spec, plan, or research. **This plan therefore names no function, parameter, or return type of the helper.** It describes the dependency by three capabilities, exactly as `spec.md` "Execution-Time Re-derivation Requirements" does:

1. **A per-segment command scanner** producing an ordered segment list, each segment recording `RawText`, `MaskedText`, `Tokens`, `HasLiveSubstitution`, and `Unbalanced`.
2. **Scan-text selection by three ordered clauses**, first match winning: `Unbalanced` or `HasLiveSubstitution` selects `RawText`; a leading command word in the fourteen-member wrapper carve-out set, determined after skipping `VAR=value` env-assignment prefixes, selects `RawText`; otherwise `MaskedText`.
3. **A structural relocation classifier** over a segment's `Tokens` with the modeled `gh` global-option table.

Phase 1 re-derives the helper's real API from the merged file **before any code is written in Phase 3**. Phase 1 is blocking: if the helper is absent, the executor halts and escalates to the epic orchestrator and does not select the Defect-1-only fallback (spec D4).
