## 1. Current Gate Decision Flow

Entry: `Invoke-OrchestrationPreimplementationGateDecision` in `.claude/hooks/enforce-orchestration-preimplementation-gate.ps1` (Codex twin `.codex/hooks/enforce-orchestration-preimplementation-gate.ps1`, same deny text verified by grep).

1. Classification. `Test-ImplementationPath` (Write/Edit): any path matching `(^|/)docs/features/active/` is never implementation (`Test-FeatureDocumentationOrEvidencePath`); the seven checkpoint literals in `$script:CheckpointPaths` are never implementation; otherwise only `.py .ps1 .psm1 .ts .tsx .js .jsx .cs .json .yml .yaml` are implementation, so any `.md` write is already allowed everywhere. `Test-ImplementationCommand` (Bash): `git add`/`git commit` is implementation unless `Test-ExemptOrchestrationStagingCommand` (helpers file, issue #539) holds: every segment is `git [-C <abs>] add|commit`, commit options limited to `-m`, `--message`, `--trailer`, at least one pathspec operand, and every operand under `docs/features/epics/`, `docs/features/parallel/`, `docs/features/active/`, `docs/features/potential/`, or `artifacts/orchestration/`.
2. Epic scope first: `Get-OrchestrationEpicScopeDecision` (epic-scope sibling). Non-epic scope returns `$null`.
3. Single-feature path: `Read-OrchestrationGateCheckpoint -Mode single-feature` reads `artifacts/orchestration/orchestrator-state.json` beneath the worktree that `Resolve-HookTargetWorktree` resolves; `Test-OrchestrationReady` requires only `issue-num`, `feature-folder` starting `docs/features/active/`, `route_id` or `path_selected`, and boolean `lifecycle_ready: true`. Then the cleanup leg; then the deny `PREIMPLEMENTATION_GATE_BLOCKED: Implementation operations require artifacts/orchestration/orchestrator-state.json to contain issue number, feature folder, route metadata, lifecycle readiness, and checkpoint state before implementation begins.`

Verified consequences for a follow-up on merged feature F:

- Already allowed today (no checkpoint needed): Write/Edit of any file under `docs/features/active/<F>/`; Write/Edit of any `.md`; `git add <paths under the five trees>`; `git commit -m <msg> -- <paths under the five trees>`.
- Denied today: (a) `git commit -F <file> ...` and `--file` (not modelled by the #539 exemption, although the execution-environment brief directs agents to pass messages with `git commit -F`); (b) a pathless `git commit -m <msg>` after staging (rows 1/4/7 of #539: no operand, no exemption); (c) any `git add`/`git commit` or `.json`/`.yml` write under `docs/features/completed/<F>/` (not a bookkeeping tree, not the active prefix); (d) any code or configuration edit.
- Where the deny is issued depends on the target worktree:
  - T-INT (integration worktree, HEAD = `integration_branch`): epic scope. `Get-EpicCommandLegReadinessFailure` (`.claude/lib/worktree-resolution/EpicScopeReadiness.psm1`) returns `merge-in-progress` for every structurally valid epic checkpoint when no `MERGE_HEAD` exists. The deny is the session-root wording of `Resolve-OrchestrationEpicTargetOutcome` (`...failed readiness predicate is 'merge-in-progress'...`) or `target-not-ready` from `Get-OrchestrationEpicTargetDenyReason` (targets file). The #1136 allowance lifts it only when fan-in is complete and only for `epic-status.md` and `artifacts/pr_body_<N>.*`. A per-item checkpoint is never read in epic scope, so a hand-authored one cannot help here.
  - T-ITEM (F's old worktree, or a new follow-up worktree on a branch other than the integration branch): not epic scope, single-feature deny above. If F's original worktree still exists with its child checkpoint, `Test-OrchestrationReady` still passes (it has no terminal-state conjunct). After `git worktree remove` (`merge_status: worktree_removed`) or in a fresh worktree, no checkpoint exists (artifacts/ is gitignored), so the deny fires and a hand-authored checkpoint with the four fields passes. This matches the reported workaround ("lifecycle_ready + receipts"; the receipts are demanded by the stop-hook validators, not the gate).
- The exact deny text of the reported incident is unknown (no log attached). T-ITEM is the only topology in which a hand-authored readiness checkpoint changes the outcome, so it is the probable reported path; T-INT is the topology a documented path should use.

## 4. Candidate Designs

### Selected: (A) Epic-recognized merged-feature follow-up allowance

- Qualifying state, all required: the call is in epic scope (HEAD of every target equals `integration_branch` of a resolved epic checkpoint with `route_id` `epic`); the readiness failure is exactly `merge-in-progress` (every structural conjunct passed and no merge is in progress); fan-in completeness is not required.
- Qualifying feature: a `features[]` entry with `merge_status` in `{merged, worktree_removed}` (reuse `$script:EpicFanInTerminalMergeStatuses`), a `feature_folder` whose basename (after stripping an optional `docs/features/active/` or `docs/features/completed/` prefix) matches `$script:EpicFanInSlugPattern`, and provenance `merge_commit_sha` (lowercase 40 or 64 hex) and `pr_number` (JSON integer > 0).
- Allowed roots per qualifying feature: `docs/features/active/<basename>/` and `docs/features/completed/<basename>/` (trailing slash required, so `<basename>-x/` does not match), plus the status document from `Get-EpicFanInStatusDocRelativePath`.
- Allowed calls: Write/Edit whose every path lies under an allowed root; `git [-C <abs>] add [--] <p...>` with every operand under an allowed root; `git [-C <abs>] commit` with only `-m --message -F --file --trailer` and either `-- <p...>` all under allowed roots, or pathless with a non-empty staged index (`Get-OrchestrationGateStagedIndex`) whose every name lies under an allowed root. `-a`, `--amend`, `-A`, globs, `..` segments, backslashes, and chained non-git segments stay denied (the existing unresolvable/balanced checks apply).
- Provenance: the epic checkpoint written by `epic-orchestrator` (the same trust source #1136 uses), plus per-feature `merge_commit_sha` and `pr_number`. No per-item checkpoint is read or accepted.
- Hand-authored checkpoint denied: in epic scope the item checkpoint is never consulted, so a hand-authored `orchestrator-state.json` changes nothing; an epic entry lacking `merge_commit_sha` or `pr_number`, or with a non-terminal `merge_status`, is denied with the unchanged `merge-in-progress` text. Residual: a same-session writer can edit the epic checkpoint (policy-level control, as #1136 and D10 state).
- Newly blocked calls: none; it is allow-side only and every existing deny text is unchanged.
- Implementation: generalize `Get-EpicFanInShapeDetail` and `Test-EpicFanInStagedIndex` from one status-doc path to an allowed-path predicate (the #1136 behavior becomes the one-path case, keeping its tests green), add `Get-EpicMergedFeatureRoots` and `Get-EpicMergedFeatureFollowUpAllowance -Scope -FilePath -Command -StagedIndexReader` to `hook-epic-fan-in.ps1` (estimate 440 to 480 lines, under the 500 guidance; a sibling file would add manifest and dependency-closure entries), and add one disjunct in each surface's `Get-OrchestrationEpicScopeDecision`.
- Documented path: follow-ups on a merged epic child are made in the integration worktree on the integration branch; code corrections are not follow-ups and go through a new orchestrated child.

### Rejected alternatives

- (B) Follow-up record written by a named skill step (for example `artifacts/orchestration/followup-<issue>.json` with merged PR number, merge commit, epic checkpoint reference) and validated by the gate in the item worktree: its provenance must be cross-checked against the epic checkpoint anyway, so the epic checkpoint remains the authority; the record is as easy to hand-author as today's checkpoint; it adds a schema, a writer step, a validator in the PowerShell (and by convention Python/TypeScript) runtimes, and a new gate leg in the single-feature path.
- (C) Model `-F`/`--file` and add `docs/features/completed/` to the #539 exemption: widens a context-free exemption for every caller, does not recognize merged state, and leaves pathless commits denied.
