## Why The Treatment Is Asymmetric (read before Phase 1)

The Claude side **extracts a new helpers file**; the Codex side **adds the branch in place**. This
is deliberate and is not a parity gap.

- `.claude/hooks/enforce-epic-merge-gate.ps1` is **487** lines by `@(Get-Content).Count` against
  the repository's 500-line cap. Thirteen lines of headroom cannot absorb a fourth branch, its
  predicate, and a header rewrite, so the new concern goes to a new file
  `.claude/hooks/enforce-epic-merge-gate-authorization.ps1` and two pure envelope factories move
  out of the parent to buy back headroom.
- `.codex/hooks/enforce-epic-merge-gate.ps1` is **186** lines, leaving over 300 lines of headroom.
  Adding the branch in place there avoids a second Codex pack-manifest entry, a second
  byte-identity list entry, a second coverage-configuration entry, and a second bundled file.
- **Codex parity means behavioural parity on the standalone decision plus byte-identical reason-code
  spelling.** The Codex hook has **no** parallel allow path and **must not acquire one**. Its allow
  representation stays `$null`, its `exit 2` throw channel stays, its wider `step9_status` accepted
  set stays, its stricter `epic_mode` type test stays, and its `$PSScriptRoot`-derived repository-root
  path anchoring stays.

## `--squash` Correction (do not reintroduce the false premise)

`--squash` is **currently allowed** and is out of the gate's trigger scope on both runtimes. The
scope filter at `.claude/hooks/enforce-epic-merge-gate.ps1:401-414` requires **both** a structural
`gh pr merge` invocation **and** a `--merge` flag; a command carrying `--squash` and not `--merge`
returns an allow at line 413 before any allow-or-deny branch runs. This is pinned by the currently
passing test at `tests/scripts/claude-hooks/enforce-epic-merge-gate.Tests.ps1:27`,
`It 'allows gh pr merge without --merge (e.g., --squash)'`. **No task in this plan makes `--squash`
deny.** The line-27 test stays green and stays byte-unedited, and a new paired case is added
proving that the presence of a valid authorization record does not widen trigger scope.

1. **The 500-line cap forbids an additive-first order.** The parent hook is at 487 lines. Adding the
   dot-source line, the branch-4 call block, and the header rewrite before removing anything lands
   the file at roughly 500-505 lines, which breaches the cap in an intermediate state. The extraction
   in [P1-T1] and [P1-T2] therefore lands **first**: removing
   `Get-EpicMergeGateAllowDecision` (currently lines 327-338) and `Get-EpicMergeGateBlockDecision`

   ([P4-T1] about 8 lines, [P4-T2] about 10 net lines) lands the parent at roughly **478**. No
   intermediate state exceeds 500.
2. **The fail-first test tasks are ordered so that no whole-suite exit-0 gate precedes their fix.**
   [P2-T3] and [P5-T2] are `[expect-fail]` runs of new suites. Every gate between [P2-T3] and
   [P4-T4], and between [P5-T2] and [P5-T4], runs **named existing suites by explicit path only**.
   No task in Phases 2 through 5 runs the whole `tests/scripts` tree and requires zero failures. The
   first whole-tree run is [P8-T4], after every implementation task has landed.
3. **The bundled-mirror parity window is open from [P1-T1] to [P6-T8], deliberately.** Creating
   `.claude/hooks/enforce-epic-merge-gate-authorization.ps1` immediately makes
   `tests/scripts/dev_tools/test_push_down_claude_resource_contracts.py::test_bundled_claude_payload_contains_all_repo_runtime_contracts`

   **No task between [P1-T1] and [P6-T8] asserts that test green.** Mirroring happens once in
   Phase 6, after every repository-side edit is final, and is re-verified inside the Phase 8 loop.
4. **Formatting precedes mirroring, and the Phase 8 loop re-syncs mirrors after formatting.** A
   formatter run that rewrites a repository-side file after the mirror was copied leaves the mirror
   stale and fails byte-identity. [P8-T3] re-syncs the mirrors after [P8-T1] and before [P8-T4].
5. **Coverage registration precedes the coverage baseline that the comparison uses.** The Phase 0
   baseline is the true pre-change baseline. [P1-T6] takes a second, post-registration coverage
   baseline **after** `.claude/hooks/enforce-epic-merge-gate-authorization.ps1` exists and **after**
   it has been added to `CodeCoverage.Path`, and that is the baseline the [P7-T2] comparison uses
   for the new file.
6. **Phase 0 leaves no formatter repair in the tree, and Phase 8 re-verifies the bound it may
   disturb.** [P0-T5] restores every path its formatter run rewrote, so the hunk-range analyses in
   [P4-T3] and [P5-T5] observe only this change's own edits rather than a pre-existing repair the
