## Implementation Audit

### PowerShell implementation audit

#### CR-1 admission-path trace

1. `Test-ImplementationCommand` (Claude gate line 155, Codex gate line 170) calls `Test-ExemptOrchestrationStagingCommand -CommandText $normalizedCommand`. The normalization is `.Trim()`, which removes whitespace only and leaves quote characters in place.
2. `Test-ExemptOrchestrationStagingCommand` returns `$false` for empty text. It then calls `Test-OrchestrationCommandTextUnresolvable` (line 469) before `Split-OrchestrationCommandLine` or any tokenization.
3. `Test-OrchestrationCommandTextUnresolvable` line 131 returns `$true` when any of the seven characters is present anywhere in the text. The check does not depend on quote state.
4. No other function in the helper returns an allow-side result. A grep for `Test-ExemptOrchestrationStagingCommand` over both hook trees finds only the two gate call sites.

Conclusion: no `$` or backtick in text containing U+2018 to U+201E can reach the line-140 single-quote allowance.

#### Residual quote-state agreement with a PowerShell interpreter (reviewer analysis)

With the seven typographic characters excluded, the remaining quote characters are ASCII `'` and `"`. The reviewer checked each PowerShell construct that could make PowerShell's quote state differ from the scanner's POSIX model:

- A doubled single quote (`''`) is an escaped quote inside a PowerShell single-quoted string, but toggles the quote state twice in POSIX. After any run of `k` consecutive `'` characters, both readings are in the same state. The two readings therefore agree at every non-quote character, including every `$` and backtick. The same parity argument applies to `""` inside double quotes.
- A backtick escape inside double quotes (`` `" ``) is denied, because backtick is unresolvable inside double quotes.
- A single-quoted here-string (`@'` ... `'@`) is literal in PowerShell. The scanner reads a single-quoted span, so the two readings agree.
- The double-quoted here-string (`@"`) expands, and the scanner denies the `$` inside it.
- The stop-parsing token `--%` is denied by `Test-ExemptOrchestrationSegmentToken`. Before `--` it is an unmodelled dash option (line 415). In the subcommand position it fails the selector check. After `--` it is an operand that fails the exempt-prefix test.

The reviewer found no remaining PowerShell construct that admits `$` or backtick. This is static analysis only. `pwsh` was not executed, because the worktree-isolation guard denies it in this agent session.

#### What changed well

- **Minimal change.** One constant was added. One disjunct was appended to an existing early return that was already documented as the "moves a span boundary the scan cannot model" check. No new function or branch was added, and the line count is net zero (11/11 per copy against `0ccba6b3`).
- **ASCII-only source.** The constant uses integer code points (`[char[]]@(0x2018, ...)`), and the tests build the characters with `[char]0x....`. This keeps both files free of non-ASCII bytes and avoids encoding-dependent parsing on Windows PowerShell hosts.
- **Documentation parity.** The constants comment, the function help, the row-12 comment, and both skill-document pairs describe the same rule.

#### Error handling and logging

- The new path returns `$true` from the unresolvable check, which yields `$false` from the exemption (fail closed). If `$script:TypographicQuoteCharacters` were ever `$null` in scope, `IndexOfAny($null)` would throw. That exception would propagate out of the predicate instead of admitting the command; it would not silently allow. The constant is defined at script scope beside the existing `$script:` constants that the same function already reads, and the passing deny rows show that it resolves on both runtimes.
