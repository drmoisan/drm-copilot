# `pytest-xdist-parallel-test-cycle` — User Story

- Issue: #1048
- Owner: drmoisan
- Status: Draft
- Last Updated: 2026-10-31T13-30

## Story Statement

- As a repository developer, I want the Python suite to run in parallel workers locally and in CI, so that the test cycle takes less wall-clock time without changing coverage results.
- As a repository developer, I want one local command and VS Code task that runs the Pester shards concurrently and merges their JUnit and coverage output, so that a full local run finishes faster and still produces the artifacts and exit code of a serial run.
- As a CI maintainer, I want Pester shard assignment based on measured per-file durations, so that the shards finish together and the Pester wall-clock time falls.
- As an agent or contributor reading the execution-environment brief, I want its test-runtime guidance to describe the parallel options for both runners, so that I diagnose first and use the supported parallel mechanism.

## Problem / Why

The repository's two large test suites run slowly, locally and in CI.

**Python (pytest).** The suite runs serially in CI on four Python versions, and the `quality-checks7 / Code Quality & Tests (3.13)` job took about 18 minutes on a recent run. Locally there is one `QC: 4 Pytest: run tests` task and no parallel option. A downstream repository measured `pytest-xdist`: on a 2 vCPU runner `-n auto` gave no gain (269 s against 275 s serial), on a 16-core runner it took 43.8 s with 16 workers, and locally 2 workers were 1.75 times faster than 1. The public `ubuntu-latest` runner has 4 vCPUs, so the measured CI result decides what is kept.

**Pester (PowerShell).** CI shards Pester across Windows runners with `Invoke-PoshQCTest -ShardIndex -ShardCount`, but a recent run's shards took 462 s, 290 s and 364 s because shard weights are file byte sizes, not durations. Locally a full run is a single process taking a very long time, with no way to run shards concurrently. Pester 5 has no in-process parallel mode, and coverage must come from a merged result.

## Personas & Scenarios

- Persona: Repository developer on a multi-core Windows machine
  - Runs the Python and Pester suites many times a day before pushing.
  - Cares about fast feedback and about trustworthy, order-independent results.
  - Constrained by the VS Code Test Explorer, which breaks if `-n` is placed in `addopts`, and by coverage artifacts that must come from a merged, complete run.
  - Frustrated by a single-process Pester run that takes many minutes.
- Scenario: Developer runs the full local checks
  - The developer finishes a change and wants full test results.
  - They run the parallel pytest task and the concurrent Pester task from VS Code.
  - The Pester runner starts several `pwsh` shard processes (default half the logical cores, at most 8), waits for all, and merges JUnit and coverage into `artifacts/pester/`.
  - If any shard fails, the command exits non-zero and does not overwrite the previous merged artifacts with partial output.
  - The developer expects the same totals and pass/fail result as a serial run, in less time.

- Persona: CI maintainer
  - Owns `_quality-checks.yml` and `_poshqc.yml` and the required-check contexts.
  - Cares about job duration, balanced shards, and a green branch-head run before merge.
  - Constrained by weights that must be identical in every shard job, so they are committed, not measured at run time.
- Scenario: Maintainer rebalances shards
  - The maintainer downloads JUnit artifacts from the newest full green run and regenerates `config/poshqc-shard-weights.json` with the documented PowerShell command.
  - Shard jobs compute the same assignment from the committed weights, with the median fallback for new files.
  - They compare before and after durations and decide from the measurement whether a further shard is needed.

## Acceptance Criteria

- [ ] `pytest-xdist` is a locked dev dependency, `poetry.lock` is regenerated by Poetry, and no `psutil` dependency is added.
- [ ] The CI step `Run tests with Pytest` runs in parallel with `-n auto` or a fixed `-n 4` (whichever measured faster), `-n` is not in `addopts`, the serial task remains, and the coverage threshold step passes on the merged `coverage.json`.
- [ ] Parallel pytest tasks exist in `.vscode/tasks.json` for unit tests and for unit tests with coverage and the lcov report.
- [ ] The `importlib.reload` leak in `test_resolve_hard_lock_prompt.py` is fixed in test code, and the Python suite passes serially, in repeated `-n auto` runs, in a seeded shuffled run and in a reversed-order run, with no order dependence.
- [ ] The before and after duration of `quality-checks7 / Code Quality & Tests (3.13)` is recorded, including both `-n auto` and `-n 4` timings.
- [ ] Each pytest strictness option has a recorded adopt or defer decision with the reason.
- [ ] A local command and VS Code task run Pester shards concurrently from a new `PoshQC.Parallel.psm1`, using new output-path parameters on `Invoke-PoshQCTest`, merge the JUnit output with a new merge function and the coverage output with the existing coverage merge, and produce the same artifacts and exit semantics as a serial run.
- [ ] The CI Pester shards are balanced from committed measured weights with a size-based fallback, and the before and after wall-clock time of the Pester jobs is recorded.
- [ ] The slow-file profile of Pester test files at or above 10 s is recorded as diagnosis, with non-trivial fixes filed as follow-ups.
- [ ] Pester suites pass when run as concurrent shards and under seeded shuffled file-order runs, with no cross-file state leaks and no ordering workarounds.
- [ ] Every changed or new PoshQC file has a bundled mirror, and the bundled parity test passes with the new module path.
- [ ] The brief's `## Test Runtime` section is updated in every copy and the mirror contract tests pass.
- [ ] `test_quality_checks_workflow_contracts.py` passes with the changed pytest step, and the PoshQC and workflow contract tests pass with the changed Pester path.
- [ ] No new Python script is added.

## Non-Goals

- Classifying pytest tests into `architecture`, `contract` and `integration` markers, and sharding integration tests in CI.
- A VS Code Test Explorer workspace settings file.
- Pester 6 `Run.Parallel`, in-process `ForEach-Object -Parallel`, and per-shard generated settings files.
- Narrowing or merging the Linux hook-suite job.
- Product or test fixes from the slow-file profile beyond trivial ones (recorded as follow-ups).
- Adding a fourth Pester shard unless the measured balance requires it.
