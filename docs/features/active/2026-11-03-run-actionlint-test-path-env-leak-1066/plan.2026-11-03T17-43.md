- Container profile: for each JUnit `testsuite` (one per suite file, named by its repository-relative path, as written by `SCRATCH/issue-1066-junit-writer.ps1`), `tests` is the number of testcases whose name does not end with `[block]` or `[container]`, `failed` is the number of those with a `failure` or `error` child, `blocks` is the number of failing testcases whose name ends with `[block]`, and `container` is 1 when a failing testcase name ends with `[container]` and 0 otherwise. A profile P is within a profile Q (`P <= Q`) when `failed`, `blocks`, and `container` of P are each not greater than those of Q and `tests` is equal. Profiles depend on counts only, so a naming artifact cannot change a comparison outcome.

## Design Decisions Fixed by This Plan

- DD1 Fix: a single `BeforeEach` and `AfterEach` pair directly in `Describe "run-actionlint.ps1"` saves and restores `$env:PATH` (value and existence) and `$global:LASTEXITCODE` (existence and value; restore removes the global variable when it did not exist). The `Context "Add-DirectoryToPath"` `BeforeEach`/`AfterEach` pair that uses `$script:originalPath` is removed, because the Describe-level pair runs outside it on every `It` and restores the same value, so behavior is unchanged. The Describe-level `AfterEach` runs while the `Install-Actionlint` Context mocks (`Test-Path`, `Join-Path`, `Remove-Item`, `New-Item`, `Write-Information`) are still active, so the pair uses only `$env:PATH` assignment, variable assignment, and `Remove-Variable`, and calls none of those mocked commands.
- DD2 Guard form (b): `GUARD` runs `TARGET` through a nested in-process `Invoke-Pester` with a configuration of `Run.PassThru` true, `Run.Exit` false, `Output.Verbosity` `None`, `TestResult.Enabled` false, and `CodeCoverage.Enabled` false, and compares `[Environment]::GetEnvironmentVariables()` before and after in an `OrdinalIgnoreCase` dictionary (added, removed, or ordinally changed values). `$global:LASTEXITCODE` is compared against a control nested run of an in-memory `New-PesterContainer -ScriptBlock` container, so a value set by Pester itself is not attributed to `TARGET`. The guard's own `BeforeEach`/`AfterEach` snapshot and restore the full environment and `$global:LASTEXITCODE`, so the guard leaks nothing even when it fails.
- DD3 Guard form (c), fallback: `GUARD` parses `TARGET` with `[System.Management.Automation.Language.Parser]::ParseFile` and fails when an assignment to `$env:PATH` (case-insensitive) inside an `It` block has no enclosing `Describe` or `Context` block that directly contains a `BeforeEach` or `BeforeAll` reading `$env:PATH` and an `AfterEach` or `AfterAll` assigning `$env:PATH`. Limited to PATH, per spec option (c).
- DD4 Guard scope: `GUARD` covers `TARGET` only. This is the smallest guard the spec allows; the other test files that assign `$env:` variables are out of scope (spec `## Scope & Non-Goals`).
- DD5 Feasibility decision rule (applied in P1-T5, pre-fix tree, so each probe compares against a Phase 0 run of an otherwise identical tree). Shapes: S0 `GUARD` alone (P1-T2); S1 single-process `Leak` order over `REPRO` including `GUARD` (P1-T3); S2 `Invoke-PoshQCTest` over `tests/scripts/dev-tools` with coverage enabled (P1-T4). Rules: R1 the control testcase passes; R2 the environment testcase fails and its failure message names exactly one differing key, `PATH` compared case-insensitively; R3 for S1, every non-`GUARD` container profile lies field-wise between `PL_min` and `PL_max` with `tests` equal, and the testcase total equals the `LK1` total plus 3; for S2, every non-`GUARD` container profile equals its P0-T9 profile and the testcase total equals the P0-T9 total plus 3; R4 (S2) the coverage report lists the same files with the same per-file line totals as P0-T9, and no file's covered-line count is lower. GuardForm is `b` when every applicable rule holds in every shape; otherwise GuardForm is `c` and the failed rules with their observed differences are recorded.

- Coverage: no production file changes, so PowerShell line coverage (85% line floor, no branch gate) cannot regress through this change; P0-T7 and P4-T4 record overall and `scripts/dev-tools/run-actionlint.ps1` line coverage from the coverage XML and P4-T4 asserts no decrease. No coverage `exclude` entry is added (P4-T6).
- Mirror parity: not applicable because only test files under `tests/scripts/dev-tools/` change, which are not mirrored or bundled; no fact stated by the execution-environment brief changes (no CI job, required context, tool route, or batch-budget rule), so no brief-update task is needed.
- File size: `TARGET` is near the 500-line guidance tier and DD1 adds a net of about ten lines; `GUARD` is a new file of about 150 lines. P0-T2 and P4-T6 record physical line counts and assert each is under 700.
- Test isolation: seeded shuffled file-order Pester runs of `REPRO` with three seeds (`1066`, `20261103`, `7`), each seed and file order recorded (P3-T3 to P3-T5), plus `Forward`, `Reversed`, and `Leak` runs (P3-T1, P3-T2, P3-T6), a fresh single-process run over `tests/scripts` (P4-T4), and an `Invoke-PoshQCParallelTest` run (P4-T5). The leak is reproduced in the explicit `Leak` order (P0-T13, P0-T14) because the CI `Forward` order runs `VICTIMS` before `TARGET`. Comparisons use container profiles, so template-name changes and duplicate keys cannot pass or fail a run; a pre-existing order dependence among `VICTIMS` is detected by the solo runs (P0-T18, P0-T19) and by the CR control order, recorded, and named in the handback. A seeded shuffled Jest run is not applicable because no TypeScript changes; a reversed-order Python run is not applicable because no Python test module changes. The nested-run risk to the outer run is measured by DD5 before the guard form is fixed.
- CI-only behavior: CI runs `GUARD` on `windows-latest` in `poshqc / PowerShell QC shard 1`, `shard 2`, or `shard 3` with coverage, aggregated by `poshqc / PowerShell QC`; `poshqc / PowerShell hook suites (Linux)` does not run `tests/scripts/dev-tools`. Windows environment names are case-insensitive (`Path`), so DD2 compares keys with `OrdinalIgnoreCase` and assumes no path format, separator, or drive letter. P1-T4 reproduces the coverage-enabled `Invoke-PoshQCTest` shape locally; AC11 stays pending-CI.
- Evidence: fail-before runs (P0-T10, P0-T13, P0-T14, P1-T2, and P1-T7 under GuardForm `c`) carry `ExpectedExitCode: 1`; every order run records its file order, seed, and profile differences; JUnit XML stays under `RAW` and evidence records counts, profiles, and keys only, with no absolute path. Pester's built-in JUnit export fails on this host when a failure message holds an 0x1B character (recorded in `evidence/other/scratch-tooling.2026-11-03T23-10.md`), so single-process runs write JUnit through `SCRATCH/issue-1066-junit-writer.ps1`, and parallel shards fall back to the `Tests Passed:` summary line when a shard JUnit does not load.
