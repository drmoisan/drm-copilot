## Standing rules for this plan

**Fail-closed evidence rule.** Every baseline task and every final-QC command task writes exactly one evidence artifact carrying `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`. A missing artifact, or an artifact missing any of those four fields, makes the outcome BLOCKED or INCOMPLETE, never PASS. `EXIT_CODE: SKIPPED` is not a passing outcome for any task in this plan; no task in this plan authorizes a skip branch.

**Evidence-location rule (non-overridable).** Every artifact path in this plan resolves inside `docs/features/active/2026-08-23-plan-acceptance-gates-miss-unobservable-and-ambient-state-gates-519/evidence/` under one of the canonical kind folders `baseline`, `regression-testing`, `qa-gates`, or `other`. No artifact is written under `artifacts/baselines`, `artifacts/qa`, `artifacts/coverage`, or any other non-canonical location.

**Fixed run stamp.** Every evidence filename produced by this plan uses the fixed run stamp `2026-08-24T00-00`, so every artifact path stated below is a concrete checkable path rather than a shape. The artifact's internal `Timestamp:` field records the actual wall-clock time of the command, which may differ from the filename stamp. This separation is deliberate: it makes each acceptance condition name a literal path while keeping the recorded time honest.

**Self-application rule (this plan is subject to the defect it repairs).** Every task in this plan that invokes a write-mode tool states an observation beyond the exit code, drawn from output the tool actually emits on a clean run. Every `git diff` span in this plan carries an explicit `main` ref operand; no bare worktree-against-index form appears anywhere. Every name-listing diff task additionally carries a `git status --porcelain` companion span in the same task, so it can observe a path the plan creates. No task asks the executor to select the evidence it is judged against.

**Observed success-case output, recorded once here so every gate below can rely on it.**
- `black` on a clean run prints a summary line containing the literal `left unchanged` and prints no line containing the literal `reformatted`. When it rewrites a file it prints `reformatted` and still exits 0.
- `ruff check` is configured with `fix = true` in `pyproject.toml`, so it rewrites files and still exits 0. On a clean run it prints the literal `All checks passed!` and prints no line containing the literal `Fixed`.
- `prettier --write`, invoked through `npm run format`, prints one line per processed file; a file it did not rewrite carries the trailing literal `(unchanged)` and a file it rewrote does not.
- The project `addopts` value is `-ra --cov-report=lcov:artifacts/python/lcov.info`, which supplies no terminal reporter. Every coverage command in this plan therefore passes `--cov-report=term-missing` explicitly, or no coverage table is printed at all.
- `pytest --cov-branch --cov-report=term-missing` prints one combined `Cover` column per file plus a `TOTAL` row, not separate line and branch columns. Coverage acceptance below reads the `Cover` value from that table and reads branch data from the same run's `TOTAL` row.
- Every coverage command in this plan places a bare `--cov` as the final argv word, or uses the `--cov=` form with an importable dotted name. Neither shape produces a G1 through G4 finding.

**Frozen design decisions, so no task requires a judgment call.**

*Write-mode register, six entries. Each entry is an argv predicate plus a set of observation markers matched case-sensitively as substrings of the owning task's attributed text.*
1. `black-write` — an argv word equal to `black`, with no word equal to `--check` and no word equal to `--diff`. Markers: `reformatted`, `left unchanged`, `unchanged`.
2. `ruff-fix` — consecutive argv words `ruff` then `check`, with no word equal to `--no-fix`. Markers: `Fixed`, `All checks passed`, `fixes applied`.
3. `prettier-write` — an argv word equal to `prettier` together with a word equal to `--write`, or the consecutive words `npm`, `run`, `format`. Markers: `(unchanged)`, `unchanged`, `rewrote`.
4. `poshqc-format` — an argv word ending with `run_poshqc_format`. Markers: `formatted`, `unchanged`.
5. `poshqc-analyze-autofix` — an argv word ending with `run_poshqc_analyze_autofix`. Markers: `autofix`, `Fixed`, `unchanged`.
6. `poshqc-suite` — an argv word ending with `run_poshqc_suite`. Markers: `formatted`, `unchanged`.

*Executable-position constraint, applying to all six entries.* A word satisfies an entry's shape only when its index lies within the leading four-word scan window and the word immediately preceding it does not begin with a hyphen. A tool name supplied as the operand of a search flag is therefore never read as an invocation, which mirrors the extractor's existing rule that a grep-family name appearing as an operand is not the executable. Without this constraint a task that searches a policy file for a register member's name would report a finding against its own search command.

*Fixture shape for the three PoshQC entries.* The two-word extraction floor is fixed, so a PoshQC tool invoked as a bare single-token name is never extracted and can never be reached by a fixture. Entries 4, 5, and 6 are therefore exercised by a two-word fixture span whose first word is the tool name and whose second word is an operand, for example the tool name followed by `scripts/powershell`. This is the concrete form of the stated limitation that [P7-T3] records in the rule file and that [P2-T9] pins by test.

*Register exclusions, with reasons.* `git add` is excluded because a plan stages in order to make a later diff complete, so its acceptance concerns the diff and not the staging. `npm ci` is excluded because its only write target is git-ignored. Both exclusions are recorded in the rule file by [P7-T2].

*Attributed task text.* The attributed text of a command is the newline-joined text of its whole attribution window: the owning task line plus every following line up to, but not including, the line that closes the window, which is a Markdown heading, the next task line, or the end of the document. Every observation-marker test and every companion-span exoneration below reads that whole-window text, because a plan states its acceptance condition on the lines that follow the task line rather than on the task line itself. A window-scoped value is assigned to each record when its window closes, so the extractor still walks the document exactly once.

*Frozen defective fixture spans, quoted here in the document preamble rather than inside a task.* The fail-before fixture built by [P1-T1] states two acceptance spans: `poetry run black .` and `git diff --exit-code -- scripts/dev_tools/plan_gate_commands.py`. They are quoted in this preamble deliberately. A span in the document preamble belongs to no attribution window and is dropped by the extractor, so quoting a defective form here defines it exactly without stating it as an acceptance condition of any task in this plan. Quoting the same two spans inside [P1-T1] would make this plan carry the very forms the new rules report.

*Finding strings, fixed verbatim so both runtimes and both parity fixture sets agree.* Each begins with the square-bracketed task identifier and renders the offending span between backticks.
- G7: task identifier, then `write-mode command`, then the span in backticks, then `rewrites tracked source and exits 0 after rewriting; the attributed task text carries none of its observation markers. Record an observation beyond the exit code.`
- G8: task identifier, then `git diff span`, then the span in backticks, then `carries no ref operand and no --cached flag; it compares the worktree against the index and passes vacuously once the change is committed. Anchor the diff to a ref.`
- G8b: task identifier, then `name-listing diff`, then the span in backticks, then `never reports an untracked file, and the attributed task text carries neither a staging span nor a porcelain-status span; a path the plan creates is invisible to it. Add a staging or porcelain-status companion.`
- G9: task identifier, then `coverage command`, then the span in backticks, then `supplies no terminal reporter and the project addopts supplies none either, so no coverage table is printed. Add --cov-report=term-missing.`

*Severity constants.* `G7_SEVERITY`, `G8_SEVERITY`, `G8B_SEVERITY`, and `G9_SEVERITY`, one named constant per rule per runtime. All four are authored as the warning channel in Phase 2 and Phase 3 and are re-set in Phase 6 to whatever the pre-declared decision rule yields from the recorded corpus counts. Rule-behaviour tests assert findings against the union of both channels and assert the channel separately against the module's own severity constant, so a Phase 6 severity change breaks no test.

*Design corrections adopted during Phase 2, recorded here because the frozen design above was inaccurate in three places. The Python implementation carries all three and is committed; Phase 3 mirrors all three into the TypeScript port, and the parity fixtures of [P4-T3] compare the two runtimes after they are mirrored.*

1. **G7 removes the offending span from the attributed task text once before searching for the observation markers.** Register entry 5 has the marker `autofix`, and its tool word is `run_poshqc_analyze_autofix`, so the marker occurs as a substring of the span itself. Because the span is part of the attributed task text, the entry exonerated itself unconditionally and could never fire, which made the register-completeness case of [P2-T6] unsatisfiable. Removing the span once, then searching the remaining text, is the same discipline the existing plan-quotation check already applies, so no new mechanism is introduced.
2. **The project coverage-configuration reader returns no value when the configuration file could not be read.** The G9 finding text asserts that the project value supplies no terminal reporter, and that claim is supportable only when the file was actually read; a read failure yields an absent value rather than an empty one, and G9 reports nothing. This is also what makes the non-zero-exit fault injection required by [P2-T9] produce zero findings.
3. **The TypeScript line splitter drops a trailing empty element**, matching the line-splitting behaviour of the Python runtime, so both runtimes derive the same attributed task text for a document that ends with a newline. No record was ever produced from the dropped element, so no existing finding string and no existing finding count changed.
