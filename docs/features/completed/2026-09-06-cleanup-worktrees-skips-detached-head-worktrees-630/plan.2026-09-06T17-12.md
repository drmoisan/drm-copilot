## What Each Toolchain Command Actually Prints (Observation Contract)

Verified in research §11.5 against `scripts/bash/shell_qc_lib.sh`. Acceptance conditions in this plan are authored against these observations, not against exit codes alone.

- **`format`** runs `shfmt -w` (`shell_qc_lib.sh:222`) and prints **nothing** on a clean run. Its exit code is 0 whether or not it rewrote files, so the exit code alone is not an observation. The assertable substitute is `git status --porcelain -- tools scripts .claude/lib/bash` captured immediately before and immediately after the `format` run: the two listings are byte-identical when shfmt rewrote nothing and differ when it rewrote something. An emptiness test is not used; byte-identity is the assertion and it holds equally for two empty listings, so nothing depends on the listing being non-empty. The pair is a per-path status comparison rather than a content comparison, so it does not observe a rewrite of a file that is untracked or already modified; P7-T1 adds a read-only `check` run before `format` to close that gap.
- **`check`** runs `shfmt -d` once over the discovered list (`shell_qc_lib.sh:188`) then `shellcheck` once per file (`:194-200`), and prints **nothing** on a clean run. Empty stdout and stderr with exit 0 **is** the falsifiable positive evidence, because `shfmt -d` prints a unified diff whenever any discovered file is unformatted.
- **`test`** prints a TAP plan line `1..N` and one `ok N <name>` line per case. Record `N` and confirm no line begins with `not ok`.
- **`test --coverage`** additionally prints the coverage headline emitted at `scripts/bash/shell_qc_lib.sh:291`. The exact literal is `Bash coverage (lines): NN.N%` with one decimal place. The threshold is **line coverage >= 85%** per `.claude/rules/quality-tiers.md`. There is **no bash branch-coverage gate**: kcov does not measure branch coverage (`.claude/rules/shell.md:68-70`). The most recent value recorded in this repository is 92.3%; Phase 0 must capture the **actual current number**, not assert that one.
- **`discover_shell_scripts`** (`shell_qc_lib.sh:75-102`) searches only `tools/`, `scripts/`, and `.claude/lib/bash/` and qualifies by `.sh` suffix or bash/sh shebang, so `tests/shell/*.bats` files are **not** seen by `format` or `check`. No task in this plan expects shfmt to format the new bats suite.
- There is **no type-check stage for bash** (`.claude/rules/shell.md:25-27`). The loop is format, then check, then test.

`bash scripts/bash/shell-qc.sh --coverage` is a bats/kcov mode flag, not a `coverage.py` argument; the numeric headline is printed unconditionally on a successful coverage run, so no terminal-reporter flag applies here.

## Baseline-Ordering Decision (Read Before Phase 0)

Phase 0 deliberately **does not run `format`**. `format` is write-mode: running it first would silently repair any pre-existing formatting drift, so the recorded baseline would describe a tree the executor created rather than the tree it inherited. The read-only `check` command is the baseline instrument instead: its `shfmt -d` stage reports exactly the drift `format` would repair, and its output is falsifiable. `format` runs for the first time in Phase 7.

## Three Named Traps

**Trap 1 — the `deletion/consolidated_merged` fixture trap.** Re-derived against the current tree in this pass: `tests/fixtures/cleanup_worktrees/deletion/consolidated_merged/` contains exactly seven files (`for-each-ref.out`, `merge-base.documentationandmemories.rc`, `rev-parse.abbrev-ref-HEAD.out`, `rev-parse.show-toplevel.out`, `rev-parse.verify.refs_heads_documentationandmemories.out`, `rev-parse.verify.refs_heads_documentationandmemories.rc`, `worktree-list.out`) and has **no** `rev-parse.main` or `rev-parse.documentationandmemories` key. Under the stub both sides of the new tip comparison would resolve to the empty string and compare EQUAL, which would wrongly trigger the guard and break the currently-green test at `tests/shell/test_cleanup_worktrees_deletion.bats:74-83`. Both halves of the mitigation are required and are separate tasks: (a) treat an empty or unresolvable `rev-parse` as a hard failure rather than as equality (P5-T1), and (b) add the two fixture files with distinct values so the scenario models reality (P1-T9). **Ordering matters: P1-T9 must land before P5-T1's verification runs, or that verification cannot pass.** `deletion/consolidated_unmerged/` has the same absence and receives the same fixture addition (P1-T10) so that the `merge-base` non-ancestor rung of `verify_consolidation_merged` stays exercised after the pre-check is added.

**Trap 2 — `classify_branch` must not be reused wholesale.** Re-derived: its worktree lookup at `scripts/bash/cleanup_worktrees_lib.sh:353-360` matches `wbranch == "$name"`, and a detached record's branch field is the literal `DETACHED`, so `wt_norm` stays empty, the `prot_path` half of the test at `:361` is skipped, and the caller's own detached worktree would escape `PROTECTED_CURRENT`. Protection for a detached candidate is therefore **by normalized path** against `compute_protected`'s `protected-path|` records (`scripts/bash/cleanup_worktrees_enumerate_lib.sh:212`, `:214`). Re-derived in this pass: `:212` and `:214` are the two `printf 'protected-path|%s\n' "$norm"` statements; `:209` is `path=${record%%|*}` and emits nothing. The four ladder rungs themselves accept a bare committish and are reusable.

**Trap 3 — the stub keys `worktree remove` on the subcommand alone.** Re-derived at `tests/fixtures/cleanup_worktrees/stub-bin/git:104` (`remove) respond "worktree-remove" ;;`), so `worktree-remove.rc` is one value per scenario. ## Ordering Constraints (Satisfiability Check)

1. **Fixtures before the guard.** P1-T9 and P1-T10 add the `rev-parse` fixture files. P5-T1 adds the guard and P5-T2 verifies the pre-existing consolidation regression. If P5 ran before P1, P5-T2 could not pass, because the empty-versus-empty comparison would fail closed on `consolidated_merged` and the merge-base rung would never be reached on `consolidated_unmerged`.
2. **Library before helper source chains.** P3 creates `scripts/bash/cleanup_worktrees_detached_lib.sh`. P4-T5 through P4-T7 add it to three existing bats helpers. Reversing the order would break four currently-green suites.
3. **Baseline before any modification.** All of Phase 0 runs against the unmodified tree, and Phase 0 deliberately omits the write-mode `format` command so the baseline describes the inherited tree.
4. **No exit-0 test gate inside the red window.** The suite is red from P2-T2 until P5-T1 completes. No task between those points asserts that `shell-qc.sh test` exits 0. P1-T11 runs before the red window opens; P4-T9, P4-T10, and P5-T2 assert only on individual suites that are green at the point they run.
5. **Coverage gate last.** P7-T3 and P7-T5 run after every fixture, test, and source change, so the kcov denominator includes the new library and every function in it is exercised.
6. **Driver-mode cases after the wiring, not before.** `run_report` reaches `report_detached_worktrees` only after P4-T2, and `run_apply` reaches `apply_detached_worktrees` only after P4-T4. Every Phase 3 acceptance condition is therefore a direct invocation of the function the task adds, using the harness at the head of Phase 3; the three report-mode driver cases are asserted in P4-T2 and the seven apply-mode driver cases in P4-T4. The direct-invocation cases already present in the new suite — `is_detached_candidate flag matrix`, the two `classify_detached_head` cases, and `reverify_detached_delete_eligible blocks on a flipped verdict` — do reach their function without the wiring, so they stay as the acceptance of P3-T2, P3-T3, and P3-T5.
7. **AC20 evidence before the mirror.** P6-T4 checks the three tokens in the repository skill file after P6-T1 through P6-T3 have added them and before P6-T5 copies the file, so the AC20 evidence describes the source of the mirror rather than the mirror itself.
