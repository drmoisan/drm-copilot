## Design Summary

- **Layer.** `PushDownLayer` (`PD/push-down-layer.ts`): layer name (`shared`, `claude`, `codex`, `copilot`), source root, root folders, root-file pairs `[destination path, resources-relative source]`, composed file system (enumeration filters, variant reads, destination-write decorators over `WriteIfChangedFileSystem`), rewrite function, merged paths, merged deliveries (path plus pure merge function, no source file), owning-pack lookup, selection record, artifact directory.
- **Pipeline.** `runPushDownPipeline` (`PD/push-down-pipeline.ts`) validates the destination, reads `.push-down-exclusions` and `.push-down-manifest.json`, wraps each layer with `ExclusionFilterFileSystem`, enumerates layers in order (an earlier layer's claim wins), classifies every path (`merge`, `excluded`, comparator otherwise, `orphaned` per D3) and builds `PushDownReport`, all before any write. A dry run returns there. `applyPushDownPlan` (`PD/push-down-apply.ts`) writes `create`, `update` and opted-in `unmanaged-conflict` files, runs merged paths and deliveries through the write-if-changed base, writes the manifest only when its text changed, and writes the summary artifact with a per-file `action`.
- **Entry points.** `pushDownHarness` (`PD/push-down-harness.ts`) builds the shared layer then the selected ecosystem layers through `PD/push-down-ecosystem-registry.ts`; the three service calls in `PD/push-down-service-call.ts` call it with exactly one ecosystem. Each ecosystem module's `pushDownCustomizations` stays as a single-layer adapter over `runPushDownPipeline` (no shared layer), so module-level tests need no shared manifest (D13).
- **Pinned declarations.** `ROOT_FOLDERS`, `MERGED_RELATIVE_PATHS`, `ROUTING_MERGE_RELATIVE_PATH`, `DESTINATION_WRITE_DECORATORS`, `EXCLUDED_RELATIVE_PATHS` (`PD/claude-customizations.ts`), `ROOT_FOLDERS`, `VIRTUAL_RESOURCE_PAIRS`, `VIRTUAL_RESOURCE_DIRECTORIES` (including the `.codex/lib/epic-wave` pair, R-5) and `VIRTUAL_ROOT_FOLDERS` (`PD/codex-agents-customizations.ts`), and the declarations the static parity tests read keep their names and values (O-6). No new `export const` in `PD/claude-customizations.ts` matches the parity test's merged-name pattern `^[A-Z_]*MERGE[A-Z_]*_RELATIVE_PATHS?$`.

## Planning Decisions (within the spec; not owner stops)

- D1. The shared manifest is `RES/codex-and-agents-customizations/pack-manifests/shared.json` (`name` `shared`); shared files record `pack` `core`. Codex `core.json` entries for shared skills stay (no partition), so the Codex generator `--check` is unaffected.
- D2. Shared configuration is the `config/` destinations of `VIRTUAL_RESOURCE_PAIRS`; `config/orchestration-routing.json` is merged through `RoutingMergeFileSystem` (absent destination: source written unchanged), which gives the Codex path the merge.
- D3. `orphaned` covers manifest entries whose `layer` is in the run and that have no payload counterpart. Under the O-2 default each wrapper selects only its own ecosystem, so no run can deselect another ecosystem. Spec Behavior 11 and the user-story criterion "files of a deselected pack or ecosystem are reported as orphaned" are therefore met for deselected packs and retired files. Entries of an ecosystem not selected in a run are neither reported nor changed.
- D14. A root-file pair whose source file is absent from the bundle is skipped (no plan entry, no read error), so module-level fixtures without a root-file source keep their file lists (X1, X4).
- D4. Summary `files` lists payload-backed entries only (merged paths that have a source file included), in enumeration order (root order, then path); merged deliveries without a source file (`.gitignore`) appear in the report, not in `files`. `destination_status` stays presence-based (`created` when absent before the run, `overwritten` when present) and `created_count`/`overwritten_count` count those classes; `PushDownFileResult.action` is optional, so typed fixtures compile unchanged.
- D5. With `packs` omitted and no recorded selection, the full tree is published and the recorded `packs` lists every accepted pack plus `core`, with C# in the input's form for the effective variant.
- D6. `payload_version` is read from `EXT/package.json` through the injected file system; absent or unparseable gives `0.0.0`.
- D7. Extension commands gain the Copilot pack QuickPick and a push-down-conflict warning; no extension dry-run step.
- D8. Pack assignment for an unlisted path: take the agent stem, skill folder, rule or instruction stem, or prompt stem; equal to or prefixed (`<name>-`) by `python`, `powershell` or `typescript` goes to that pack; `csharp`-prefixed goes to `csharp-modern.json` and `csharp-legacy.json` (Claude, Codex) or `csharp.json` (Copilot); otherwise `core.json`. Shared-set paths go to `shared.json` only. Existing entries are not moved, and new entries are appended at the end of the `paths` array, so the stored `0010` ledger hunks in both `core.json` files keep their context (`ProcessReductionChain.Ledger.Tests.ps1`).
- D9. `EXT/jest.config.cjs` is 596 lines (above the 500 guidance tier); new entries go in `EXT/jest.push-down-coverage.json`, required and spread into `coverageThreshold` as the docs map is (one `require` line and one spread line added). `EXT/test/discovery-coverage-contracts.test.ts` pins the discovery map and its merge into `coverageThreshold`; it is unchanged, because the new map's keys are distinct from the discovery keys. No test pins the docs map.
- D10. `PD/claude-customizations.ts` is 496 lines. The Claude composition moves into the new `PD/claude-layer.ts` (`composeClaudeLayer`), which takes the pinned declarations as parameters and imports nothing from `PD/claude-customizations.ts`; `buildClaudeLayer` in `PD/claude-customizations.ts` passes them in. The private `deliverDestinationGitignore` and the exclusion wiring are removed from that file, so it shrinks.
- D11. Codex manifests are re-rendered by `scripts/dev_tools/generate_codex_agent_variants.py` (`render_manifest`: load, append missing agent paths, two-space JSON plus LF). Hand edits to the Codex manifests are followed by one generator write run, then `--check`. No `config/orchestration-regeneration.json` exists in this repository, so the #1156 regeneration path governs no file of this plan.
- D12. The execution-environment brief states no fact this plan changes (no CI job, required context, tool route, batch-budget rule or contract-test file changes); it is not edited, so no process-reduction ledger region is touched.
- D13. `RoutingConfigFileSystem` and `CodexFilteringFileSystem` in `PD/codex-agents-customizations.ts` are module-private today; P2-T2 adds `export` to `RoutingConfigFileSystem` only.
- D15. The shared set `S` (spec Behavior 2), the one definition P0-T1, P2-T1, P2-T2 and P4-T1 use: the destination paths `AGENTS.md`, `config/orchestration-routing.json`, `config/orchestration-handoff-registry.json` and `config/orchestration-handoff.schema.json`, plus every file under `.agents/skills/<name>/` in the Codex bundle for each `<name>` whose `config/harness-parity-matrix.json` entry has `kind` `skill`, `ecosystem` `codex` and `disposition` `shared`, sorted in code-point order. `shared.json` `paths` equal `S` exactly.

## Pre-Mortem

- Review checklists: a reviewer could find a changed default, an edited test without a reason, or a spec rule with no failing test. Prevention: `## Existing Test Dispositions` (X1 to X12, rules R1 to R4), `## Spec Rule Traceability`, the compatibility test (P3-T5), and the three-template self-review (P5-T7).
- Coverage: a new module without an entry is ungated because the map has no `global` key, and mocked units would overstate coverage. Prevention: every module task adds its entry to `EXT/jest.push-down-coverage.json` (D9); core modules are tested with in-memory fakes and no module mocks; baselines (P0-T5 to P0-T7) and the delta (P5-T5) compare per file. Python and PowerShell production code is unchanged.
- Mirror parity: new and edited manifests could break resource-contract, completeness, closure or generator checks. Prevention: Codex manifests go through the generator write run (D11, P4-T3); shared paths do not move Codex `core.json` entries (D1); the Python contract tests and Manifest suites run in every gate. The execution-environment brief states no fact this plan changes, so no brief task is needed (D12).
- File size: `PD/claude-customizations.ts` (496), `EXT/jest.config.cjs` (596), `mcp-tool-inputs.ts` (483), `mcp-tools.ts` (473) and `repo-automation-service.ts` (476) sit near tiers. Prevention: D9 and D10 move growth into new files; P2-T3, P2-T5 and P3-T3 require shrinkage; P3-T2 and P3-T4 cap at 500; P5-T6 measures; `FileSizePolicy.RepoGate.Tests.ps1` runs in every Pester gate.
- Test isolation: shared fakes or module state could couple tests. Prevention: a fresh in-memory fake per test, no module-level mutable state in pipeline modules, and only the parallel gates: one `Invoke-PoshQCParallelTest`, one `pytest -n auto`, and Jest through its normal parallel workers, each re-run only after a fix; test-order dependence is a defect fixed on both sides.
- CI-only behavior: drive-letter roots fail on Linux, CRLF fixtures become LF under `eol=lf`, real-tree tests can read gitignored state. Prevention: POSIX in-memory roots (`/dest`, `/ext`), CRLF built in code (P2-T6), real-tree tests read only tracked resources, Jest runs on both CI operating systems, and no CI job or required context changes.
- Evidence: hand-composed stamps, absolute paths or counts from PoshQC MCP summaries would fail review. Prevention: write-time UTC stamps, append-only files, the `SCRATCH` token, Pester counts from `artifacts/pester/pester-junit.xml`, and Phase 0 gate records written before any edit.

## Size Justification

The plan has 40 canonical tasks, within the legacy guideline that its pre-cutoff stamp selects but above the current 20-task target. It needs that size because it carries three execution gates, three parallel test baselines, thirteen new production modules each paired with its test file, edits across five push-down modules, seven MCP or service files and the admin command file, two manifest sets, a full-bundle completeness test, a real-bundle suite, four phase gates and a final QA loop for TypeScript, Python and Pester. Splitting it would separate the pipeline from the wrappers that must delegate to it, which the spec requires to land together, and the downstream plans of #1049, #1050 and #1051 depend on this item as one unit.
