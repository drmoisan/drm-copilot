## Design Decision (naming)

- New CLI flag: `--require-pr-creation-ready` (added to the existing `orchestrator-state` subcommand in `scripts/dev_tools/validate_orchestration_artifacts.py`, alongside `--require-complete`, which is unmodified).
- New pure function: `validate_orchestrator_state_pr_creation_readiness(state: dict[str, Any]) -> list[str]` in `scripts/dev_tools/validate_orchestrator_state.py` (or, if the 500-line cap requires it, extracted into a new sibling module `scripts/dev_tools/_orchestrator_state_pr_creation_readiness.py` following the existing `_orchestrator_state_human_interaction.py` pattern).
- New keyword parameter on the existing entrypoint: `validate_orchestrator_state_text(text, *, require_complete=False, strict_route_membership=False, require_pr_creation_ready=False)`. The new parameter is independent of `require_complete`; it does not call `validate_completion_pr_gate`, `_validate_completion_ci_gate`, `validate_phase_completeness`, or `validate_routing_contract`.
- Message prefix for the new checks: `"Checkpoint PR-creation readiness validation failed: "` (distinct from `--require-complete`'s `"Checkpoint completion validation failed: "` prefix, so failures from the two modes remain independently greppable).
- New constants: `PR_CREATION_READY_STEP_KEYS = ("step5_status", "step6_status", "step7_status", "step8_status")` and `PR_CREATION_READY_EMPTY_LIST_KEYS = ("local_execution_overrides", "delegation_bypasses")`.

## Do Not Do (carried forward from remediation/2026-07-02T22-05/remediation-inputs.md)

- Do not weaken, remove, or bypass `--require-complete`'s existing full-lifecycle semantics (`ci_gate`, `pr_gate`, full routing-contract receipts). It remains available and unchanged for contexts where it is structurally satisfiable (post-PR-creation, post-CI).
- Do not hard-code the hook to always allow `gh pr create`/`gh pr edit` — the new check must still meaningfully reject a missing/malformed checkpoint or a checkpoint with pending/blocked upstream steps (`step5_status`-`step8_status`).
- Do not stub/mock the real checkpoint in production code paths (only test code may mock `$Invoker`/`_read_text`).
- Do not remove the `pr_author_preflight` checkpoint-recording concept; adjust what it validates, not whether it exists.
- Do not touch `ci_gate`/`pr_gate` semantics used elsewhere in `orchestrator.md` (Step S9, PR Creation Gate condition 6).
- Do not delete or rename the real, live `artifacts/orchestration/orchestrator-state.json` checkpoint at any point in this remediation cycle. Any field additions made to unblock the Phase 6 verification (P6-T2) must be limited to already-mandatory, orchestrator-owned metadata fields (`relativeFile`, `long-name`) sourced from data already present in the checkpoint — never `ci_gate`, `pr_gate`, or delegation-receipt fields.
- Do not touch `.claude/hooks/validate-orchestrator-output.ps1` (out of scope for #272).
- Do not extend `tests/scripts/dev_tools/test_validate_orchestrator_state.py` or `tests/scripts/dev_tools/test_validate_orchestration_artifacts.py` — both already exceed the repository's 500-line cap (pre-existing condition). New pytest coverage goes into new sibling split files, per the repository's own established split pattern (`test_validate_orchestrator_state_human_interaction.py`, `test_validate_orchestrator_state_remediation_loop.py`, `test_validate_orchestrator_state_routing_contract.py`).
