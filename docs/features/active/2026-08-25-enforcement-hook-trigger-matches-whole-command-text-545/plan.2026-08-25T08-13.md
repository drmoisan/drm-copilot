## Toolchain and measurement contracts (normative for every task below)

**Coverage must be measured with the self-hosted runner.** The MCP PoshQC test runner resolves its settings from the installed VS Code extension's copy, so a `CodeCoverage.Path` entry added in this checkout is invisible to it and the file is silently absent from the report rather than reported at zero. Every coverage figure in this plan is therefore produced by the direct route, whose `-SettingsPath` parameter makes the in-repo settings authoritative:

`pwsh -NoProfile -Command "Import-Module './scripts/powershell/PoshQC/PoshQC.psd1' -Force; Invoke-PoshQCTest -Root (Get-Location).ProviderPath -SettingsPath 'scripts/powershell/PoshQC/settings/pester.runsettings.psd1'"`

Do not substitute the MCP test runner for any coverage figure. `config/poshqc-scan.json` supplies test scan folders only and needs no edit for coverage registration; coverage entries live in the two `pester.runsettings.psd1` copies, which `tests/scripts/dev_tools/test_poshqc_bundled_parity.py` pins text-identical through its `POSHQC_PARITY_PATHS` tuple.

**Reading a coverage figure.** `CodeCoverage.OutputFormat` is `CoverageGutters`, which emits a JaCoCo-shaped document at `artifacts/pester/powershell-coverage.xml`. There is no `coverage` element and no `line-rate` attribute. Overall line coverage is `covered / (covered + missed)` on the report-level `counter` element whose `type` is `LINE` — the direct child of the root `report` element. A per-file percentage requires a **package-qualified** selection: the `counter` whose `type` is `LINE`, on the `sourcefile` whose `name` equals the bare filename, selected within the enclosing `package` whose `name` ends with that file's directory. A bare-filename lookup is ambiguous because several filenames occur under both `.claude/hooks` and `.codex/hooks`.

**Two measurements that must be re-taken, not carried forward.** The prior documents cited an aggregate of approximately `61.6%` and a `CodeCoverage.Path` length of `83` entries, while the prior baseline artifact recorded `96.1433%`. All three figures are unusable and none is cited as fact anywhere in this plan. [P0-T7] re-measures the aggregate and [P0-T8] re-measures the list length.

**Files that produce no coverage row.** `CodeCoverage.Path` holds zero entries under `extensions/drm-copilot/resources/`. Every bundle mirror is therefore outside the coverage denominator and can never produce a `sourcefile` element. A task recording coverage for a bundle mirror records the literal entry `outside the coverage denominator - bundle mirror, parity enforced by content or hash` and never a fabricated percentage.

**Targeted Pester runs.** A targeted run is `pwsh -NoProfile -Command "Invoke-Pester -Path tests/scripts/claude-hooks/validate-bash.Tests.ps1 -Output Detailed"` with the path substituted for the suite named in the task. [P0-T10] records the verbatim shape of the run-summary line before any later task asserts over it, so no assertion in this plan is written against output that has not been observed on a successful run.

**Diff anchoring.** Every `git diff` in this plan carries the explicit ref operand `origin/epic/cleanup-merged-worktrees-hardening-integration`. [P0-T3] resolves that ref and records its SHA; if it does not resolve, the executor runs `git fetch origin epic/cleanup-merged-worktrees-hardening-integration` and records the fetch before continuing. Any task asserting over a name-listing diff pairs it with a `git status --porcelain` span in the same task, because a name-listing diff enumerates tracked changes only and cannot report a file the task creates.

## Known-red inventory and the batch toolchain gate

Regression tests are written before the fixes that make them pass, so a repository-wide green assertion is unsatisfiable in the middle of this plan. [P1-T13] records a **known-red inventory** artifact naming every test that is expected to fail and the phase that closes it. Batch gates assert against that inventory rather than against an absolute zero.

**Batch toolchain gate (BTG).** Three stages in order, restarting from stage 1 whenever any stage fails or rewrites a file:

1. `mcp__drm-copilot__run_poshqc_format` over the repository. The formatter rewrites tracked source in place and exits 0 whether or not it changed anything, so the exit code alone is not evidence: capture `git status --porcelain` before and after, record both captures verbatim, and record the count of paths present in the after-set and absent from the before-set. That count may be zero.
2. `mcp__drm-copilot__run_poshqc_analyze` over the repository. Acceptance: zero error-severity diagnostics on the files the batch touched, and a repository-wide total at or below the [P0-T6] baseline total.
3. A targeted Pester run over each test file the batch owns. Acceptance: the run reports a numeric failed count, and every failing test name is a member of the [P1-T13] known-red inventory minus the entries the batch closes.

Each BTG task writes `evidence/qa-gates/batch-BATCHID-toolchain.TIMESTAMP.md` carrying `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:` for each of the three stages, plus both porcelain captures and the set-difference count for stage 1.

**Batch reset is mandatory and is not implicit.** `.claude/hooks/enforce-powershell-batch-budget.ps1` holds a cumulative per-session count in `.claude/state/powershell-batch-budget.<session_id>.json` and caps it at three production and three test PowerShell files. Its own documentation states that a session must delete that state file to start a new batch. Beginning a batch below therefore requires the executor to first run `Remove-Item -LiteralPath (Join-Path '.claude/state' ("powershell-batch-budget." + $sessionId + ".json")) -ErrorAction SilentlyContinue`, resolving `$sessionId` exactly as `Get-PowerShellBatchBudgetSessionId` resolves it. That function returns the first non-empty of `$env:CLAUDE_SESSION_ID` and the contents of `.claude/state/current-session-id`, in each case trimmed and then sanitized by replacing every character outside `[A-Za-z0-9._-]` with `_`; when both are empty it returns `worktree-<leaf>-<shorthash>`, where `<leaf>` is the sanitized leaf name of the repository root path after backslashes are normalized to `/` and any trailing `/` is removed, and `<shorthash>` is the lowercase hexadecimal of the first four bytes of the SHA-256 of that same normalized root path. Recording only the leaf name composes a state-file name that does not exist, so `Remove-Item` exits 0 having deleted nothing and the reset reads as successful while the counter is untouched. The executor records the resolved id verbatim in each reset artifact and, from the second reset onward, cross-checks it against the file names actually present in `.claude/state/`. Without a working reset the fourth distinct test PowerShell file of the run is denied at [P1-T8] and the fourth distinct production file is denied inside batch B2. Each batch toolchain gate task performs its reset as the closing action of its own batch, so that reset opens the NEXT batch and is recorded in the artifact of the batch whose gate task performs it. Three batches are opened by a reset written into their own first task instead, because no preceding gate task exists: B0a at [P1-T1], B0b at [P1-T8], and B1 at [P2-T1].

Phases 11 and 12 touch Markdown, evidence, and test files only and consume no production-file batch budget. They do consume test-file budget: [P12-T9] edits test suites and carries its own resets.
