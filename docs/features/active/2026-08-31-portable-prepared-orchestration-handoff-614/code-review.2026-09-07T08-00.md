## Executive Summary

This branch adds a provider-neutral contract that lets a prepared orchestration checkpoint move between Claude and Codex runtimes without either side reading the other's private state. The delivery is unusually well factored for its size: 324 files and 32609 insertions, of which the production surface is only 21 TypeScript modules, 5 Python modules, and 1 PowerShell hook, with the remainder split between tests, committed fixtures, and documentation and bundling surfaces that must move in lockstep. The design choice that carries the most weight is expressing the contract as data — a Draft 2020-12 schema plus a semantic registry — and keeping the validators thin over it, which makes cross-language agreement checkable by equality rather than by inspection. The 16-code `HANDOFF_*` precedence list is the clearest example: it lives once in `config/orchestration-handoff-registry.json`, and both the Python tuple and the TypeScript constant are pinned to it by load-bearing exact-equality tests in their own suites.

Evidence reviewed: the full branch diff against the merge base, the refreshed PR-context summary and appendix generated at this head, all three canonical coverage artifacts parsed directly, the Pester JUnit report, 106 evidence records across six cycles, and reproduced runs of every toolchain stage. Implementation quality is high. Coverage is 99.19% line on the 14 new TypeScript modules and 97.71% on the 3 new Python modules; the seven-stage toolchain passes in one clean pass in all three languages; and publishing parity is byte-identical across all five root-to-bundle pairs by `git hash-object`. Three Major findings remain, all carried forward and previously deferred by orchestrator decision, and none of them is a correctness defect.

**What changed:**

The Python layer adds `orchestration_handoff_contract.py` (envelope construction and validation, including the `no_replay = value.next_transition not in value.completed_phases` guard at line 251), `orchestration_handoff_adapters.py` (bidirectional Claude/Codex projection), and `orchestration_handoff_contract_support.py` (path normalization, raw-byte hashing, legacy-v1 read, bounded scheduler-return validation, semantic identity parsing). The TypeScript layer adds a parallel contract plus a runtime authority (`orchestration-handoff-authority-service.ts`), a path boundary, a checkout-context observer that shells out to read-only `git` queries through an injected runner, and a materializer split across four modules so no file exceeds 500 lines. The MCP surface exposes four semantic operations, of which exactly one is marked mutating. The PowerShell hook `.codex/hooks/enforce-epic-planning-only.ps1` gains `Get-EpicPlanningRegisteredMcpTool`, which reads the registry at load and builds the preparation allowlist, admitting `drm-copilot.transition_prepared_orchestration` as the sole mutating preparation-gate operation. `.gitattributes` gains two `-text -eol` entries protecting the byte identity of the TaskMaster plan fixtures.

Since the previous review at head `0decbdbb`, the branch was rebased onto `0542c92a`, pull request #638 was opened, and one test-only commit `645c40b0` remediated the two CI failures observed in run 34090900558. That commit is genuinely test-only: it touches six test and test-support files, adds one 3-line fixture, and modifies no production source.

**Top 3 risks:**

1. The four fail-closed `throw` paths in the PowerShell registry loader are untested, so the hook-side half of the AC7 rejection contract is asserted by construction rather than by test. If the registry shape drifts, the hook would begin failing every preparation gate at load time and no test would have caught the regression first.
2. The 14 new TypeScript modules carry no per-file `coverageThreshold` entry, so their present 99.19% coverage is unguarded. A later change could erode any of them to near zero without failing the Jest run, because `jest.config.cjs` deliberately has no `global` key.
3. Fifteen `catch` blocks discard the caught value when mapping to a structured code. Most map to `HANDOFF_VALIDATOR_UNAVAILABLE`, so an absent file, a permission denial, and a corrupt read are indistinguishable to whoever has to diagnose a stuck handoff.

**PR readiness recommendation:** **Conditional Go** — the implementation is correct, fully gated, and independently reproduced clean at this head; the three open Major findings are diagnosability and gate-durability gaps suitable for a follow-up issue, and the only remaining condition is that pull request #638's own required checks conclude green.

## Implementation Audit

### Python implementation audit

#### What changed well

- **The registry is the single source of ordering, enforced by test rather than by convention.** `FAILURE_PRECEDENCE: Final = tuple(...)` at `orchestration_handoff_contract.py:67` is pinned to `config/orchestration-handoff-registry.json` by `test_failure_precedence_matches_the_shared_registry`, which asserts full tuple equality. This is the right shape: the runtime does not pay a JSON load on every call, and the two cannot silently diverge. The TypeScript side carries the mirror assertion, so a three-way divergence is impossible without a red test.
- **Primary-failure selection is a two-line function with an explicit unknown-code guard.** Lines 347-350 compute `unknown = found.difference(FAILURE_PRECEDENCE)` before `next((code for code in FAILURE_PRECEDENCE if code in found), None)`, so an unrecognized code is detected rather than silently sorted last. That guard is what makes the precedence list safe to extend.
- **The replay prohibition is expressed as a single readable invariant.** `no_replay = value.next_transition not in value.completed_phases` at line 251 reads exactly as AC5 is worded, and the named local makes the subsequent `_require(no_replay, "lifecycle.next_transition")` self-explanatory.
- **Path normalization takes the field name as a keyword argument.** `normalize_repository_relative_path(value, *, field: str)` means every rejection message names the offending field rather than just the offending value, which is the difference between a usable and an unusable validation error at a 13-field contract boundary.

#### Typing and API notes

Pyright reports 0 errors, 0 warnings, 0 informations across the repository. Module-level constants are annotated `Final`. Value objects are dataclasses with sensible defaults, for example `replay_policy: str = "forbid_completed_phases"` at line 154, which encodes the safe default in the type rather than at every construction site. `Any` appears only inside explicit `cast(...)` calls in test modules narrowing JSON fixtures to known shapes, which is the sanctioned narrowing idiom rather than an escape hatch. The public surface is marked by the explicit `from ... import x as x` re-export form, which Pyright treats as an intentional export; the one problem with that surface is `raw_file_sha256`, covered as a Minor finding.

#### Error handling and logging

Validation failures are returned as structured codes rather than raised, which is the correct choice for a contract validator whose caller needs to distinguish sixteen failure modes. Where the modules do raise, they raise with specific messages. No bare `except:` and no broad `except Exception:` without re-raise appears in the changed Python. The modules perform no console output, leaving reporting to the caller, which keeps them usable from both the CLI and the MCP paths. Invariants are enforced during construction through `_require(...)` in `_build_portable_envelope`, so an invalid envelope cannot be represented at all.

### TypeScript implementation audit

#### What changed well

- **The materializer is decomposed by responsibility, not by line count.** The split across `-materializer.ts` (state machine), `-materializer-request.ts` (request shaping), `-materializer-support.ts` (shared helpers), and `-materializer-production.ts` (real-dependency wiring) keeps each module under 500 lines while leaving a coherent boundary at every seam. The production wiring being its own module is what lets every other module be tested with in-memory fakes and no filesystem.
- **The dependency record is a genuine seam, not a formality.** `HandoffMaterializerDependencies` carries `fileSystem`, `pathBoundary`, `validator`, `gitStatus`, and `clock`. `resolvePortableHandoffAuthority` takes `pathBoundary` as an optional parameter and falls back to `createDefaultPathBoundary(fileSystem)` at line 271. This is what allowed the CI-614-002 remediation to be test-only: the platform-sensitive `path.isAbsolute` call at line 59 lives inside the default boundary and is never constructed when a boundary is injected.
- **Git observation is read-only and constructed as argv.** `readGitFact` in `-checkout-context.ts` builds `["git", "-C", workspaceRoot, ...args]` and passes `{ allowError: true }`, so no shell string is assembled and a non-zero exit returns `null` rather than throwing. The `CheckoutObservation` type makes `unavailable` an explicit variant, and the module comment states why: "so that a caller cannot mistake an unobservable checkout for a matching one". That is the correct instinct at a security-relevant boundary.
- **Dirty-worktree detection is deliberately last in precedence.** `HANDOFF_DIRTY_WORKTREE` sits at index 15 of 16, so unrelated working-tree noise can never mask a contract, identity, or authority failure. The user story asks for exactly this ordering and the implementation delivers it structurally rather than by convention.

#### Type safety and maintainability

`tsc -p ./ --noEmit` exits 0 under `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitOverride`, `noUnusedLocals`, and `noUnusedParameters`. A directed scan of all 21 changed production modules for `: any`, `<any>`, and `as any` returned zero matches; unknown JSON input is typed `unknown` and narrowed through `isRecord`-style predicates. Only 5 `as <Type>` assertions exist across the 14 new modules — 3 in `-contract-support.ts` and 1 each in `-materializer-production.ts`, `-materializer.ts`, and `orchestration-handoff-handlers.ts` — and each follows a validating predicate that established the shape. ESLint with type-aware parsing over both `src` and `test` exits 0.

#### Error handling and logging

Failures become structured `blockedResult(...)` values carrying a `HANDOFF_*` code plus `affectedPaths` and `unsupportedCapabilities`, so a caller can act on the outcome without parsing a message. The gap is that 15 catch sites discard the cause on the way there, covered as a Major finding. It is worth noting that the code already knows better in one place: line 272 uses `catch (error: unknown)` and makes a decision based on the bound value, which is the pattern the other 15 sites should adopt.

### PowerShell implementation audit

#### What changed well

- **The allowlist is derived from the registry at load, not duplicated.** `Get-EpicPlanningRegisteredMcpTool` reads `config/orchestration-handoff-registry.json`, verifies each semantic id's `operation` matches its id suffix, verifies every `transport_aliases` entry against `^mcp__(?:drm-copilot|drm_copilot)__<escaped-operation>$`, and returns a sorted unique array. The hook therefore cannot drift from the registry the TypeScript and Python sides validate against, which is what makes AC7's "one shared alias registry" claim true rather than aspirational.
- **The regex escapes the interpolated operation.** `$escapedOperation = [regex]::Escape($operation)` before interpolation into the pattern is the correct handling of registry-sourced input in a regex position, and it is easy to omit.
- **Failures are prefixed and specific.** Every throw uses the `EPIC_PLANNING_ONLY_BLOCKED:` prefix with the offending id or path interpolated, so the hook's deny reason is greppable and self-locating.
- **Exactly one mutating operation is admitted.** `$script:PreparationSemanticMcpIds` lists four ids and the registry marks precisely one of them `mutating: true`. This reviewer verified both halves independently: the hook lists `drm-copilot.transition_prepared_orchestration` once at line 25, and the registry reports `mutating=True` for that id alone.

#### API and safety notes

`Get-EpicPlanningRegisteredMcpTool` declares `[CmdletBinding()]` and `[OutputType([string[]])]`, and both parameters are `[Parameter(Mandatory)]` with explicit types. `ConvertFrom-EpicPlanningJson` uses `[AllowNull()][AllowEmptyString()]` where an empty value is a meaningful input rather than a binding error, which is the right distinction. State uses `$script:` rather than `$global:`. PSScriptAnalyzer reports zero findings at every severity. Constructs are restricted to the intersection of PowerShell 5.1 and 7.x: no ternary, no null-coalescing, no `ForEach-Object -Parallel`.

#### Error handling and logging

The design is fail-closed and correct: an unreadable registry, an unregistered id, a mismatched operation, or a malformed alias each throws at hook load rather than degrading to a permissive allowlist, which is the only safe posture for a gate. `ConvertFrom-EpicPlanningJson` wraps `ConvertFrom-Json -ErrorAction Stop` in try/catch and rethrows with the parameter name attached. The one deficiency is that none of the four throw paths is exercised, covered as finding F1.
