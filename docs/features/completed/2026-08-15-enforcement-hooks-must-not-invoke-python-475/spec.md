## Overview

Remove every Python invocation from the enforcement-hook surface (`.claude/hooks/**` and `.claude/lib/**`), keep the hooks in PowerShell, and add a structural guard that prevents Python invocations from reappearing in that tree. After this change, one PowerShell implementation of each gate runs identically in drm-copilot and in every destination repository that receives the pushed-down governance payload; no gate's verdict depends on whether a Python toolchain happens to be installed.

Per owner decision HI-1 (resolved 2026-08-15T15:45Z), the orchestrator-state completion validator is ported to PowerShell at **complete parity** with the Python surface, measured row by row against the enumerated 85-check inventory in the 2026-08-15T15-30 research artifact. No check family is deferred, scoped out, or recorded as a follow-up. The existing tested PowerShell mirror is extended, not discarded. The hook-enforced completion gate does not weaken anywhere.

There are exactly four Python invocation sites (re-verified at HEAD b1a86fd3; research section 1.1):

| 1 | `.claude/hooks/enforce-discovery-artifact-gate.ps1:50` | `& python -m scripts.dev_tools.validate_discovery_artifacts` |
| 2 | `.claude/hooks/validate-discovery-artifact-gate.ps1:53` | same invocation |

Six additional hooks contain the word `python` only in string literals, comments, artifact paths, agent names, or `Invoke-Python*` function names. They contain no invocation and are not modified (research section 1.1).

- Target users: the repository owner pushing governance packs to destination repositories; orchestrator and executor agents whose runs are gated by these hooks.
- Expected impact: identical gate behavior regardless of installed toolchains; elimination of the dual-implementation drift class that produced the recorded MCP/Python parity divergence (`docs/features/potential/2026-08-15-mcp-pr-creation-ready-parity-divergence.md`).

### The guard

A new AST-based Pester guard at `tests/scripts/claude-runtime/enforcement-hooks-no-python-invocation.Tests.ps1`, modeled structurally on the house precedent `tests/scripts/claude-runtime/test-name-uniqueness.Tests.ps1` (CWD-independent root resolution in `BeforeAll`, a detection helper function, in-memory fixture `It`s proving the detection logic, and one repository-scan `It` asserting zero findings with the finding list in `-Because`).

- **Scope:** `.claude/hooks/**/*.ps1` plus `.claude/lib/**/*.ps1` and `.claude/lib/**/*.psm1`; excludes `.claude/lib/bash/**`.
- **Detection classes (research section 5.1)** — every `CommandAst` is classified:
  1. Bare or `&`/`.`-invoked constant command whose `GetCommandName()` is exactly `python`, `python3`, `py`, or `poetry` (case-insensitive), including quoted constants (`&'python'`, `& "python"`).
  2. `Start-Process` whose `-FilePath` argument (or first positional argument) is a constant matching the same name set.
  3. Dynamic invocation (`& $variable`, `. $variable`): fail-closed finding, with a required carve-out for scriptblock-parameter calls — a `CommandAst` whose invoked element is a `VariableExpressionAst` bound to a `[scriptblock]`-typed parameter in the same file (the hooks' `& $Invoker`, `& $ProfileReader`, `& $RequiredArtifactReader`, `& $FileExistsCheck` pattern) is not a finding. If distinguishing scriptblock parameters proves unreliable in the AST, the permitted fallback is to flag dynamic invocations only when the variable name matches `(?i)python|poetry|py\b`, with the residual gap documented in the guard file.
  4. `Invoke-Expression` in any form (already prohibited repo-wide; zero occurrences exist in scope today).
- **Non-detection requirements** — the guard must produce zero findings for: `python`/`poetry run` inside string literals and comments; `Invoke-Python*` function names invoked as commands (`Invoke-PythonTestPurityDecision`, `Invoke-PythonBatchBudgetHook`); and scriptblock-parameter `& $Invoker` calls. Concretely, the repository scan must report zero findings for the six incidental hooks (`check-python-test-purity.ps1`, `enforce-evidence-locations.ps1`, `enforce-orchestration-preimplementation-gate.ps1`, `enforce-python-batch-budget.ps1`, `validate-executor-output.ps1`, `validate-feature-review-coverage.ps1`) without modifying them.
- **Timing and allowlist:** the guard lands in the same change as the removals, after them, with no known-violations allowlist machinery (research section 8.1). With the HI-1 component hold released, the completion validator is in scope of this same run, so the guard's allowlist is zero entries: no site in the guarded tree is exempted for any reason.
- CI coverage is automatic: `_poshqc.yml` executes the full `tests/` tree; no new workflow step is required. The bundle mirror needs no second scan because `test_push_down_claude_resource_contracts.py` asserts text identity with the repo root files.

### Deliberate deviations (owner-visible; these are NOT deferred checks)

Every check is ported. The following are points where literal parity is wrong or undefined; each has a stated resolution recorded here and in the acceptance criteria.

- **PD-1 — missing-config crash.** `validate_route_membership` runs unconditionally (`validate_orchestrator_state.py:468`) and reads `config/orchestration-routing.json` with no exception handling, so even a plain Python validator call raises an uncaught `FileNotFoundError` in a repository lacking that config. Destinations do not receive the config; four config readers are implicated (inventory section 3). Literal parity would mean crashing in every destination — the exact portability failure this feature exists to remove. **Resolution: pinned constants with a config-parity test**, following the established `ModelRouting.psm1` pattern (`ModelRouting.psm1:33-39` records precisely this rationale for its own hard-coded constants). The port embeds the routing-matrix subset the checks consume — per-route `requires_pr_gate`, `requires_ci_gate`, `required_agents`, `required_skills`, `required_mcp_tools` — as constants, with a static Pester config-parity test pinning them against `config/orchestration-routing.json` in drm-copilot. Rationale for choosing constants over fail-closed-on-missing-config: fail-closed-on-missing-config would render the completion gate inoperable in every destination until the config ships, blocking all checkpoints rather than enforcing checks; pinned constants keep all 85 checks enforceable everywhere, and the parity test prevents drift where the config exists. The port performs no disk read of `config/orchestration-routing.json` at validation time.
- **PD-2 — duplicate error emission.** Under the hook's flag pair (`--require-complete --require-model-routing`) the Python model-routing gate re-runs the U6.C/U6.M per-entry validators, so a malformed entry emits each error string twice (inventory section 2.3, "Parity subtlety"). The duplication is an artifact of the Python call graph, not an intended contract. **Resolution: the port emits each error once (single emission), declared explicitly here rather than left emergent.** The M3 reuse requirement is satisfied by invoking the same per-entry validator implementation from the gate, not by re-emitting its output. The hook's verdict is unaffected (it keys on non-empty error output and prefix tokens, never on error counts). A test asserts that a malformed entry produces exactly one instance of each error string under the completion call.
- **PD-3 — undefined parity for epic/parallel.** For `epic-orchestrator-state` and `parallel-orchestrator-state` under the hook's flags, the Python CLI hits an argparse usage error and exits 2, so **zero** checks run; there is no Python behavior to be parity with (inventory section 1). The port must therefore **define** fail-closed behavior rather than port one. This confirms that defect D-1's fix is a design decision, not a port target. **Resolution: the type-scoped structural check specified in the Site 2 dispatch (exists, JSON parse, object root; fail-closed; no standard-checkpoint keys; no model-routing gate).** AC-3 and AC-4 are the enforcement of this definition; their wording is reconciled to describe defined behavior in an undefined-parity region rather than a deferral.

## Decision Record — Language Selection for the Completion-Validator Port (HI-1)

This section records the owner decision resolving HI-1 (`artifacts/orchestration/orchestrator-state.json`, `human_interaction.requirements[0]`, resolved 2026-08-15T15:45Z) so that the eventual bash migration of the hook surface inherits the analysis instead of relitigating it. It is a decision record, stated factually.

- **Decision.** The completion validator is ported to PowerShell now, at complete parity, extending the existing tested mirror. The proposed bash port is declined for this run. SD-1's scoped-port approach remains rejected.
- **The substantive correction.** The portability argument does not transfer from Python to bash. "Remove Python" and "adopt bash" are distinct arguments. Removing Python eliminates a dependency that destination repositories have no reason to carry. Adopting bash for one component **adds** two dependencies — bash, and a JSON parser — on top of the `pwsh` dependency that all 34 hook commands in `.claude/settings.json` already impose unconditionally (every hook command is `pwsh -NoProfile -File ...`; there are zero non-pwsh hook invocations). A mixed pwsh-dispatcher-plus-bash-library architecture would require destinations to carry `pwsh` AND bash AND a JSON parser, which is strictly more dependencies than today.
- **The sequencing rationale the owner accepted.** A bash port of a single component only pays off once the whole hook surface migrates to bash. Porting to PowerShell now and to bash later is two ports, but the second port runs against a full-parity Pester suite as its behavioral oracle instead of porting blind.
- **The oracle intent, stated explicitly.** The Pester suite written for this port is intended to serve as the behavioral oracle for the eventual bash migration. This intent must survive in the artifacts: it is recorded here and in the parity test suite header (AC-24).
- **Supporting facts (verified in the 2026-08-15T15-30 research and the HI-1 findings).** `jq` is absent locally and is referenced nowhere in `.claude/lib/bash/` or `scripts/bash/`; no bash library in the repository parses JSON (three only emit it). `bats` and `kcov` are absent locally while `shellcheck` and `shfmt` are present, so no agent in this run could execute bash unit tests or measure the kcov line-coverage floor that `.claude/rules/shell.md` applies to `.claude/lib/bash/`; the established verification path is CI dispatch of `_shell-coverage.yml`.
- **Preserved bash-branch analysis.** Had the bash branch been chosen, its own internal recommendation (inventory section 4.4) was to depend on `jq` with a fail-closed `command -v jq` probe and a test-override seam, rather than a hand-rolled bash JSON parser — the hand-rolled option was rejected because its residual risk is a silent wrong verdict in exactly the type-fidelity territory (escape decoding, absent-vs-null, int-vs-bool) the 85 checks depend on, and the checkpoint's unconstrained prose fields make a fail-closed subset parser unviable. The future migration should start from that conclusion.

## Destination Version Floor — PowerShell 7.4+

The discovery-validation leg of this feature imposes an explicit **destination version floor: PowerShell 7.4 or later**. This is a version floor, not a footnote: per owner ruling it is recorded here as a first-class requirement and is stated where a destination operator will actually encounter it — in the shared discovery-validation module's fail-closed runtime check and in that module's comment-based help — rather than only in a research artifact or a risk list.

- **Why the floor exists.** All seven schemas under `schemas/discovery/v1/*.json` declare `"$schema": "https://json-schema.org/draft/2020-12/schema"` (verified: 7 of 7). `Test-Json -SchemaFile` supports JSON Schema Draft 2020-12 only on PowerShell 7.4+; 7.0–7.3 do not support it. Verified in this environment: PowerShell 7.6.3 with the `-SchemaFile` parameter present. The repo standard stated in `.claude/rules/powershell.md` is "PowerShell 7+", which is below this floor; `.claude/rules/**` is not modified by this feature.
- **Draft 2020-12-free alternative assessed and rejected.** Per owner instruction, a Draft 2020-12-free implementation was to be preferred if available at reasonable cost. It is not available at reasonable cost: it would require either downgrading the seven schemas (a contract change, out of scope) or hand-rolling a JSON Schema validator in PowerShell. Hand-rolling is rejected on the same reasoning this feature already applied when declining a hand-rolled bash JSON parser (Decision Record, preserved bash-branch analysis): a bespoke parser inside a governance validator is a correctness risk that outweighs the dependency it avoids. The floor is therefore adopted deliberately, not by default.
- **Why a version floor is defensible where a new dependency would not be.** `pwsh` is already an unconditional dependency of all 34 hook commands in `.claude/settings.json` (verified: 34 of 34 are `pwsh -NoProfile -File ...`). Raising the minimum version of an existing unconditional dependency is strictly narrower than introducing bash plus a JSON parser. But because this feature exists to stop destinations needing things they do not have, the floor must be visible at the point of failure — hence the runtime check and help text below.
- **Enforcement at the point of failure.** The shared discovery-validation module performs a runtime version check and fails closed on PowerShell < 7.4 with an explicit, actionable message that names the required version, names `Test-Json -SchemaFile` Draft 2020-12 support as the reason, and identifies issue #475 (AC-26). It must not fail obscurely and must not silently degrade. The module's comment-based help states the 7.4+ floor (AC-27); the help text is the destination-visible surface because the module ships to destinations inside the `.claude/**` payload, the pushed-down pack contains only `config/` and `pack-manifests/` alongside `.claude/**` (there is no pack README to carry the statement), and `.claude/rules/**` must not be modified.
- **Test seam.** The version check is verified deterministically through an injectable version seam, without mutating the real `$PSVersionTable`, consistent with `.claude/rules/powershell.md`'s prohibition on reliance on mutable ambient host state (AC-28).

## Self-Gating Invariant (Plan Phases 10–11)

During plan Phases 10–11 the completion validator goes live while this very run is being gated by it: `.claude/settings.json` wires `validate-orchestrator-output.ps1` as the `orchestrator` SubagentStop hook, so the live `artifacts/orchestration/orchestrator-state.json` becomes subject to 79 newly enforced checks. The binding invariant, stated verbatim per owner requirement:

> **The reconciliation branch corrects the checkpoint, never the check.**

- If a newly enforced check fails against real checkpoint state, that is the gate working correctly, not a defect in the check.
- The permitted response is to correct the checkpoint and record the failing check IDs in the evidence artifact.
- Adjusting a check to accommodate the checkpoint, weakening a row to make this run pass, or relaxing a threshold is prohibited.
- Rationale, recorded so a later reader understands why the prohibition is absolute rather than a preference: a validator that a run edits to let itself through is worse than no validator — it certifies compliance while enforcing nothing.
- If the failure cannot be resolved by correcting the checkpoint, the run halts and reports it as a finding.
