## 2. Parallel Checkpoint Schema (`.claude/rules/parallel-orchestration.md`)

### 2.1 Top-level required fields

Per invariant 1 (`.claude/rules/parallel-orchestration.md:23`): `objective`, `completed_steps`,
`next_step`, `last_updated`, `route_id`, `parallel_slug`, `parallel_manifest_path`,
`parallel_status_doc_path`, `mode`, `max_concurrency`, `current_cohort`, `recolor_generation`,
`cohorts`, `items`, `conflict_edges`, `mutations`, `drift_events`.

### 2.2 Route identity

Invariant 2 (`.claude/rules/parallel-orchestration.md:25`): `route_id` must be **exactly**
`'parallel'`. This is the field a new hook branch should check to identify a parallel-shaped
checkpoint before trusting any other field on it (the epic-integration branch has no analogous
`route_id` check because the epic checkpoint's shape — presence of `epic_merge_pr` — is itself
distinguishing; the parallel checkpoint's shape is a bare `items[]` array, so the explicit
`route_id == 'parallel'` check is the correct discriminator, consistent with invariant 2's
purpose).

### 2.3 Per-item fields relevant to merge authorization

Invariant 5 (`parallel-orchestration.md:31`): each `items[]` entry has (at minimum) `issue_num`
(positive integer, unique) and `feature_folder` (non-empty string).

Invariant 6 (`parallel-orchestration.md:33`), the item **state** enum (eight members):
`proposed | admitted | prepared | scheduled | in_flight | merged | withdrawn | blocked`.

Invariant 7 (`parallel-orchestration.md:35`), the **`merge_status`** enum (eight members):
`not_started | worktree_created | pr_open | ci_green | merged | worktree_removed |
blocked_drift | blocked_ci_loop_limit`. Absent `merge_status` is treated as `not_started`.

The enum-ownership table restates the same eight members verbatim at
`parallel-orchestration.md:181`.

**PR number field**: the checkpoint schema does not name the item's PR-number field inside the
numbered invariants directly, but it is named explicitly in the Cache Doctrine section
(`parallel-orchestration.md:131`): `` `gh pr view --json state,mergedAt,headRefOid` — pull-request
state, merge time, and merge commit (`items[].pr_number`, `pr_url`, `merge_status`, `merged_at`,
`merge_commit_sha`) ``. This is confirmed independently in `.claude/agents/parallel-orchestrator.md:217`
("`pr_number`, `pr_url`, `merge_status`, `merge_commit_sha`") and in
`.claude/skills/parallel-orchestrate/SKILL.md:448` ("`pr_number`, `pr_url`, `merge_status`,
`merge_commit_sha`, and the lifecycle timestamps"). **The field name is `pr_number` (singular,
per-item), not `pr_number` on a nested object** — it sits directly on each `items[]` entry,
structurally parallel to the epic checkpoint's `epic_merge_pr.pr_number` but one level shallower
(no wrapping `epic_merge_pr`-equivalent object per item).

### 2.4 Cache Doctrine (`parallel-orchestration.md:125-133`)

> "The parallel-orchestrator checkpoint is a CACHE of durable state, not the source of truth."

The three re-derivation commands are `git worktree list --porcelain` (worktree existence/path),
`git branch` (branch existence/name), and `` `gh pr view --json state,mergedAt,headRefOid` ``
(PR state/merge time/merge commit). The doctrine explicitly states validators "check the
checkpoint's structural shape only; they never assert that the cached values agree with the
repository, because that reconciliation is a runtime concern of the orchestrator surface, not a
schema concern" (`parallel-orchestration.md:133`). This matters for the hook design: the existing
`enforce-epic-merge-gate.ps1` design decision (hook lines 23-26) is explicitly to "trust the
on-disk checkpoint rather than shelling out live to `gh pr view`... matching the same
non-adversarial, policy-level-not-cryptographic posture." That same posture is consistent with the
Cache Doctrine's framing of the checkpoint as a trusted (if stale-tolerant) cache for schema
purposes — the hook is not expected to re-verify against `gh` at PreToolUse time, matching current
behavior for both existing branches.

## 3. Merge-Ready Gate Value

**`ci_green`** is the merge-ready enum member (`parallel-orchestration.md:35,181`). Confirmed by
the transition-chain description in `.claude/skills/parallel-orchestrate/SKILL.md:456-459`:

> "`pr_open` to `ci_green` on durable confirmation after child DONE; `ci_green` to `merged` when
> the parent's merge succeeds"

`ci_green` and `merged`/`worktree_removed` are distinct and sequential: `ci_green` is the
pre-merge state (checks are green, PR still open) and `merged` is the post-merge state (the
`gh pr merge --merge` command already succeeded). The correct merge-ready gate for the new hook
branch is therefore **`merge_status == 'ci_green'`** on the target item — a merge attempted while
the target item is already `merged` or `worktree_removed` is not a legitimate scenario the
"about-to-merge" check needs to authorize (the command would not normally be re-issued at that
point), and other values (`not_started`, `worktree_created`, `pr_open`, `blocked_drift`,
`blocked_ci_loop_limit`) all represent states where CI has not been durably confirmed green or the
item is blocked, so none should authorize a merge attempt. The Cohort Barrier documentation
independently confirms `ci_green` is not itself a terminal/merged state: "`ci_green` does not
satisfy the barrier" (`.claude/agents/parallel-orchestrator.md:192`; also
`.claude/skills/parallel-orchestrate/SKILL.md:119-120,712`) — the barrier requires `merged` or
`worktree_removed`, precisely because `ci_green` denotes "not yet merged."

Issue #492's AC1 and AC3 (`docs/features/active/2026-08-19-parallel-merge-gate-allow-branch-492/issue.md:63,65`)
independently specify `merge_status == "ci_green"` as the allow condition and specify that a
target item whose `merge_status` is not `ci_green` must deny — consistent with the above.

## 4. Actual `gh pr merge` Invocation Form

`.claude/skills/parallel-orchestrate/SKILL.md:305-333` ("Per-Item Merge to Main (Merge-on-Green)")
documents the procedure. Step 3 (line 322):

> "3. Execute `gh pr merge --merge <PR>` for that item's pull request, whose base is `main`."

`<PR>` is a placeholder for that item's own PR reference (its `pr_number`), **not** a bare
invocation. This is a structural necessity, not merely a style choice: `parallel-orchestrator`
runs multiple items concurrently, each in its own isolated git worktree/branch
(`.claude/agents/parallel-orchestrator.md:42-45,165-167`), so there is no single "current branch"
the parent's own working directory could use to disambiguate which item's PR a bare `gh pr merge
--merge` should target — unlike the epic-integration path, which operates from a single
integration-branch context where "the current branch's PR" is unambiguous (hook comment, lines
190-192). The parallel-orchestrator's own working directory when it runs `gh pr merge` is its own
process context, not any one item's worktree, so an explicit PR number is the only way to identify
the target item.

Consequently, the actual command form to expect from a legitimate parallel merge is
**`gh pr merge --merge <N>`** with an explicit integer PR number, matching the existing
`Get-EpicMergeGateCommandPrNumber` regex (`(?i)\bgh\s+pr\s+merge\s+(\d+)\b`, hook line 116) without
modification. AC2 of issue #492 (`issue.md:64`) explicitly asks the new branch to require a
matching PR number "mirroring the existing epic-path PR-number matching logic," which is
consistent with this finding.

**Open design question for the plan** (not resolved by any document read): the epic-integration
branch's existing code trusts a bare (no-PR-number) `gh pr merge --merge` to mean "the current
branch's PR" (hook lines 190-192). Because the parallel case structurally always names an explicit
PR number in practice, the plan does not need to replicate that same bare-command trust for the
parallel branch; it can require a resolvable PR number for the parallel path and treat the
otherwise-bare-command trust as strictly an epic-branch feature. This is a design choice for the
plan to make explicit, not an ambiguity in the current documented behavior of
`parallel-orchestrator`.

No other file within `.claude/agents/`, `.claude/skills/parallel*/`, or `.claude/lib/bash/`
contains a second literal `gh pr merge` invocation; the grep across `.claude/` surfaced exactly the
skill line above plus the hook's own doc comments/regex.

## 7. Candidate Approaches

### Approach A (recommended): Add a third branch function mirroring the existing pattern

Add `Get-ParallelOrchestratorCheckpointContent` (read seam, same shape as the two existing seam
functions), a `Test-ParallelCheckpointAllowsMerge` function that: (1) requires `route_id ==
'parallel'`; (2) requires a resolvable target item — via the explicit PR number extracted by the
existing `Get-EpicMergeGateCommandPrNumber` matched against `items[].pr_number`; (3) requires that
resolved item's `merge_status == 'ci_green'`. Wire it into `Invoke-EpicMergeGateDecision` as a
third `if` after the existing two branches, before the final deny. This is the minimal-diff
approach: it reuses the existing read-seam pattern, the existing PR-number-extraction regex, and
the existing allow/deny decision constructors verbatim, and requires no change to any other hook.

**Advantages**: matches repo conventions exactly (wrapper/seam pattern already established in this
file); minimal surface area; the existing test file's dot-source/mock pattern extends directly;
satisfies AC1-AC4 and AC6 as literally specified.

**Limitations**: requires deciding how to resolve "target item" when no PR number is present in
the command (see the open design question in Section 4) — the safest choice, given the fail-closed
posture the hook already uses elsewhere (comment lines 18-19), is to deny when no PR number is
present and no item can be unambiguously resolved, rather than inventing a "current branch" concept
for the parallel path that no other document supports.

### Approach B (rejected): A separate dedicated parallel-merge-gate hook file

A new `.claude/hooks/enforce-parallel-merge-gate.ps1` file, wired as an additional `Bash`-matcher
hook, that independently allows the command. This was explicitly rejected by the issue's own
"Suspected Cause / Notes" (`issue.md:53`): "Multiple PreToolUse hooks on the same `Bash` matcher are
conjunctive for denial, so any dedicated new hook cannot un-deny a merge on its own;
`enforce-epic-merge-gate.ps1` itself must stop denying legitimate parallel merges." Confirmed by
this research: PreToolUse hooks are independently invoked and a `deny` from any one of them blocks
the tool call (each hook returns its own decision; there is no cross-hook "allow overrides prior
deny" mechanism visible in any hook read). A new hook could only ever add another point of denial,
not authorize past `enforce-epic-merge-gate.ps1`'s own deny.

**Rejected alternative summary**: Approach B cannot work under the current PreToolUse hook
composition model; Approach A is the only viable design and is adopted.

## 8. Behavior Semantics (success/failure/edge cases)

- **Success**: command matches `gh\s+pr\s+merge\b` + `--merge\b`; parallel checkpoint exists,
  parses, and has `route_id == 'parallel'`; the command's explicit PR number resolves to an
  `items[]` entry; that item's `merge_status == 'ci_green'` → allow.
- **Failure (fail-closed, per existing hook posture)**:
  - Parallel checkpoint file absent or unreadable → this branch does not allow (falls through to
    final deny, unless another branch already allowed).
  - Checkpoint present but malformed JSON → same (existing `ConvertFrom-EpicMergeGateJson` returns
    `$null` on malformed JSON, matching existing behavior for the other two branches).
  - `route_id` present but not exactly `'parallel'` → branch does not allow.
  - No PR number in the command text → branch should not allow (no safe "current branch" fallback
    exists for a multi-worktree surface; see Section 4).
  - PR number present but no `items[]` entry has that `pr_number` → branch does not allow.
  - Resolved item found but `merge_status` is anything other than `ci_green` (including `merged`,
    `worktree_removed`, `not_started`, `worktree_created`, `pr_open`, `blocked_drift`,
    `blocked_ci_loop_limit`) → branch does not allow.
- **Ordering**: the three branches are independent `if`-return checks; order does not affect
  outcome since each is a pure predicate over its own checkpoint file, matching the existing
  two-branch structure (child branch checked first, then epic branch, per lines 278-285). The new
  branch can be appended as a third check without reordering the existing two.
- **Non-regression**: AC4 requires the existing two branches to behave identically. Since Approach
  A adds a new independent function and a new `if` block without touching
  `Test-ChildCheckpointAllowsEpicMerge` or `Test-EpicCheckpointAllowsMerge`, this is structurally
  guaranteed by the diff shape, not merely by test coverage.
