## Scope of the Fix

Research candidates **B + A + G** are adopted. Candidates C, D, E, and F are rejected; the rejection reasoning is recorded in the spec under Scope & Non-Goals and is not re-litigated here.

- **B (primary, test-side).** Substitute an ordered, synchronous `threading.Thread` stand-in in the two racy end-to-end tests so the Python lane runs and fails before the JSON lane starts. The Python lane's failure sets the cancel event at `fix_all_runtime.py` lines 144-145 before the JSON lane begins, so the JSON lane returns at its **first** cancel check (`fix_all_branches.py` line 102) and never reaches the 10 ms wall-clock grace period at line 112. Precedent already in the repository: the `_SkipBranchThread` synchronous stand-in at `tests/scripts/dev_tools/test_fix_all_failure_paths.py` lines 425-461.
- **A (coverage).** Add three direct, single-threaded unit tests of `run_json_branch` covering all three cancel branches, with zero threads and no elapsed-time dependency.
- **G (production hardening).** Harden `_runner` at `scripts/dev_tools/fix_all_runtime.py` lines 141-145 so a branch function that raises is recorded as a failing `BranchResult` instead of terminating its thread silently. Today an exception leaves the `results` entry unset and line 183 computes the exit code over recorded results only, returning 0 when the other four lanes pass — a silent false pass.

Two racy tests are in scope, not one:

1. `tests/scripts/dev_tools/test_fix_all_failure_paths.py::test_json_cancel_before_validate_returns_canceled_result` (the reported flake).
2. `tests/scripts/dev_tools/test_fix_all.py::test_fail_fast_cancels_json_before_validate` at lines 382-399 (identical latent race; its sibling failure is at the third Python step, so its race window is at least as tight).

## Fail-Before Evidence Decision (stated explicitly)

The two classes of regression in this fix have different fail-before characteristics, and this plan treats them differently on purpose.

- **Candidate B (the two racy tests): intermittent and load-dependent.** A single pre-fix run is not reliable fail-before evidence, because the outcome flips on whether the Python lane's time-to-failure exceeds the fixed 10 ms grace period. This plan therefore requires **both** of the following, unconditionally: (1) a bounded repeated-run protocol of 50 iterations executed while a concurrent full-suite run occupies the machine, recording a numeric observed failure count; and (2) a `fail-before-exception` dossier under the canonical regression-testing evidence folder carrying `WhyFailingRunImpossible:` and an alternative proof. The dossier is required even when the protocol does observe failures, because a probabilistic failure is not a deterministic fail-before artifact and the audit trail must say so rather than imply a determinism the pre-fix code never had. The alternative proof is the line-cited static argument recorded in the research document plus the measured failure count from the protocol run.
- **Candidate G (the `_runner` hardening): deterministic.** A clean fail-before test exists and is planned as a real failing-then-passing test. `test_runner_records_failing_result_when_branch_raises` is written first, run against the unmodified production module where it must fail, then run again after the `_runner` change where it must pass. Both runs are recorded.
