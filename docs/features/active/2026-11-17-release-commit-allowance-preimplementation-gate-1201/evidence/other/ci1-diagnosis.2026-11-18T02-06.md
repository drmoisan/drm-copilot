It makes no explicit `Import-Module` call and no `Reset-EpicStateProbeModuleBinding` call.
- `enforce-orchestration-preimplementation-gate.BookkeepingLeg.Tests.ps1` (outer `BeforeAll`): dot-sources the same gate, then the helpers. It calls `Register-EpicStateBaselineMock`, then makes explicit `Import-Module` calls of `EpicScopeResolution.psm1` and `WorktreeRunResolution.psm1` without `-Force`, with `-ModuleName` mocks of `Get-EpicScopeCheckpointText`, `Get-WorktreeRunCheckpointText`, and `Get-WorktreeItemLiveRoot`. - `enforce-orchestration-preimplementation-gate.ReleaseAllowance.Tests.ps1` (outer `BeforeAll`): same shape as BookkeepingLeg, with an explicit `WorktreeRunResolution.psm1` import and two run-module mocks, and no reset.
- Conclusion of the comparison: every import is made without `-Force`, so in all three suites each `Import-Module` is a no-op against an already-loaded instance, and each `-ModuleName` mock binds to whatever instance is current. The three setups are equivalent with respect to a stale binding. None of them repairs a stale binding, and none would pass the probe if a stale binding existed when it ran. The two decision suites passed on Linux because no run-module-replacing suite ran before them in that process (section 3), not because of a setup difference.

## 2. Module state

- `enforce-orchestration-preimplementation-gate-epic-scope.ps1` (dot-sourced by the gate) imports `WorktreeResolution`, `WorktreeItemResolution`, `WorktreeRunResolution`, `EpicScopeResolution`, `EpicScopeReadiness`, and `HookTargetWorktree` without `-Force`. `hook-release-allowance-context.ps1` imports no module. Against an empty table these imports load one instance of each module. Against a loaded table they re-export the existing instances and load nothing.
- `EpicScopeResolution.psm1` imports `WorktreeRunResolution.psm1` without `-Force` at module load, so its `Resolve-WorktreeEpicTarget` is bound to the `WorktreeRunResolution` instance that was current when `EpicScopeResolution` was first loaded.
- `Register-EpicStateBaselineMock` and `Import-EpicStateProbeModule` (`EpicStateIsolation.Baseline.Helpers.ps1`) import without `-Force`, so they bind `Mock -ModuleName` to the instance currently in the module table.
- `Resolve-EpicScopeCheckpoint` (`EpicScopeResolution.psm1`) calls `Resolve-WorktreeEpicTarget`. When the target status is `NoTarget`, it returns `epic-checkpoint-absent-or-unparseable` before it calls `Get-EpicScopeCheckpointText`.
- The condition `Reset-EpicStateProbeModuleBinding` repairs arises as follows. `Import-Module -Force` of `WorktreeRunResolution.psm1` replaces the run module in the table while a loaded `EpicScopeResolution` keeps its reference to the removed instance. The probe's `Invoke-EpicStateProbeEpicScope` mocks `Get-WorktreeItemLiveRoot` and `Get-WorktreeRunCheckpointText` with `-ModuleName WorktreeRunResolution`, which binds them to the current instance. The stale instance that `EpicScopeResolution` calls is therefore unmocked: it runs the real `Get-WorktreeRunLiveRoot` and checkpoint reads, which on a CI runner find no epic checkpoint recording `epic/hostile-integration`, so it returns `NoTarget`. The observed CI result matches this path exactly: the probe's `IsEpicScope` and `Reason` assertions passed, and the `Should -Invoke Get-EpicScopeCheckpointText ... -Times 1 -Exactly` assertion observed 0 calls.
- Source of the replacement: of every `Import-Module -Force` under `.claude/hooks` and `.claude/lib`, only `.claude/hooks/validate-orchestrator-output.ps1` (its dependency-import block) force-imports `WorktreeRunResolution.psm1`. `enforce-pr-author-skill-helpers.ps1` force-imports `EpicScopeResolution.psm1`, which reloads it bound to the current run module and so does not create the stale state. Two test suites force-import `WorktreeRunResolution.psm1` directly.

## 6. Conclusion

RootCause: in the single-process Linux job, a suite that runs earlier and loads `validate-orchestrator-output.ps1` (which runs `Import-Module -Force` of `WorktreeRunResolution.psm1`), or force-imports that module directly, leaves the loaded `EpicScopeResolution` bound to a removed `WorktreeRunResolution` instance. `hook-release-allowance-context.Tests.ps1` does not repair that binding before it registers its mocks, so the probe's run-module mocks miss, `Resolve-WorktreeEpicTarget` returns `NoTarget`, and `Get-EpicScopeCheckpointText` is never called.

ProductionDefect: no. `validate-orchestrator-output.ps1` runs as its own `pwsh -File` process in production, where its `-Force` imports load into an empty table and leave no stale binding. The interaction exists only when a test dot-sources the hook into a shared Pester process, and the four-copy release hook files are unaffected.
Fix: victim side: in the outer `BeforeAll` of `hook-release-allowance-context.Tests.ps1`, call `Reset-EpicStateProbeModuleBinding` after the helpers are dot-sourced and before the first `Register-EpicStateBaselineMock` (the form of `hook-dependency-failure.Claude.Tests.ps1` and `hook-command-consumers.Issue824.Tests.ps1`). The reset discards a stale `EpicScopeResolution`, and `Register-EpicStateBaselineMock` then imports a fresh instance bound to the current `WorktreeRunResolution`, so the probe holds whatever ran before. No further module mock is added: `Register-EpicStateBaselineMock` already registers `Get-WorktreeRunCheckpointText` in `WorktreeRunResolution`, and the probe mocks the remaining run-module seams itself. Leaker side: add to each listed suite only a teardown that calls `Reset-EpicStateProbeModuleBinding` (the `AfterAll` form of `enforce-parallel-cohort-barrier.Tests.ps1` and `validate-orchestrator-output.Envelope.Tests.ps1`). The teardown goes at file level, or in the Describe that loads the hook for `hook-import-failure-exemptions.FailClosed.Tests.ps1`. Where the suite does not already dot-source `EpicStateIsolation.Baseline.Helpers.ps1`, it dot-sources the helper inside that `AfterAll` first.
