## New module design — reference text for Phase 3

`scripts/dev_tools/check_python_coverage_thresholds.py` separates pure comparison from file I/O and from argument parsing, per the general code-change policy.

Public surface:

```text
DEFAULT_MIN_LINE = 85.0
DEFAULT_MIN_BRANCH = 75.0

class CoverageReportError(RuntimeError): ...

def find_threshold_breaches(totals, *, min_line, min_branch) -> list[str]
def load_totals(report_path) -> Mapping[str, object]
def main(argv=None) -> int
```

Behavioural contract:

- `find_threshold_breaches` is pure. It takes the parsed `totals` mapping and the two floors and returns a list of failure messages. An empty list means the gate passes. Comparison is inclusive at the floor: a value exactly equal to its floor passes.
- A missing `percent_statements_covered` key, and a missing `percent_branches_covered` key, each produce a failure message rather than a silent pass. The branch-absence message must contain the exact lowercase substring `branch data was not collected`, which is the shape produced when the branch flag was omitted.
- A line breach message must contain the exact lowercase substring `line coverage`. A branch breach message must contain the exact lowercase substring `branch coverage`. When both metrics breach, both messages are returned in the same call, not only the first.
- `load_totals` raises `CoverageReportError` when the report file is missing or unreadable, when its content is not valid JSON, or when `totals` is absent or is not a mapping. Every such message names the report path.
- **Mandatory I/O constraint, load-bearing for the tests.** `load_totals` must read the report through `pathlib.Path.read_text`. The builtin `open`, `json.load` applied to an open file object, and `os`-level reads are all prohibited in this module. The reason is testability under the repository's no-temporary-file rule: the in-memory filesystem fixture `mem_fs_path` in `tests/conftest.py` monkeypatches `Path` methods including `read_text`, `exists`, and `is_file`, and does **not** intercept builtin `open`; `pyfakefs` is not installed. If the loader is implemented with `open`, the unparseable-report case in P3-T8 cannot be exercised without writing an on-disk temporary file, which `.claude/rules/general-unit-test.md` prohibits outright. The module therefore parses with `json.loads` applied to the string returned by `Path.read_text`.
- `main` parses `--report`, `--min-line`, and `--min-branch`, defaults the two floors to 85.0 and 75.0 so an omitted argument cannot weaken the gate, writes every failure message to standard error, and returns 0 when there are none and 1 otherwise. There is no broad catch-all that can return success on an unread metric.
- The module is fully type-annotated, stays under the 500-line limit, and adds no third-party dependency.

## Five environment traps this plan encodes as explicit steps

**Trap 1 — the virtual environment may belong to a different checkout.** The Poetry environment `poetry run` resolves is not guaranteed to be rooted in the executing checkout, and in the preparation worktree it was not: no `.venv` existed there and `poetry env info --path` resolved to an environment outside it. The current working directory still wins on the module search path, so an import run from the repository root resolves to that checkout's source, but that must be demonstrated rather than assumed. P0-T2 resolves the repository root, then prints both the environment path and a resolved module file path into its artifact, and no coverage number produced by any later task may be treated as evidence unless P0-T2's artifact is present and shows the module resolving under the resolved repository root.

Related, and expected rather than a finding: when the executing checkout has no `.venv` subdirectory, `poetry run pyright` prints a message about a missing virtual-environment directory, because pyproject.toml sets a virtual-environment path and name. It still type-checks and still exits 0. The executor must record that message in the artifact and must **not** create a virtual environment in response, because doing so would be an unstated write outside the closed write set.

**Trap 2 — the local `main` ref may be stale, and HEAD does not carry the change until Phase 6.** Two distinct hazards share this trap, and the plan handles them separately.

First, the local `main` ref can lag `origin/main` while the branch was cut from `origin/main`. Every **committed-diff** acceptance condition in this plan therefore uses the three-dot form against `origin/main`, never against local `main`.

Second, and the more consequential hazard: this plan makes its first commit at P6-T1. Before that point the branch carries no commit of its own, so `HEAD` is the merge base of `origin/main` and `HEAD`, and `git diff --name-only origin/main...HEAD` — whose three-dot form diffs against that merge base — prints an empty list, so any acceptance condition phrased against that list is satisfied by emptiness whatever the executor did. **The premise is the merge base, not equality of the two refs.** `origin/main` may already have advanced past the branch point, in which case `HEAD` and `origin/main` are different commits while the three-dot listing is still empty; the emptiness therefore does not depend on the two refs being equal, and no condition anywhere in this plan may be built on the claim that they are. See R22 in the cycle-4 preflight findings for the measurement that falsified that claim. That is precisely the class of unfalsifiable verification step this work item exists to repair, so the plan must not reproduce it. Accordingly:

- The Phase 4 scope gates P4-T9, P4-T10, and P4-T11 read the **working tree** through `git status --porcelain --untracked-files=all`, which does carry the Phase 1 through Phase 3 edits at that point, and each of the three additionally asserts that the recorded path list is **non-empty**. An empty list at Phase 4 proves the edits are absent and is a failure, not a pass.
- The **committed** form of the same three assertions is carried by P6-T2, which runs immediately after the first commit at P6-T1 and is therefore the point at which `git diff --name-only origin/main...HEAD` is capable of returning a non-empty list. P6-T2 is the falsifiable form of AC-14 and AC-15.

**Trap 3 — multi-line `-c` strings.** A multi-line string passed to `python -c` under `poetry run` prints nothing and exits 0 on this machine. Every `-c` invocation below is a single line.

**Trap 4 — `git status --porcelain` output is not a bare path list, and deriving one takes three steps.** The three Phase 4 scope gates P4-T9, P4-T10, and P4-T11 all read the output of `git status --porcelain --untracked-files=all` and all use the exact phrase **"derived path list"** for what they assert against. That phrase means the result of applying all three of the following steps to that output, in order. Applying only the first is not sufficient.

1. **Strip the status field.** Each line begins with a two-character staged/unstaged status field, followed by a single space, followed by the path. An untracked entry uses the status field `??`. Remove the first three characters of every line.
2. **Expand a renamed entry into both of its paths.** A rename or copy entry carries the arrow form `old -> new` in its path position. Record both the old path and the new path as separate entries in the derived path list, so that neither side of the rename escapes the gate.
3. **Unquote a quoted path.** When a path contains a space, a double quote, a backslash, or a byte outside the printable ASCII range, git wraps the path in double quotes and escapes it in C style, and by default also renders non-ASCII bytes as octal escapes. Strip the surrounding double quotes and decode the C-style escapes before recording the path, so that a quoted path is compared in the same form as the write-set entries it is checked against. A path recorded with its quotes still attached matches no write-set entry and would halt a gate spuriously; a path whose escapes were never decoded could hide a real escape from the write set.

The post-commit scope gate P6-T2 is different and needs none of this handling: it reads `git diff --name-only origin/main...HEAD`, which emits a bare name list with no status field and no arrow form, and the plan therefore uses the distinct phrase **"recorded name list"** there. The one shape it shares with `git status` is quoting of unusual paths, so step 3 applies to it as well; steps 1 and 2 do not.

**Trap 5 — a command that is correct in intent can be inert on the executing shell, and an inert command returns no result rather than a failing one.** The executing shell of this plan is not fixed: this environment declares PowerShell primary, a POSIX shell is also available, and no task names which one runs. This plan's preflight cycles produced three Blocking findings of exactly this shape — R4 and R11 in cycle 2 and R21 in cycle 4 — so it is recorded here as a standing authoring obligation rather than as three isolated corrections.

The general obligation: **every command in this plan that contains shell-significant punctuation must be quoted so that the token reaches the program rather than the shell parser, and the quoting must be correct in both PowerShell and a POSIX shell.** Double quotes satisfy both, so double quotes are the default form. An acceptance condition whose command cannot be parsed does not fail — it raises a parser error before the program is invoked and returns no verdict at all, which is a strictly worse outcome than a failing condition and is invisible to a reader who reads the command only for intent.

The instances this plan encodes explicitly, each with its reason stated inline at the task so that a later editor does not undo it:

1. **The upstream ref `@{u}` must be written `"@{u}"`** — P6-T3 conditions (b) and (c). Unquoted, PowerShell reads `@{` as the opening of a hash literal and raises `ParserError: Missing '=' operator after key in hash literal` before `git` runs. The quoted form is correct under both shells.
2. **The containment probe is a single-line double-quoted `-c` string** — P0-T2. See Trap 3 for the multi-line half of the same hazard.
3. **No path is compared as raw text across a separator boundary** — P0-T2. The `pathlib` comparison exists because the two sides use different separators on Windows; this is the same class of platform-dependence expressed in path syntax rather than in shell syntax.

A later editor who adds a command containing `@`, `{`, `}`, `$`, `(`, `)`, `;`, `|`, or a space inside an operand must quote it under this rule and must state the reason inline, as the three entries above do.
