### D-1 — the containment comparison, and the exact-root candidate

The comparison becomes, quoted verbatim as the literal the executor writes:

`return ([string]::Equals($normalizedPath, $normalizedRoot, [System.StringComparison]::OrdinalIgnoreCase) -or $normalizedPath.StartsWith($normalizedRoot + '/', [System.StringComparison]::OrdinalIgnoreCase))`

**The exact-root candidate must still be admitted, and the equality operand is how.** `spec.md`
lines 325-328 pin `StartsWith($root + '/', [System.StringComparison]::OrdinalIgnoreCase)` and nothing
else; that form alone rejects a candidate equal to the root, because the root carries no trailing
separator after `TrimEnd('/')`. Three reasons make the explicit equality operand the right reading of
that rule rather than a departure from it. First, the helper is shared by the decision path and by the
rehydrate filter `ConvertTo-*BatchBudgetState`, and the rehydrate filter applies no extension filter
to persisted entries, so a persisted entry equal to the root is structurally representable in the
state file even though the scope filter keeps it out of the decision path. Second, the pre-fix
behaviour admitted the exact-root candidate, and narrowing it would be a behaviour change no finding
asks for. Third, the cost is one operand in one expression.

**The replacement is a single-line replacement of one existing line and must add no line and remove
no line.** The current line is `.claude/hooks/enforce-powershell-batch-budget.ps1:92` and
`.claude/hooks/enforce-python-batch-budget.ps1:89`, each carrying
`return $normalizedPath.StartsWith($normalizedRoot, [System.StringComparison]::OrdinalIgnoreCase)`.
Holding the line count fixed is load-bearing, not cosmetic: the B-3 fail-before evidence is a per-line
coverage record keyed on absolute line numbers 154 and 155 of the PowerShell hook and 151 and 152 of
the Python hook, and any line-count change in the same file would silently move those numbers between
the baseline capture and the final capture. The early return for a relative candidate, the empty-root
guard, the null-or-whitespace path guard, and `OrdinalIgnoreCase` throughout are all preserved
unchanged.

### D-2 — the unterminated managed block

**When no closing sentinel is found at or after the opening sentinel, the managed block is treated as
the opening sentinel line alone. Every line after the opening sentinel is preserved, in its original
order.** This is a single answer and no alternative is offered.

The edit is `extensions/drm-copilot/src/lib/push-down/claude-gitignore-merge.ts:126`, changing
`const endIndex = endOffset === -1 ? lines.length - 1 : beginIndex + endOffset;` to
`const endIndex = endOffset === -1 ? beginIndex : beginIndex + endOffset;`.

Consequences, stated so they are accepted deliberately rather than discovered later:

- The former body of the unterminated block becomes ordinary unmanaged content sitting after the
  newly closed managed block. On the reviewer's demonstrated input
  `"a/\n# BEGIN drm-copilot managed ignores\n.old/\nb/\nc/\n"` the output retains `.old/`, `b/`, and
  `c/` after the block. Retaining `.old/` is correct under the module's line-26 invariant, which
  preserves content outside the block rather than judging it, and a stale ignore pattern is inert to
  git in the same way the module's existing duplicate-entry decision already relies on.
- The result is a fixed point. Applying the function to that output finds a well-formed block at
  `beginIndex = 1` with its closer three lines later, replaces it in place, and returns the same
  document. Each sentinel occurs exactly once in the output.
- The well-formed path is untouched, because `endOffset === -1` is false whenever a closer exists at
  or after the opener. Append-when-absent, never-a-second-block, and the existing seven merge tests
  are unaffected.

## Toolchain command forms

Every TypeScript command is a single compound command of the form
`cd extensions/drm-copilot && npx <tool> <args>`, because each Bash tool call starts in the repository
root and inherits no working directory from a previous call. The flags `--passWithNoTests`,
`--onlyChanged`, and `--lastCommit` are prohibited in every Jest command in this plan; each converts
zero discovered tests into a green run.

PowerShell format and lint run through `mcp__drm-copilot__run_poshqc_format` and
`mcp__drm-copilot__run_poshqc_analyze`. There is no PowerShell type-check stage. Pester measures
command and line coverage only, so the 85 percent line threshold applies and no branch gate applies.

**How `EXIT_CODE:` is derived for a PoshQC MCP task.** The PoshQC MCP tools return a structured result
object with fields `ok`, `tool`, `workspace_root`, `summary`, and, on failure only, `stderr_excerpt`
(`extensions/drm-copilot/src/mcp-tools.ts`). A non-zero exit of the spawned `pwsh` process becomes a
`CommandExecutionError` whose message is `Command exited with code <N>.`
(`extensions/drm-copilot/src/command-runtime.ts`), which the MCP layer projects onto `ok: false` with
that message in `summary`. Record `EXIT_CODE: 0` when the result carries `ok: true`; record
`EXIT_CODE: <N>` taken from that message when it carries `ok: false`; quote `summary`, and
`stderr_excerpt` when present, verbatim in both cases. An `ok: true` analyze result is a falsifiable
zero-findings claim: `Invoke-PoshQCAnalyze` raises `PSScriptAnalyzer reported N issue(s).` whenever
its result set is non-empty (`scripts/powershell/PoshQC/PoshQC.Analyzer.psm1`), and the bundled entry
script sets `$ErrorActionPreference = "Stop"`, so one finding terminates the process and yields
`ok: false`. A PoshQC MCP result carries no test counts and no test names at all.

**Form A — self-hosted scoped Pester run.** One suite per invocation, using the single-string
`-ScanFolders` form that the completed plan exercised:

`pwsh -NoProfile -Command "Import-Module ./scripts/powershell/PoshQC/PoshQC.psd1 -Force; Invoke-PoshQCTest -Root (Get-Location).Path -SettingsPath 'scripts/powershell/PoshQC/settings/pester.runsettings.psd1' -ScanFolders '<suite>'"`

with `<suite>` replaced by exactly one of the two suite paths named in each task. `Run.Exit = $true`
in `scripts/powershell/PoshQC/settings/pester.runsettings.psd1` makes Pester terminate the process
with a non-zero exit code when the run has failures, so the process exit code of a Form A run is a
real pass/fail signal. On a completing run `Invoke-PoshQCTest` replays one line beginning
`Tests Passed: ` carrying the passed, failed, skipped, inconclusive, and not-run counts. On a failing
run Pester exits inside the run and that replayed line is not printed; failing-run counts come from
Form B instead.

**This plan runs no unscoped Pester invocation and states no acceptance condition over one.** A
consecutively clean unscoped run is unsatisfiable in this worktree for two independently verified
pre-existing reasons: one failure in `tests/scripts/claude-hooks/enforce-pr-author-skill.Tests.ps1`
and one in `tests/scripts/codex-hooks/codex-pretooluse-integration.Tests.ps1`, the latter produced by
`enforce-epic-wave-barrier.ps1` reading the ambient epic checkpoint, which currently records issue 596
itself as carrying unmerged `depends_on` edges. Scanning the whole `tests/scripts/claude-hooks`
directory is likewise prohibited, because the pr-author suite lives in it.

**Form B — Pester result-file extraction.**

`pwsh -NoProfile -Command '[xml]$junit = Get-Content -LiteralPath "artifacts/pester/pester-junit.xml" -Raw; $root = $junit.SelectSingleNode("/*"); "root={0} tests={1} failures={2}" -f $root.Name, $root.GetAttribute("tests"), $root.GetAttribute("failures"); $junit.SelectNodes("//testcase[failure]") | ForEach-Object { $_.name }'`

**The JUnit file is written when a run ends through Pester's failure exit.** This was open when this
plan was drafted and is now settled on two independent grounds. First, Pester 5.6.1 registers the
TestResult writer as the `End` step of a plugin (`Get-TestResultPlugin`), and `Invoke-Pester` runs
every `End` plugin step before it reaches `exit $failedCount`; the only path that exits without
writing is the `catch` branch that exits `-1` on a Pester-internal error, which is not the
test-failure path. Second, the completed plan already observed it: the [P7-T5] artifact
`docs/features/active/2026-08-29-batch-budget-state-portability-596/evidence/qa-gates/powershell-test-coverage-final.2026-08-29T16-05.md`
records that after a run exiting 2 with two failures, `artifacts/pester/pester-junit.xml` was present
and parsed, and states that the blocked branch was not taken.

Every task that uses Form B after an expected-failing run nonetheless retains the blocked branch, now
as a guard against the internal-error path rather than as an open question: if the file is absent,
record `BLOCKED: Pester result file not produced by the failing run`, keep the verbatim Form A
console output as the evidence of record, and report to the orchestrator. Taking that branch is a
signal that the run failed inside Pester rather than in a test, so it is reported rather than
absorbed.

**Form C — per-file coverage extraction.**

`pwsh -NoProfile -Command '[xml]$report = Get-Content -LiteralPath "artifacts/pester/powershell-coverage.xml" -Raw; foreach ($leaf in @(".claude/hooks/enforce-powershell-batch-budget.ps1", ".claude/hooks/enforce-python-batch-budget.ps1")) { foreach ($pkg in @($report.report.package)) { foreach ($sf in @($pkg.sourcefile)) { $full = ($pkg.name + "/" + $sf.name).Replace("\", "/"); if ($full.EndsWith("/" + $leaf)) { $c = @($sf.counter) | Where-Object { $_.type -eq "LINE" }; "{0} LINE covered={1} missed={2}" -f $leaf, $c.covered, $c.missed } } } }'`

registered in `CodeCoverage.Path`. Percentage derivation, computed independently per file:
`LINE percent = 100 * covered / (covered + missed)`, recorded to one decimal place.
