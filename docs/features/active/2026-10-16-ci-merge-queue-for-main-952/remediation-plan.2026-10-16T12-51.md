**MCP observation rule (fixed).** A PoshQC MCP result carries only a pre-composed summary string and no count, finding, test name or coverage value. The observables of the call itself are: (1) call disposition — the call returned (record `EXIT_CODE: 0`, `Disposition: RETURNED`) or the call raised (record `EXIT_CODE: 1`, `Disposition: RAISED`, and the error text verbatim); and (2) for `run_poshqc_format`, the tree comparison `git status --porcelain -- <the scan folders of the call>` recorded immediately before and after the call. No acceptance condition reads a count, percentage, finding or test name from an MCP result. The JUnit file that a `run_poshqc_test` call writes is a separate observable governed by the JUnit file rule below. **JUnit file rule.** A `run_poshqc_test` call writes JUnit XML to `WORKTREE_ROOT/artifacts/pester/pester-junit.xml`: the MCP tool runs the bundled template `extensions/drm-copilot/resources/templates/run-poshqc-test.ps1`, which imports the bundled PoshQC module and calls `Invoke-PoshQCTest` with no settings path (`:22-32`); the bundled settings enable JUnit output at `artifacts/pester/pester-junit.xml` (`extensions/drm-copilot/resources/powershell/PoshQC/settings/pester.runsettings.psd1:12-16`) and set `Run.Exit = $true` (`:2-5`), so the file is written before a run with failing tests exits non-zero; the module resolves the relative path against the workspace root (`extensions/drm-copilot/resources/powershell/PoshQC/PoshQC.Testing.psm1:193-207`). The path is gitignored (`.gitignore:6`, `/artifacts`), so it is read with the Read and Grep tools, never with `git grep`. Each `testsuite` element carries a `name` attribute holding the absolute suite path, and each `testcase` element carries `name` (the Describe, Context and It names joined by `.`), `status` (`Passed` or `Failed`) and `classname` (the absolute suite path) on one line (observed by the planner in an existing `WORKTREE_ROOT/artifacts/pester/pester-junit.xml` from an earlier MCP run). Freshness: the file is fresh for a call only when, read after that call, (F1) every line matching `<testsuite name=` contains the call's scan folder text (for example `codex-hooks`), and (F2) it contains the freshness testcase the task names, a testcase that exists only after the edit the task follows. A file that fails F1 or F2 is `JUnitFreshness: STALE` and is not used. The failing set of a fresh file is every `testcase` line matching `status="Failed"`, plus every `testsuite` line whose `errors` attribute is not `"0"` (a container-level error, listed by suite path); a suite whose only non-zero count is `failures` contributes only its failed testcases. Artifacts record suite paths repository-relative (the text after `WORKTREE_ROOT`), never the absolute path.
