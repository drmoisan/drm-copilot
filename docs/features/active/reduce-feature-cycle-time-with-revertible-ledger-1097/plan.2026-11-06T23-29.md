## Design

**Key.** `review_mode` is a top-level checkpoint key. Only the exact string `concurrent` activates anything, compared ordinally in every runtime. Absent, null, `sequential`, `Concurrent`, a number, and any other non-string value all mean sequential: no guard, no relaxation, no `gh` call. A PowerShell reader tests `-is [string]` first, because `-ceq` on an array filters rather than compares. The guard and the readiness relaxation share this predicate, so neither can act without the other.

**Review record.** `remediation_loop.review_outcomes[]` entries gain `head_sha`: the head the review ran against, read by the orchestrator from the pushed branch before the delegation. It is a full lowercase object id of 40 or 64 characters. Last-entry semantics: only the final list element counts, so an earlier `PASS` never satisfies the guard, and a K7 synthetic `REMEDIATION_REQUIRED` entry denies the merge.

**Guard decision**, `Get-EpicMergeGateReviewDecision`, evaluated in this order; the first match ends it. Deny reasons read `EPIC_MERGE_GATE_BLOCKED: <code>: <message>`.

| Step | Condition | Result |
| --- | --- | --- |
| 1 | Checkpoint absent, or key not exactly `concurrent` | Inert: no process, no denial |
| 2 | Bare command (no PR number) | `REVIEW_GATE_HEAD_UNRESOLVED`, before any process |
| 3 | No last entry, last entry not an object, or `verdict` not exactly `PASS` | `REVIEW_GATE_NOT_PASSED`, before any process |
| 4 | `head_sha` absent or malformed | `REVIEW_GATE_NOT_PASSED`, before any process |
| 5 | The one bounded `gh pr view <PR> --json headRefOid` fails or is malformed | `REVIEW_GATE_HEAD_UNRESOLVED` |
| 6 | `head_sha` equals the live head | Pass |
| 7 | `git merge-base --is-ancestor <reviewed> <live>` exits 1 | `REVIEW_GATE_HEAD_STALE` |
| 8 | That command exits anything other than 0 or 1 | `REVIEW_GATE_HEAD_UNRESOLVED` |
| 9 | `feature-folder` is not a clean path below `docs/features/` (blank, absolute, backslash, dot segment, trailing slash) | `REVIEW_GATE_HEAD_UNRESOLVED` |
| 10 | `git diff --name-only -z --no-renames --no-color --no-ext-diff --no-relative <reviewed> <live>` fails, or its non-empty output does not end with NUL | `REVIEW_GATE_HEAD_UNRESOLVED` |
| 11 | Any listed path does not start with `<feature-folder>/` (ordinal) | `REVIEW_GATE_HEAD_STALE`, naming the path |
| 12 | Otherwise, including an empty listing | Pass |

Any code change after the review is stale, including a merge of `origin/main`, because that diff lists code paths. A sibling folder whose name extends the feature folder does not match, because the prefix carries the separator. `feature-folder` must be a clean path below `docs/features/` so that a value such as `.` cannot widen the rule. The hook never fetches: a head not present locally fails step 7 or 8 and denies.

**Binding.** The guard applies to whichever checkpoint its gate hands it, with no binding exemption. An explicit PR number that the checkpoint does not bind therefore fails at the head comparison. Exempting an unbound number would open a bypass on Codex, whose child branch requires no PR binding.

**One file, two runtimes.** `enforce-epic-merge-gate-review.ps1` is byte-identical at `.claude/hooks` and `.codex/hooks`, like `enforce-epic-merge-gate-command.ps1`. It defines functions only, dot-sources nothing, imports nothing, and calls `Invoke-DocsOnlyGhExe` and `Invoke-DocsOnlyGitExe` at run time. Premise correction: research section 6 says the guard reuses `Get-EpicMergeGateLivePrHeadSha`, but that function lives in the Claude-only green-CI sibling. The guard therefore has its own seam, `Get-EpicMergeGateReviewLiveHeadSha`, and its own `Test-EpicMergeGateReviewObjectId`.

**Placement.** Claude: in `Invoke-EpicMergeGateDecision`, right after the `$childCheckpoint` read and before branch 1, with `gh` in `$sessionRoot` and git in `$childRoot`. Codex: in `Invoke-CodexEpicMergeDecision`, right after `$child` is parsed and before `Test-CodexChildMergeReady`, with both in `$RepositoryRoot`. On the Claude green-CI path under the key, the guard's lookup and the stage D lookup are two bounded calls; the guard itself makes one. The worst case stays within the time limit recorded in `hook-docs-only-diff.ps1`.

**Limits (D10).** The guard is policy-level, not a security control. A same-session writer can edit the checkpoint. A merge outside the Bash hook surface is not gated. A merge whose item target does not resolve (`NoTarget` or `Ambiguous`), or whose child checkpoint does not parse, sees no key; the parallel skill step is then the only backstop. A push after the lookup can change the head unless the command passes `--match-head-commit`. The `CI full run` requirement of the join is skill-level, because a docs-only head passes `CI Required Gate`. The sibling header and the rule section state these limits.

**Validators.** Readiness under the key stops rejecting `step7_status` only for the value `pending`: `blocked`, and every other step, keep today's result. TypeScript has no readiness port. `require_complete` under the key appends exactly one of these strings, byte-identical in Python, TypeScript, and PowerShell, after the existing completion checks:

- `Checkpoint completion validation failed: review_mode concurrent requires a last review_outcomes entry with verdict PASS.`
- `Checkpoint completion validation failed: review_mode concurrent requires head_sha on the last review_outcomes entry.`

The second is reported only when the first does not apply. Validators do no git work, so head currency stays with the guard. Plain validation ignores both keys. Under D9 the TypeScript rule reaches the MCP surface only after a release. Until then, installed MCP accepts a checkpoint that the PowerShell stop hook and the Python CLI reject, so the skill names the Python CLI route.

**Skill section.** All orchestrate wording is one new section placed immediately before `## PR Creation Gate`, so it gives one contiguous revert block per copy, cannot collide with stage B, and leaves every sequential sentence byte-identical. The section heading is `## Concurrent Review and CI (review_mode)`. It states:

1. New-run default: the first checkpoint write of a new run records `review_mode: "concurrent"` when the route opens a PR and the target worktree holds the guard sibling. Without the sibling the run stays sequential, because a skill newer than its hooks would otherwise stop at readiness.
2. Resume: a run that resumes a checkpoint without the key stays sequential, and the key is never added on resume. A sequential run follows every other section unchanged.
3. Sequence: the local parallel run passes, commit (the pre-review commit steps of the section that names them run here, before the PR), open the PR, run review and CI together, join, merge.
4. Recording: `head_sha` on every `review_outcomes[]` entry, read before the review delegation.
5. Join: last entry `PASS` at a current head; `ci_gate.conclusion` `success` at the live head; a `CI full run` check with conclusion `success` at the reviewed head, or at an ancestor of it whose diff to the reviewed head lists only `feature-folder` paths. The head rule is the guard's rule. A docs-only head reports success without the heavy suites.
6. Moved conditions: PR Creation Gate conditions 1 and 2 apply at the join. S9 steps 6 and 7, and DONE, run only after the join. A parallel child still never merges itself.
7. Re-entry: any code push after a `PASS`, including a CI fix or a merge of `origin/main`, requires a new review and a new S9 pass. Commits inside the feature folder, such as review artifacts and stage-timing evidence, do not. Ledger back-fills are outside the feature folder and land before the review starts (K8).
8. Portable handoff: the destination projection is a closed key set and drops `review_mode`, so a concurrent run is not handed off between PR creation and the join.
9. Validator route under D9 and the deny codes.
10. Step order: `completed_steps` stays in canonical order, because `enforce-checkpoint-monotonic.ps1` denies a checkpoint Write that lists `S8_create_pr` before `S7_feature_review`. When the review completes, `S7_feature_review` is inserted before the existing `S8_create_pr` entry, not appended. A later review adds no second entry. `step8_status` is `in_progress` at PR creation, because readiness rejects `pending`, and it stays `in_progress` until the join, because `enforce-completion-consistency.ps1` reads `completed` there as a completion claim and denies a checkpoint Write whose `ci_gate.conclusion` is not `success`. A `completed` value would therefore deny the `ci_gate` write of every re-entry.
