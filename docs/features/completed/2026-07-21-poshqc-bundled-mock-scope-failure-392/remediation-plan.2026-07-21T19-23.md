## Background (verified by reading exact source; cite before assuming)

Read directly from the installed Pester 5.6.1 module the suite actually loads
(`C:\Users\DanMoisan\OneDrive\Documents\PowerShell\Modules\Pester\5.6.1\Pester.psm1`), the same file the
revision-1/original research artifact cited:

- `Pester.psm1:8556-8662` (`Get-CoveragePlugin`): the `RunStart` plugin phase calls `Enter-CoverageAnalysis`
  **exactly once per `Invoke-Pester` invocation**, before any test container (and therefore before any test
  file's `BeforeAll`) executes.
- `Pester.psm1:8780-8868` (`Enter-CoverageAnalysis`): sets one `Set-PSBreakpoint -Script <file> -Line <n>
  -Column <n>` per command position, derived from `Get-CoverageBreakpoints` / `Get-CommandsInFile`
  (`Pester.psm1:9037-9093`), which performs its **own independent** `[System.Management.Automation.Language.Parser]::ParseFile($Path)`
  of each coverage-tracked file — entirely separate from whatever `PoshQC.psm1` does to load its submodules.
  `UseSingleHitBreakpoints` defaults to `$true` (`PesterPreference.CodeCoverage.SingleHitBreakpoints`), so each
  breakpoint's action removes itself (`Remove-PSBreakpoint -Id $_.Id`) the first time it is hit.
- `Pester.psm1:9390-9397` (`Get-CoverageMissedCommands` / `Get-CoverageHitCommands`): covered vs. missed is
  decided purely from `$_.Breakpoint.HitCount -eq/-gt 0` on the **same** breakpoint-wrapper objects captured
  once at `RunStart`; no new breakpoints are registered mid-run.
- `Pester.psm1:8664-8708` (`RunEnd` / `End`): `Exit-CoverageAnalysis` and the final JaCoCo/CoverageGutters
  report both read from that same one-time `CommandCoverage` list.

Consequence: coverage bookkeeping is, at the Pester script level, a single, stable, file/line/column-keyed
structure established before any `BeforeAll` runs. The regression the revision-1 executor found (a later
file's already-covered lines losing credit after an earlier file becomes a new caller of the same function)
therefore cannot be explained by anything visible in Pester's own PowerShell-level coverage logic — it must
arise from how the compiled PowerShell engine associates a running script's execution position with the
breakpoint set for its file path, interacting with `PoshQC.psm1`'s bootstrap loop
(`scripts/powershell/PoshQC/PoshQC.psm1:82-106`) re-parsing and re-dot-sourcing a **fresh**
`[Parser]::ParseFile(...).GetScriptBlock()` for `PoshQC.Testing.psm1` on every `Import-Module -Force` — a call
every test file's `BeforeAll` makes unconditionally. That association lives inside compiled
`System.Management.Automation` internals, not in any readable PowerShell source, so it cannot be confirmed by
reading text alone. **This is a hypothesis to be tested empirically in Phase 0, not an established fact.**

Corollary from the original cycle-1 baseline itself: the existing 8-file suite, with its existing
`Import-Module -Force`-per-`BeforeAll` convention and existing cross-file calls, was stable at 149/195 covered
with no observed regression before this remediation's Phase 1 additions. This means repeated reimport alone
(the pre-existing pattern) is not sufficient to cause loss; loss was observed only after a **new** earlier-file
caller was introduced into a function whose other lines were exercised by the always-last-sorting
`PoshQC.Tests.ps1`. Phase 0 below does not re-litigate that already-established point; it focuses on
discriminating between fix candidates.
