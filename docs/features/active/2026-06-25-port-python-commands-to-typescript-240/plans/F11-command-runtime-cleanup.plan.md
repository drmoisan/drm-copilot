## Scope and Constraints

F11 removes the now-dead Python bridge and the bundled Python resources from the extension and the standalone MCP server. After F2–F10 merged, every one of the 12 in-scope commands is wired to in-process TypeScript; no `RepoAutomationService` method still spawns Python. F11 deletes the remaining Python-spawn surface so that no `python` interpreter is required to execute any extension or MCP command (AC-E3/AC-E4).

This feature is delicate because the repository's own Python CI (GitHub Actions "Code Quality & Tests" on Python 3.10–3.13) must remain green. The Python source under `scripts/dev_tools/**` and its tests under `tests/scripts/dev_tools/**` are repo-internal dev tooling and STAY. Only the BUNDLED Python copies shipped inside the extension package and the tests that assert those bundled copies are removed.

### helloPython decision (recorded for the executor): PORT IN-PROCESS (option a)

Per the task directive, prefer preserving the command surface unless removal is clearly cleaner. Decision: PORT `hello_python.py` to a trivial in-process TypeScript message that preserves the `drmCopilotExtension.helloPython` command ID and its observable output (`artifacts/hello_python.txt` containing `hello_python:ok\n`), and remove the Python spawn. Rationale: this keeps the `package.json` command contribution, the registered disposable, and the documented command surface stable (no removal of a public command ID), while eliminating the last `runtimeKind: "python"` spawn path required by AC-E4. The in-process write uses the injected `FileSystem` (F1 `src/lib/file-system.ts`) and the resolved workspace root, consistent with the F4 `collect_commit_context` precedent. The `package.json` `commands` contribution and the README "Hello Python" entry are kept; only the implementation changes from a Python spawn to an in-process write.
