# Research: worktree agents inherit the main checkout's virtual environment (#1127)

Scope: evaluate the proposed PreToolUse hook plus execution-environment section. No implementation. Facts marked "orchestrator-verified" were supplied and not re-derived. Everything else was read from the tree. "Not verified" marks items the plan must confirm because this role has no shell.

## Orchestrator-verified facts
- With `VIRTUAL_ENV` set to a venv outside the worktree, Poetry 2.5.1 `env info -p` reports that venv, so `poetry install` writes into it. With it unset, the tracked `poetry.toml` (`[virtualenvs] in-project = true`) yields `<worktree>/.venv`.
- `env -u VIRTUAL_ENV poetry -C <worktree> install` builds a worktree-local `.venv` and leaves the main checkout's `.pth` entries unchanged. A bare `poetry run` with no `.venv` creates an empty one.
- `VIRTUAL_ENV` comes from the user's shell before Claude Code starts. The `CLAUDE_ENV_FILE` channel of `.claude/hooks/persist-session-id.ps1` was not observed to take effect, so it is not a fix channel.
- No skill, agent, or script tells agents how to bootstrap Python in a worktree.

- Command parsing: do not use regexes over raw text. `.claude/hooks/hook-command-scanner.ps1` and `hook-command-invocation.ps1` provide `Test-CommandLineInvocation -CommandText -CommandWord -SubcommandPath` and `Resolve-CommandLineInvocationTarget`, which parse command words structurally, so quoted prose is not matched (issue #545). This directly addresses the over-matching risk. Constraints found:
  - `$script:CommandLineGlobalOptions` models only `git` and `gh`; an unmodeled dash-leading token between the command word and subcommand classifies the segment Indeterminate (fail-closed). `poetry -C <dir> install` therefore needs a `poetry` entry (`WithArgument = -C, --directory, -P, --project`, plus `-n`, `-q`, `-v` standalone), which edits a shared helper that has `.codex/hooks/` twins and bundle copies.
  - `$script:CommandLineTransparentWrapperNames` = `command`, `env`, `nohup`, `time`, `timeout`. Not verified: whether `env -u VIRTUAL_ENV poetry install` is unwrapped (the `-u NAME` arity) and whether `unset VIRTUAL_ENV; poetry install` is recognized; the neutralization check may need its own token pass over the same segment.

## Candidate approaches
1. Hook plus skill section (proposed). Deterministic, fails before a write to the shared venv, matches the `enforce-*` precedent. Cost: eight to ten mirrored files, shared-helper edit for Poetry options.
2. Skill text only. Cheap, but prior ad hoc `env -u VIRTUAL_ENV` use shows agents do not retain it; no enforcement; rejected as the sole fix.
3. Hook that rewrites the command (prefix `env -u VIRTUAL_ENV`). PreToolUse here is allow/deny only in every existing hook; rejected.
4. Session-level unset via `CLAUDE_ENV_FILE`. Observed not to work; rejected.

Recommendation: approach 1, with the hook scoped to Claude first and the Codex twin as an explicit parity decision recorded in the plan (Codex agents inherit the same `VIRTUAL_ENV`).

## Behavior semantics and risks (question g)
- Deny only when all hold: an in-scope Poetry invocation (`install`, `sync`, `add`, `remove`, `update`, structurally parsed); `VIRTUAL_ENV` non-empty; its path not contained in the resolved target project directory; no neutralization in the same command segment.
- `VIRTUAL_ENV` unset or empty: allow. `VIRTUAL_ENV` equal to the target's own `.venv` (main checkout, or a worktree that already activated its own venv): allow; containment check is path-prefix with separator boundary, after normalizing `\`, `/c/...` to `C:/...`, trailing slash, and case on Windows. A sibling like `.venv-old` must not count as contained.
- Target directory precedence: `-C`/`--directory`/`-P`/`--project` over a leading `cd <dir>` over payload `cwd`. A relative `-C` resolves against `cwd`. If the target cannot be derived (variable, substitution), choose and test one direction explicitly; fail-open is consistent with "policy-level control" framing in the brief, fail-closed is consistent with the structural-parser Indeterminate handling. Record the choice in the spec.
- Over-matching: only structural invocation counts (Test-CommandLineInvocation), so `git commit -m "poetry install"` and `echo 'poetry install'` are allowed. Compound lines (`cd x && poetry install`) need segment-level handling, and `poetry run`, `poetry env info`, `poetry check`, and `poetry show` stay allowed. Note `poetry run` can create an empty `.venv` when none exists but does not write into the foreign venv; it is out of scope for the deny, and the skill text should say so.
- `poetry install` in the main checkout with its own `VIRTUAL_ENV` set is the common legitimate case; it must pass.
- A Poetry variant `POETRY_VIRTUALENVS_IN_PROJECT`/`POETRY_VIRTUALENVS_CREATE` environment settings could change resolution; out of scope, noted.
- Reason text must not contain the denied-command text in a form a sibling hook re-matches.
