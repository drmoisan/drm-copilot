## Normative Context

### Evidence conventions

- All evidence artifacts are written under `docs/features/active/2026-08-17-reject-unfalsifiable-acceptance-gates-in-atomic-plans-486/evidence/<kind>/`. Valid kinds: `baseline`, `regression-testing`, `qa-gates`, `issue-updates`, `other`.
- `<ts>` in every evidence filename below is the ISO-8601 `yyyy-MM-ddTHH-mm` capture time of that command.
- Every command-step evidence artifact records `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`.
- Baseline and final-QC test artifacts record numeric coverage percentages, never placeholders.

### Acceptance-command discipline (this plan dogfoods its own subject matter)

- Coverage assertions use the dotted-module form only, for example `--cov=scripts.dev_tools.plan_gate_discrimination`. The path forms `--cov=scripts/dev_tools/x.py` and `--cov=scripts/dev_tools/x` collect no data and are prohibited in this plan.
- Acceptance conditions are expressed as named tests that cannot pass before the change and do pass after it, or as commands whose recorded output differs between the two states.
- Where a search is used, it asserts a short, single-line, non-interpolated token that this plan quotes verbatim.

### Toolchain commands

- Python: `poetry run black`, `poetry run ruff`, `poetry run pyright`, `poetry run pytest`.
- TypeScript: run from `extensions/drm-copilot` using `npx prettier`, `npx eslint`, `npx tsc`, and `node run-jest.cjs`.

### Scope boundaries (binding)

- The expected-exit-code declaration requirement is out of scope. The extractor is still authored as a reusable module returning `{ task_id, source_line, raw_span, argv, kind }` so the later feature can attach to it.
- `.claude/hooks/validate-planner-output.ps1` is not modified.
- No new MCP `artifact_type`, no new MCP flag, no MCP input-schema property change.
- G6 ships as a Warning. The word-count wrap heuristic is not shipped.
- G5's severity is fixed by the corpus measurement in Phase 5 and by nothing else.

### Module layout (500-line ceiling)

`scripts/dev_tools/validate_orchestration_artifacts.py` is 398 lines and `extensions/drm-copilot/src/lib/validate/orchestration-artifacts.ts` is 284 lines, so the new logic lands in new sibling modules in each runtime:

- Python: `scripts/dev_tools/plan_gate_commands.py` (extractor) and `scripts/dev_tools/plan_gate_discrimination.py` (context, rules, report; re-exports `extract_plan_commands` so the spec's public surface is a single module).
- TypeScript: `extensions/drm-copilot/src/lib/validate/plan-gate-commands.ts` and `extensions/drm-copilot/src/lib/validate/plan-gate-discrimination.ts` (re-exports `extractPlanCommands`).

### Import direction (no cycles)

`validate_orchestration_artifacts.py` imports `plan_gate_discrimination.py`, which imports `plan_gate_commands.py`. The extractor therefore never imports the validator: it declares its own task-line and heading patterns, and a parity test (P10-T7) asserts the declared task pattern is textually identical to `PLAN_TASK_RE` in the validator. The same direction and the same parity test apply on the TypeScript side (`orchestration-artifacts.ts` → `plan-gate-discrimination.ts` → `plan-gate-commands.ts`).

### Deferred-verification convention

Some implementation tasks state their acceptance as a named test that a later task in the same phase creates. Every such task carries the clause "verified when `[P#-T#]` completes; this task is checked off only after that task passes", naming the task that creates the test. No task names a test that no task in this plan creates.
