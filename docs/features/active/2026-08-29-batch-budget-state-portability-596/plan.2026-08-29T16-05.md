## Toolchain command forms

`atomic-executor` carries the Bash permission patterns `Bash(poetry run pytest *)`,
`Bash(npx prettier *)`, `Bash(npx eslint *)`, `Bash(npx tsc *)`, `Bash(npx jest *)`, `Bash(pwsh *)`,
`Bash(git *)`, and the four PoshQC MCP tools. It carries **no `npm` and no `node`**. Membership of
those patterns in the allowlist is what has been verified; whether a given command text matches a
pattern at call time, and whether the named binaries are runnable in the executing worktree, are
separate questions that [P0-T1] and [P0-T2] settle empirically before any other TypeScript task runs.

Every TypeScript command in this plan is written as a single compound command of the exact form
`cd extensions/drm-copilot && npx <tool> <args>`. The `cd` is part of the command rather than a
separate step because each Bash tool call starts in the repository root and does not inherit a working
directory from a previous call, so a bare `npx` would resolve `jest.config.cjs`, `tsconfig.json`, and
the local binaries against the wrong directory. Tasks below state the full compound command and do not
repeat this rationale.

`extensions/drm-copilot/run-jest.cjs` is a wrapper that injects `--config jest.config.cjs` and rejects
`--passWithNoTests`, `--onlyChanged`, and `--lastCommit` (its `PROHIBITED_FLAGS` list is on line 9),
because each of those converts zero discovered tests into a green run (issue #423). `npx jest` bypasses
that wrapper, so **those three flags are prohibited in every command in this plan** and must not be
added by the executor. `npx jest` run from `extensions/drm-copilot` resolves `jest.config.cjs` through
Jest's default config lookup, so the effective configuration is the same one the wrapper injects.

## PowerShell runner selection and evidence sources

PowerShell format and lint run through `mcp__drm-copilot__run_poshqc_format` and
`mcp__drm-copilot__run_poshqc_analyze`. There is no PowerShell type-check stage. Pester measures
instruction (command) and line coverage only, so the line threshold of 85 percent applies and no
branch-coverage gate applies.

**How `EXIT_CODE:` is derived for a PoshQC MCP task.** The PoshQC MCP tools return a structured result
object, not a process exit code. Its fields are `ok`, `tool`, `workspace_root`, `summary`, and — on
failure only — `stderr_excerpt` (`extensions/drm-copilot/src/mcp-tools.ts:60-73` and `:90-129`). A
non-zero exit of the spawned `pwsh` process is converted into a `CommandExecutionError` whose message
is `Command exited with code <N>.` (`extensions/drm-copilot/src/command-runtime.ts:60-85` and
`:244-264`), which the MCP layer projects onto `ok: false` with that message in `summary`. Therefore:
record `EXIT_CODE: 0` when the result carries `ok: true`; record `EXIT_CODE: <N>` taken from the
`Command exited with code <N>.` message when it carries `ok: false`; and quote `summary` and, when
present, `stderr_excerpt` verbatim in both cases so the derivation is auditable.

**What a PoshQC MCP result does not carry.** On `ok: true` the `summary` field is a canned sentence
built from a fixed template — for `run_poshqc_test` it is `Ran bundled PoshQC test against '<root>'.`
(`extensions/drm-copilot/src/repo-automation-service-support.ts:48-53`) — and no Pester counts, no `It`
names, no analyzer output, and no process stdout are returned at all. Every task in this plan that must
read a test count or a test name therefore uses Form A and Form B below instead of the MCP runner. The
MCP runner is retained only where a pass/fail signal alone is the evidence.

**Why an `ok: true` analyze result is a falsifiable zero-findings claim.** `Invoke-PoshQCAnalyze` raises
`PSScriptAnalyzer reported N issue(s).` whenever its result set is non-empty
(`scripts/powershell/PoshQC/PoshQC.Analyzer.psm1:181-184`), and the bundled entry script sets
`$ErrorActionPreference = "Stop"` (`extensions/drm-copilot/resources/templates/run-poshqc-analyze.ps1:14`),
so any finding terminates the process with a non-zero code and the MCP result is `ok: false`. An
`ok: true` analyze result therefore entails zero findings, and a single finding falsifies it.

**Form A — self-hosted Pester run.** The command shape is
`pwsh -NoProfile -Command "Import-Module ./scripts/powershell/PoshQC/PoshQC.psd1 -Force; Invoke-PoshQCTest -Root (Get-Location).Path -SettingsPath 'scripts/powershell/PoshQC/settings/pester.runsettings.psd1'"`,
with `-ScanFolders '<suite path>'` appended when the run is scoped to one suite. `Run.Exit = $true`
(`scripts/powershell/PoshQC/settings/pester.runsettings.psd1:4`) makes Pester terminate the process with
a non-zero exit code when the run has failures, so the process exit code of a Form A run is a real
pass/fail signal. On a completing run `Invoke-PoshQCTest` replays one line beginning `Tests Passed: `
carrying the passed, failed, skipped, inconclusive, and not-run counts
(`scripts/powershell/PoshQC/PoshQC.Testing.psm1:423-428` and `:453-461`). On a failing run Pester exits
inside the run, so that replayed line is not printed; failing-run counts are read from Form B instead.
Form A is also used for the coverage-bearing runs because
`mcp__drm-copilot__run_poshqc_test` resolves its Pester settings from the installed extension rather
than either in-repo copy, so only a self-hosted invocation reads this repository's own settings file.

**Form B — Pester result-file extraction.** The command is
`pwsh -NoProfile -Command '[xml]$junit = Get-Content -LiteralPath "artifacts/pester/pester-junit.xml" -Raw; $root = $junit.SelectSingleNode("/*"); "root={0} tests={1} failures={2}" -f $root.Name, $root.GetAttribute("tests"), $root.GetAttribute("failures"); $junit.SelectNodes("//testcase[failure]") | ForEach-Object { $_.name }'`.
The settings enable a JUnit result file at `artifacts/pester/pester-junit.xml`
(`scripts/powershell/PoshQC/settings/pester.runsettings.psd1:12-16`). This plan does **not** assert that
the file is written when a run ends through Pester's failure exit; that ordering was not observed.
Every task that uses Form B after an expected-failing run therefore carries an explicit blocked branch:
if the file is absent, the task records `BLOCKED: Pester result file not produced by the failing run`,
records the Form A console output verbatim instead, and reports to the orchestrator. After a passing
run no such branch is needed, because the run returns normally and the file is written before
`Invoke-PoshQCTest` prints its replayed summary.

**Form C — per-file coverage extraction.** The command is
`pwsh -NoProfile -Command '[xml]$report = Get-Content -LiteralPath "artifacts/pester/powershell-coverage.xml" -Raw; $rootLine = @($report.report.counter) | Where-Object { $_.type -eq "LINE" }; "REPO LINE covered={0} missed={1}" -f $rootLine.covered, $rootLine.missed; foreach ($leaf in @(".claude/hooks/enforce-powershell-batch-budget.ps1", ".claude/hooks/enforce-python-batch-budget.ps1", ".claude/hooks/persist-session-id.ps1")) { foreach ($pkg in @($report.report.package)) { foreach ($sf in @($pkg.sourcefile)) { $full = ($pkg.name + "/" + $sf.name).Replace("\", "/"); if ($full.EndsWith("/" + $leaf)) { $c = @($sf.counter) | Where-Object { $_.type -eq "LINE" }; "{0} LINE covered={1} missed={2}" -f $leaf, $c.covered, $c.missed } } } }'`.

Three properties of that command are load-bearing and are fixed here so the executor selects nothing.

- The `package` element's `name` attribute carries a path rooted at the executing worktree, not a bare
  directory name. `Convert-PoshQCCoverageToRelative` exists precisely to strip that absolute prefix
  from a separate copy of the file (`scripts/powershell/PoshQC/PoshQC.Testing.psm1:107-115`), so a
  match on a bare directory name is wrong and a match on a bare `sourcefile` name is wrong.
- Form C matches on the concatenation of `package/@name`, a forward slash, and `sourcefile/@name`,
  normalized to forward slashes, ending with the full three-segment suffix. The concatenation is used
  rather than either attribute alone because the split between the two attributes differs between
  Pester's JaCoCo and CoverageGutters output formats, and this settings file selects CoverageGutters
  (`scripts/powershell/PoshQC/settings/pester.runsettings.psd1:21`); the suffix test on the
  concatenation is correct under either split.
- The suffix includes the `.claude/` segment because `enforce-powershell-batch-budget.ps1` and
  `enforce-python-batch-budget.ps1` each exist under both `.claude/hooks` and `.codex/hooks`, and both
  directories are registered in `CodeCoverage.Path` (lines 30-31 and 127-128 of that settings file), so
  the bare filenames collide.

Percentage derivation, computed independently for the report root and for each of the three files:
`LINE percent = 100 * covered / (covered + missed)`, recorded to one decimal place. Pester emits no
branch counter for PowerShell, so no branch figure is recorded and no branch gate applies.

All three in-scope hooks are already registered in `CodeCoverage.Path` of
`scripts/powershell/PoshQC/settings/pester.runsettings.psd1`: `.claude/hooks/enforce-python-batch-budget.ps1`
(line 30), `.claude/hooks/enforce-powershell-batch-budget.ps1` (line 31), and
`.claude/hooks/persist-session-id.ps1` (line 79). No registration task is required.

`quality-tiers.yml` does not exist at the repository root; a repository-wide glob for
`**/quality-tiers.y*ml` returns no files. No task in this plan reads it. The uniform thresholds apply
regardless of tier.

## Change-budget sequencing obligation (this will bind)

`.claude/rules/powershell.md:40` caps a batch at 3 production PowerShell files and 3 test PowerShell
files. Six production `.ps1` files are in scope — three repository hooks plus their three bundle
mirrors — and none matches the hook's test-file predicate, so all six count against the production cap.
Three test `.ps1` files are in scope, exactly at the test cap. **The hook being repaired is the hook
that enforces this cap.**

The plan handles it by splitting the production edits across three phases of two production files each
and resetting the batch-budget state at the head of each of those phases, and again at the head of
Phase 7 and on every iteration of the Phase 7 restart loop. The reset is a glob-based removal rather
than a fixed filename removal, because once Phase 2 lands the session-identity fix the composed
state-file name is no longer `powershell-batch-budget.default.json`.

`.claude/state/` is gitignored (`.gitignore:68`). Its contents cause the known issue #510 failure in
`tests/scripts/dev_tools/test_push_down_claude_resource_contracts.py`, which is recorded in the spec's
Non-Goals. **No task in this plan edits that test file.**

Merge semantics: the function normalizes CRLF and lone CR to LF; locates the managed block by its

managed entry set inside the block even when one of those entries also appears outside it, because
suppression would make the output depend on unmanaged content and would produce two different fixed
points, whereas a duplicate ignore pattern is inert to git. An empty input string is a valid input
representing an absent destination file.
