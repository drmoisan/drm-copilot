## Design

**Installed MCP outcome (D9).** Settled by observation at planning time. The installed `danmoisan.drm-copilot-1.1.22` folder holds no text `remediation_path`. A `validate_orchestration_artifacts` call with `artifact_type: "orchestrator-state"` on `tests/fixtures/orchestrator_state_remediation_loop_backcompat/violation_execution_before_clear_preflight.json` returned `ok: false` with the invariant 2 string. A cycle with no `preflight` object takes the same branch. So installed MCP rejects a truthful light cycle with `Checkpoint remediation cycle #N execution_status is X but preflight.final_status is not 'clear'.` The consequence differs by runtime:

| Runtime | What reads the checkpoint | Outcome |
| --- | --- | --- |
| Claude | `### Model-choice reconciliation on resume` and `## PR Authoring (pr-author Handoff)` name MCP or the repository-local validator CLI. `## Completion Requirements` is the stop hook, which uses the PowerShell module, not MCP. | **A light cycle can complete under the installed release.** The checkpoint is validated through the Python CLI. The required route tool is satisfied by the existing receipt: `_mcp_tools` counts `tool`, `ok`, and `evidence` and is not bound to an artifact type, and `### mcp_call_receipts[]` gives "plan validator exit 0" as its example, so the plan validation that precedes every review is a truthful receipt. A failed MCP checkpoint call records no receipt. |
| Codex | `## Hard Enforcement Boundary` requires MCP with `require_complete` and states there is no fallback. | **The light path is unavailable until a release carrying invariant 8 is installed.** The orchestrator moves every cycle heavier, which the spec permits. |
| Parallel parent | Validates `parallel-orchestrator-state` only, which holds no child cycles. | Unaffected. A Claude child follows the Claude row. |

No checkpoint is reshaped to look like a full cycle. **Detection is one rule on both runtimes**, needing no version parsing. As the last step before the light execution delegation, the orchestrator records the cycle truthfully (`plan_path` naming the inputs file, `remediation_path: "light"`, `opened_by_review`, `execution_status: "in_progress"`, no `preflight`) and validates the checkpoint through its route: on Claude the Python CLI `poetry run python -m scripts.dev_tools.validate_orchestration_artifacts orchestrator-state <path>` run in the item worktree (MCP where the repository has no such CLI, because a pushed skill arrives with a release that carries the rule), and on Codex `validate_orchestration_artifacts`. An error naming that cycle means the route lacks invariant 8, either from installed MCP or from an item branch that predates this reduction. The orchestrator then removes `execution_status`, sets `remediation_path: "full"`, writes the mode line as `Remediation-Mode: proportionate` or `Remediation-Mode: design`, and continues at R1, after which `plan_path` names the remediation plan. No fix work has run at that point, so the record stays true. [P1-T4] proves both route results on the corpus row.

**Validators.** Invariant 2 keeps its code and gains one condition in each `per-cycle` check: it does not run when `remediation_path` is exactly the string `light`, compared ordinally (`_validate_remediation_cycle`, `validateRemediationCycle`, `Get-RemediationCycleError`; PowerShell tests `-is [string]` first). Invariant 8 needs `review_outcomes`, so it runs in the accounting stage, after the R7 checks, at the end of `_validate_remediation_accounting`, `validateRemediationAccounting`, and `Get-OrchestratorStateRemediationAccountingError`. Absent `remediation_path` reaches neither branch, so every existing rule is byte-identical. `scope` is read only by invariant 8, so a `scope` on a full cycle is tolerated and unvalidated.

Per cycle whose key is present, in this order, with strings byte-identical in all three runtimes and no rendered checkpoint value, so no display helper can diverge:

1. Value not exactly `light` or `full` (including null): `Checkpoint remediation cycle #N remediation_path must be light or full.` Nothing further runs for the cycle. For `full`, nothing further runs either.
2. Key `preflight` present, whatever its value: `Checkpoint remediation cycle #N remediation_path is light but the cycle carries preflight.`
3. `opened_by_review` absent, or not naming a `REMEDIATION_REQUIRED` outcome by the R11 predicate: `Checkpoint remediation cycle #N remediation_path is light but opened_by_review does not name its opening review.` Rules 4 to 6 are skipped.
4. More than 3 findings: `Checkpoint remediation cycle #N remediation_path is light but its opening review has M findings; the limit is 3.` A `findings` value that is not a list counts as empty; R9b reports it.
5. Per finding K, in order, when `remediability` is not exactly `autonomous` (a non-object finding included): `Checkpoint remediation cycle #N remediation_path is light but finding #K is not autonomous.`
6. Per finding K, when `scope` is not exactly `contained` (absent included): `Checkpoint remediation cycle #N remediation_path is light but finding #K scope is not contained.`
7. The immediately prior list element is an object whose `remediation_path` is exactly `light`: `Checkpoint remediation cycle #N remediation_path is light but the prior cycle is light.`

Python and TypeScript hold this in new pure modules, `validate_light_cycles(cycle_list, outcomes, opens_review)` and `validateLightCycles(cycleList, outcomes, opensReview)`. The third parameter receives the existing private R11 predicate, so no import cycle arises and no predicate is duplicated. PowerShell adds the private `Get-RemediationLightCycleError` to the existing accounting module, which avoids a manifest, closure, and pin change, as stage C did.

**Review contract.** `feature-review` writes one line `Remediation-Path: light` or `Remediation-Path: full`, and in each blocking finding block one line `Finding-Scope: contained` or `Finding-Scope: design`. These lines never carry the substrings the orchestrator counts. A missing path line reads as `full`; a missing scope line reads as `design`. `Remediation-Path: light` is allowed only when all of the spec threshold holds: at most 3 blocking findings, every one `autonomous`; no change to a spec acceptance criterion, a public interface, or the file inventory beyond the branch diff plus tests and mirrors; no change to a validator contract, hook decision, or production logic beyond the finding's named location; a review-opened cycle; and a prior cycle that was not light. With that line the reviewer also writes `## Light Fix Tasks`, one canonical `- [ ] [P0-T1] ...` line per fix, numbered in order, with the file and the finding, and no checkbox line anywhere else in the file. On Claude a light review creates no remediation plan target. On Codex and Copilot the plan target stays, because their review contracts require it.

**Orchestrator rule.** `Remediation-Mode:` stays orchestrator-owned. It writes `Remediation-Mode: light` only when the reviewer wrote `Remediation-Path: light`, and every mechanically checkable condition holds: the count, the classes, each `Finding-Scope: contained`, a non-empty `## Light Fix Tasks`, no other checkbox line, `opened_by_review` set, a prior cycle not light, and the detection rule passes. Otherwise it writes `proportionate` or `design` by the existing rule. It may move a cycle heavier and never lighter. CI-failure and merge-conflict cycles are never light. Each `findings[]` entry records `scope` from its `Finding-Scope:` line when present. New cycles record `remediation_path` as `light` or `full`.

**Light cycle.** R1 and R2 do not run. R3 is one `atomic-executor` delegation with the inputs file as its plan and no preflight directive. The pre-R4 commit, R4, R5, cycle accounting, and the termination guard are the existing ones, unchanged. `candidate_applied` and `completed_attempts` follow `Cycle accounting`. The cycle after a light cycle is full. An executor stop before the first checked task rewrites the mode line to `Remediation-Mode: design`, sets `remediation_path: "full"`, removes `execution_status`, and enters the design chain at R1; `plan_path` then names the remediation plan, and the cycle truthfully is a full one from that point. No attempt number is consumed.

**Executor stop hook, confirmed by reading `Get-ExecutorOutputBlockDecision`; no hook edit.** Completion needs an advertised `plan-path` to an existing file, at least one checkbox, all ticked, `AC Status Summary`, command and status evidence, and a PASS or FAIL line for each language named by a path in the file; no remediation-plan name is required. The file's checkbox test counts every checkbox line, which is why the section must be the only source of them: a search found no checkbox line in any committed `remediation-inputs.*.md` under `docs/features/active/`. A stop is allowed when `Test-IsPreflightRun` is false, the output carries `BLOCKED at preflight (before [P0-T1])` and a plan delta, and no `[P#-T#]` task is ticked. The transcript's delegation prompt decides the run kind, so the absence of the directive makes it an execution run. The executor agent text permits blocking only during preflight, so `.claude/agents/atomic-executor.md` and `.codex/agents/atomic-executor.toml` gain one sentence permitting the same stop in a light run.

**Pins.** `test_single_pass_preflight_contracts.py` `test_remediation_surfaces_define_remediation_mode` requires the two mode lines on six surfaces: unchanged, because those literals stay on every surface and the test checks presence only. `Remediation-Mode: light` is pinned by the new Pester contract suite, not by a new Python test, under the rule that Python changes only for validator parity. The handoff skill, the Codex prompt, and the `.github` surfaces keep two modes and stay correct: a planner runs only after the mode line is `proportionate` or `design`, and those runtimes never write `light`.

**Deferred wording (K3, K6).** `atomic-plan-contract` `### Single-Pass Preflight`, which names proportionate cycles, and the `execution-environment` brief wait for stage E. Entry `0002-light-remediation.md` says so in `## Files Changed` now, and the commit that lands the wording updates the entry.
