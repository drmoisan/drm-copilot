## Detailed Notes

### Cycle 2 verification

- `Get-PoshQCShardSlice` (`PoshQC.Shard.psm1:20-74`): the sort uses a `System.Comparison[int]` over positions with weight descending and `[string]::CompareOrdinal` ascending, which is a total order for distinct paths, so the unstable `Array.Sort` yields a deterministic result. The greedy loop picks the least load, then the fewest files, then the lowest index. Results are emitted in input order. With `-Weight` omitted, every weight is 1 and the assignment reduces to round-robin in ordinal path order; SH01 and SH03 inputs are already in ordinal order, so their expectations are unchanged.
- `Select-PoshQCShardTestFile` (`PoshQC.Shard.psm1:234-256`): a string weighs 1; an object with a `Length` property uses that value. The empty-slice check runs before the manifest write, so TS05 can assert that no manifest is written. The function is not listed in `FunctionsToExport`; it is reachable from `Invoke-PoshQCTest` because the sub-module loader dot-sources it into module scope.
- `Invoke-PoshQCTest` (`PoshQC.Testing.psm1:411-414`): the shard block is one call; `Run.Path` receives `[string[]]` full paths. Changed line 413 has `ci=3` in the final local artifact.
- `Merge-PoshQCCoverageReport` (`PoshQC.CoverageMerge.psm1:90-94`): the XPath `//class | //counter[@type!='LINE' and @type!='INSTRUCTION']` removes class subtrees (including their `method` children and nested counters) and the report-, package-, and sourcefile-level METHOD and CLASS counters. `sourcefile` elements and their `line` children are untouched, so the LINE recomputation is unaffected (CM08 asserts 2 sourcefiles and LINE `3/1`). `Convert-PoshQCCoverageToRelative` rewrites path text only, and `validate-feature-review-coverage-metrics.ps1` reads LINE counters only, so no repository consumer loses data it uses.
- `_poshqc.yml`: `${{ strategy.job-total }}` is valid inside a matrix job's step; actionlint is clean (`r2-final-actionlint.2026-10-16T16-52.md`). The merge step reads `shardCount` from shard 1's manifest after `Test-PoshQCShardCompleteness` has already required every manifest to declare a count equal to the number of manifests, so a missing or inconsistent shard fails the earlier step.

### Test quality

- WF03 builds its mutations from the committed text and asserts both that each mutation changes the text and that the helper reports it. This guards the WF02 helper against becoming vacuous.
- TS04 asserts the literal path, a UTF-8 encoding (`[string] $Encoding -match '(?i)utf-?8'`), and the parsed JSON `selected` list. The `InModuleScope` wrapper ensures the mock and the default seam bind to the same module instance in a full-suite run, which was the cause of the CI shard 1 failure at `1f208b4e5`.
- The fail-before evidence shows exactly the nine expected cases failing; the four cases that pass on the pre-fix tree by design (WF01 to WF03, TS04) are covered by the exception dossier with absence-of-test and mutation proofs.

### API compatibility

- `-Weight` is optional on both public functions; callers that omit it receive a deterministic round-robin in ordinal path order. That order can differ from the previous positional round-robin when the input is not already in ordinal order; both shard and merge sides compute the same assignment, and no external consumer persists shard assignments, so this is not a breaking change in practice.
- The six exports and the `Invoke-PoshQCTest` shard parameters are unchanged in signature from the previous round apart from `-Weight`.
