## Design

- Evidence document, written by the orchestrator main session and read by the report: a JSON object with `issue-num` (a string of decimal digits) and `stage_timing` (a list). Each entry has `stage` (non-blank string), `attempt` (integer, 1 or more), `started_at` (ISO-8601 UTC string), and `ended_at` (ISO-8601 UTC string, or null while the stage is open). The checkpoint key holds the same list.
- Writer protocol: at each transition where the orchestrator already rewrites `last_updated`, it reads the clock once, sets that reading as `last_updated`, as `ended_at` of the open entry, and as `started_at` of the entry for the next stage; `attempt` is one more than the number of earlier entries for the same stage. It never composes a time. In its last commit before the merge it writes `FEATURE/evidence/other/stage-timing.<timestamp>.json` (UTC write time, `yyyy-MM-ddTHH-mm`) holding the whole list, inside the feature folder, so the commit does not stale a concurrent review. A re-written file carries a newer stamp, and the report uses the greatest stamp per issue.
- Portable handoff carriage, traced for this plan: the source checkpoint is archived byte for byte and bound by its SHA-256 (`validate_provenance_bytes`), so a source checkpoint that carries `stage_timing` keeps it in the archive. The destination projection (`ClaudeToCodexAdapter.project` and `CodexToClaudeAdapter.project` in `scripts/dev_tools/orchestration_handoff_adapters.py`) is a closed set of keys and copies no unknown key, so the destination checkpoint starts without `stage_timing`. The committed evidence file is therefore the record that spans a handoff. The documentation states this, and [P2-T2] pins both facts.
- Report: per issue and stage, the total of closed durations and the attempt count; per stage, the median across issues of those per-issue totals. Open entries are counted and excluded from totals. Stage order is the order of the earliest `started_at` across all issues, ties by ordinal comparison, because ordinal order would place `S10` before `S5`.
- Labels, exact: "Figures are wall-clock time and include queueing; they are not agent time." and "The merge stage is not captured."

## Open Questions / Notes

These are design choices this plan makes where the spec is silent. A reviewer should confirm them.

- The evidence file holds `issue-num` and the whole list, and the report uses the greatest stamp per issue, so a re-written file replaces an older one. The spec does not say how repeated writes combine.
- The per-stage median is taken over per-issue stage totals, so a stage with two attempts in one issue counts once for that issue.
- Handoff carriage: `stage_timing` survives only inside the archived source checkpoint, and the destination projection starts without it. The plan documents and pins that behavior and does not change the adapters. If the owner wants the key carried into the destination checkpoint, that is a handoff-contract change outside stage B.
- The Codex base `.codex/agents/orchestrator.toml` is not edited, to avoid regenerating its variants for a Claude-persona sentence it does not contain. The `.agents` orchestrate skill carries the Codex-facing text.
- Whether the orchestrator of this item's own run writes a stage-timing file is outside this plan; the report prints its labels on an empty tree, and a test covers that.
