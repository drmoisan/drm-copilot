## Q5. Parity and unresolved references

- Proposed corpus: `tests/fixtures/epic_wave/wave-computation-cases.json` with `cases[]` of `{name, manifest: {folder: [deps]}, expected_waves | expected_error: {kind: "cycle"|"unresolved", ...}}` for: empty, single, chain, diamond, multiple roots, two-node cycle, self-loop, unresolved reference. Python lane `tests/scripts/dev_tools/test_epic_wave_corpus_parity.py` and Pester lane `tests/scripts/claude-lib/epic-wave/EpicWave.Parity.Tests.ps1` both read it (committed file, no temp files). The existing seven inline Python tests stay unchanged.
- Existing tests asserting unknown dependencies get wave 0: grep of `test_*epic*.py` for "unresolved|unknown dep" finds none for `compute_wave_numbers`; `test_epic_wave_computation.py` has no such case. Unresolved handling elsewhere: `validate_epic_planner_state.py` rejects `features[N].depends_on contains unresolved reference` before calling `compute_wave_numbers`, pinned by `test_validate_epic_planner_state_feature_indices.py` (`UNRESOLVED_DEPENDENCY_ERROR`). So callers already guard; the bare function is the only place that silently yields wave 0. The TS `computeWaveNumbers` has the same `?? []` behavior; no TS test for it was examined.
- Recommended: enforce unresolved rejection in the PowerShell port (new behavior the skills already claim), and leave the Python/TS reference functions untouched. Do not add the corpus unresolved case to the Python lane's must-return list; mark that case `pwsh_only: true`, or have the Python lane assert the planner-state validator's error instead. Rationale: changing `compute_wave_numbers` to raise could not break any asserted behavior found, but it touches a function used by `validate_epic_planner_state.py` and widens the diff in a bug with concurrent edits. If the owner wants Python parity, add an `EpicWaveUnresolvedReferenceError` there afterwards.
