## 2. Candidate Approaches

### Python split and combine
- A (recommended): in-repo PowerShell helper that reuses `PoshQC.Shard.psm1`. A thin script under `scripts/ci/` enumerates `tests/**/test_*.py` in ordinal order, weights them, and calls `New-PoshQCShardManifest` or `Select-PoshQCShardTestFile`. Advantages: the LPT algorithm, manifest shape, `Test-PoshQCShardCompleteness`, and `Test-PoshQCShardTestCount` already exist with Pester tests; there is no new Python and no new dependency; PowerShell is preinstalled on ubuntu-latest. Limits: needs a small new script and Pester tests, and the module must load on Linux (it uses only .NET and core cmdlets).
- B (rejected): `pytest-split` or `pytest-shard`. It adds a dependency, the split is at test-id level (changes within-file ordering, so the "every file exactly once" guarantee is not a file-level contract), and `pytest-split` needs a durations file generated by a run. Not clearly simpler than A, and the issue says to avoid it.
- C (rejected): `pytest --collect-only` plus a bash `awk` splitter. It pays a collection pass in every shard and needs a second algorithm that duplicates the existing LPT.

### Job layout and context stability
- Layout A (recommended): move 3.13 out of the `quality-checks7` matrix into three jobs, so the legacy context stays meaningful.
  - `python-static-313` (name e.g. `Python 3.13 static`): checkout, setup, Poetry, lock check, black, ruff, pyright, Codex check, tier check. It runs in parallel with the shards.
  - `python-coverage-shard` (name `Python 3.13 coverage shard ${{ matrix.shard }}`, matrix `shard: [1, 2]`, `fail-fast: false`, `-ShardCount ${{ strategy.job-total }}`).
  - A combine job with the explicit `name: Code Quality & Tests (3.13)`, `needs: [python-static-313, python-coverage-shard]`, `if: always()`. Its first step is the poshqc-style "Require the static and shard jobs to succeed". Its context is exactly `quality-checks7 / Code Quality & Tests (3.13)`, because the caller job id is `quality-checks7` and the context is built from the job `name`.
  - `quality-checks7` keeps its job id, so the matrix becomes `["3.11", "3.12"]` and the contexts `(3.11)` and `(3.12)` are unchanged.
- Layout B: keep the three-value matrix and make the 3.13 leg static-only, with new unrequired shard and combine jobs. This keeps the matrix literal, but a legacy ruleset that still requires the `(3.13)` context would pass without tests; only `CI Required Gate` would catch a shard failure. Choose B only if the ruleset is confirmed to require only `CI Required Gate` (VERIFY with `gh api repos/drmoisan/drm-copilot/rulesets/15241672`).
- Reason for A over B: the issue asks that the required gate stay blocking and the 3.13 context name stay stable, and A satisfies both with the existing poshqc pattern. The cost is one test edit (section 5).

## 3. Recommended Design

### 3.1 PowerShell (6 shards)
- Edit `_poshqc.yml` only: `shard: [1, 2, 3, 4, 5, 6]`. `strategy.job-total` and the aggregator loops follow the matrix. The weights file is not edited (an unlisted new test file weighs the median, existing behavior).
- Rebalance check: after the change, regenerate `config/poshqc-shard-weights.json` only if the shard timings show more than about 20% spread. A single 189 s file does not block 6-way balance.
- No `ci.yml` change: `ci-required-gate` needs only the caller job `poshqc`.
- Contexts: `poshqc / PowerShell QC shard 4`, `shard 5`, `shard 6` are new. They are skipped at job level on a docs-only run (matrix names never expand), like shards 1-3.

### 3.2 Python (2 shards)
1. Helper `scripts/ci/Select-PythonTestShard.ps1` (new, PowerShell). It imports `scripts/powershell/PoshQC/PoshQC.Shard.psm1`, enumerates `tests/**/test_*.py` under the repository root, and sorts by `[string]::CompareOrdinal` on root-relative forward-slash paths. Weights are the LF-normalized byte size, which `Get-PoshQCShardTestFileWeight` already computes for a FileInfo item. A later optional step is a measured-weights file such as `config/pytest-shard-weights.json` in the existing schema, passed through the existing `-ReadWeightsText` seam, so the module needs no edit and its three mirror copies stay unchanged. It writes `artifacts/python/shard-files.json` (the `New-PoshQCShardManifest` shape) and a `shard-files.txt` list of this shard's files.
2. Shard job steps: setup as in the current job (checkout, setup-python 3.13, Poetry 2.5.1, venv cache, install), run the helper, then in `shell: bash`:
   `mapfile -t files < artifacts/python/shard-files.txt` then `poetry run pytest -n auto --cov --cov-branch --junitxml=artifacts/python/junit-shard-${{ matrix.shard }}.xml "${files[@]}"`, with `env: COVERAGE_FILE: artifacts/python/coverage-shard-${{ matrix.shard }}.data`. No `--cov-report=xml` or `json` per shard (the combine job produces both). The addopts lcov report is still written per shard and is unused.
   Upload (`if: always()`) of the `.data` file, the JUnit file, and `shard-files.json` as `python-coverage-shard-${{ matrix.shard }}`.
3. Combine job: gated steps (each `if: ${{ inputs.run-heavy }}`), then checkout, setup, Poetry, cache, install (needed so `coverage` and the source tree exist and the `source` list resolves). Download with `pattern: python-coverage-shard-*`. Then:
   - Completeness (file level): load the manifests and call `Test-PoshQCShardCompleteness`. It throws on a missing or duplicated file.
   - Completeness (test level): `poetry run pytest --collect-only -q tests` (no `-n`, nothing is run, so it is not a serial test run) yields the discovery count. `Test-PoshQCShardTestCount` compares it with the sum of the `tests` attributes of the shard JUnit files. This is the analog of the existing Pester discovery check.
   - `poetry run coverage combine artifacts/python/coverage-shard-1.data artifacts/python/coverage-shard-2.data`, which uses the `data_file` of `[tool.coverage.run]`, then `poetry run coverage xml -o coverage.xml` and `poetry run coverage json -o artifacts/python/coverage.json`. These report the same `source` set and `exclude_lines` as the pytest-cov report.
   - The unchanged `Enforce Python coverage thresholds` step (`--min-line 85 --min-branch 75`) and the unchanged `Upload coverage to Codecov` step (`files: ./coverage.xml`, flag `unittests`).
4. Why `COVERAGE_FILE` and not `.coverage.*`: `actions/upload-artifact` v4 and later skips hidden files (names starting with `.`) unless `include-hidden-files: true`. Naming the per-shard data without a leading dot avoids the issue. VERIFY in the first CI run that the `COVERAGE_FILE` environment value overrides `data_file` under pytest-cov with xdist; the fallback is `include-hidden-files: true` on the upload.
5. Cross-job path validity: coverage data holds absolute paths. All jobs run on ubuntu-latest and check out to the same workspace path, so `coverage combine` needs no remapping. `relative_files = true` plus `[tool.coverage.paths]` is a hardening option, but it changes the local report shape and is not needed; do not add it unless VERIFY shows path mismatches.
6. Skipped and docs-only behavior: the shard and static jobs use job-level `if: ${{ inputs.run-heavy }}`; the combine job uses `if: always()` and gates every step on `inputs.run-heavy`, so on a docs-only run the `(3.13)` context still reports success. This is the pattern `CiChangeScopeWorkflow.Tests.ps1` already tests for `poshqc`.
7. Timing estimate (not measured): shards about 6.8 min of tests plus about 1.5 min setup; combine about 1.2 min setup plus collect-only and combine. The result is close to the 11-minute target. Design the count from `strategy.job-total` so a third shard is a matrix edit if the measured run exceeds the target. Also measure `-n 4` against `-n auto` (the existing test allows `auto` or `4`), because `-n auto` can start fewer workers than vCPUs.

### 3.3 Required gate and contexts
- `CI Required Gate` needs only the caller job ids, so it is unchanged. A shard failure fails the caller `quality-checks7`/`poshqc` and the combine job's require-step, so the gate stays red.
- New contexts (unrequired, shown only): `poshqc / PowerShell QC shard 4` to `6`, `quality-checks7 / Python 3.13 coverage shard 1` and `2`, `quality-checks7 / Python 3.13 static`. The context `quality-checks7 / Code Quality & Tests (3.13)` stays as the combine job.

## 4. Behavior Semantics
- Success: every `tests/**/test_*.py` appears in exactly one shard's `selected`; shard JUnit test counts sum to the collect-only count; combined coverage meets 85% line and 75% branch; the combine job is green.
- Failure: any shard failing makes its job red, the combine job's require-step exits 1, and the aggregator result gates the context. A missing or duplicated file makes `Test-PoshQCShardCompleteness` throw. A count mismatch makes `Test-PoshQCShardTestCount` throw.
- Determinism: ordinal sort plus LPT with a fixed tie-break gives the same split on every runner. The size weight normalizes CRLF to LF, so the checkout line endings do not change the assignment.
- Edge: a shard that selects no file throws (existing behavior of `Select-PoshQCShardTestFile`); a test collected outside `tests/` is not run by either layout.

## 7. Trade-offs (runner contention)
- PowerShell: 3 more windows-latest jobs per run, each with about 30 s of checkout and tool install, so total windows minutes rise by roughly the setup overhead while wall-clock falls.
- Python: from 3 jobs to 6 (static, two shards, combine, plus 3.11 and 3.12), with about 1.5 min setup each. Total runner minutes rise by roughly 5-6 minutes while wall-clock falls.
- Concurrent PR runs compete for the account's concurrent-job limit; the plan tier is not known from the repo (VERIFY). More jobs per run lengthen the queue wait when several PRs run CI at once, which is the effect the issue already reports.
