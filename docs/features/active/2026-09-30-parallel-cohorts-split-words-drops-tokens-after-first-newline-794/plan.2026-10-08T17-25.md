**Scope statement:** Fix `pcoh_split_words` in `.claude/lib/bash/parallel-cohorts.sh` so newline, CR, VT, and FF in a `--keys` or `--edges` value separate tokens, in the same way #609 fixed `pla_parse_edges`. The defect: `read -ra PCOH_WORDS <<<"${1-}"` consumes one newline-terminated record, so every token after the first newline is dropped without a diagnostic and never validated, and CR, VT, and FF are not in the default IFS. The fix is one parameter expansion in front of the existing `read -ra` plus a comment update.

**Spec gap found while planning (companion fix, recorded not hidden; accepted by the orchestrator):** the spec states that a fix inside `pcoh_split_words` covers every call site. The call-site list is correct, but `pcoh_build_adjacency` in `.claude/lib/bash/parallel-cohorts.sh` also tests endpoint membership with `pc_contains_word "$keys" "$first"` and `pc_contains_word "$keys" "$second"` (lines 145 and 149) against the raw `$keys` string, and `pc_contains_word` in `.claude/lib/bash/parallel-common.sh` (lines 223-230) matches the pattern space, word, space. A `--keys` value whose tokens are separated by newline, tab, CR, VT, or FF therefore fails that membership test even after `pcoh_split_words` is fixed, and `--keys` plus `--edges` supplied together as multi-line values would still exit 1 with a false "not a member of item_keys" message. The plan adds one two-statement normalization in `pcoh_build_adjacency` (P2-T3) that rebuilds the membership haystack from the already-split tokens. The orchestrator accepted this companion fix (P2-T3) and its spec-gap note (P2-T4) as written. It touches no file outside the spec's write set, it is covered by the new rows `separator-parity: newline-separated --keys and --edges together match the single-line control` and `separator-parity: the sourced library accepts multi-line keys and edges`, and the gap is written to `evidence/other/spec-gap-note.2026-10-08T21-25.md` (P2-T4). `spec.md` is not edited except for acceptance-criterion check-offs.

# Helpers for the separator rows below. Each asserts exit status 0 and the exact
# stdout, so a multi-separator value is compared with its single-line control.
cohorts_print() {
    run bash "$COHORTS" --keys "$2" --edges "$3"
    [ "$status:$output" = "0:$1" ] || { printf 'expected 0:%s but got %s:%s\n' "$1" "$status" "$output"; return 1; }
}

batches_print() {
    run bash "$BATCHES" --keys "$2" --max-concurrency 2
    [ "$status:$output" = "0:$1" ] || { printf 'expected 0:%s but got %s:%s\n' "$1" "$status" "$output"; return 1; }
}

@test "separator-parity: a newline-separated --keys value matches the single-line control" {
    cohorts_print "[[1,2,3]]" "1 2 3" ""
    cohorts_print "[[1,2,3]]" $'1\n2\n3' ""
}

@test "separator-parity: a newline-separated batching --keys value matches the single-line control" {
    batches_print "[[1,2],[3]]" "1 2 3"
    batches_print "[[1,2],[3]]" $'1\n2\n3'
}

@test "separator-parity: a newline-separated --edges value honors an edge after the first newline" {
    cohorts_print "[[1,3],[2]]" "1 2 3" "1:2"
    cohorts_print "[[2],[1,3]]" "1 2 3" "1:2 2:3"
    cohorts_print "[[2],[1,3]]" "1 2 3" $'1:2\n2:3'
}

@test "separator-parity: newline-separated --keys and --edges together match the single-line control" {
    cohorts_print "[[2],[1,3]]" $'1\n2\n3' $'1:2\n2:3'
}

@test "separator-parity: a tab-separated value matches the single-line control" {
    cohorts_print "[[2],[1,3]]" $'1\t2\t3' "1:2 2:3"

    cohorts_print "[[2],[1,3]]" $'1\t2\t3' $'1:2\t2:3'

}

@test "separator-parity: a CR-separated value matches the single-line control" {

    [ "${PCOH_WORDS[0]}" = "*" ]

}
