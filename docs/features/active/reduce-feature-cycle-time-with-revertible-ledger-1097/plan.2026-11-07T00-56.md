## Design

**Key.** `features[].early_start` on the dependent, in the shape of research section 8: `dependency`, `upstream_branch`, `interface_settled_at`, `interface_evidence`, `synced_at`. A record is valid only when it is an object under the exact key `early_start`, `dependency` is a non-empty string or a number (never a boolean), and the other three named fields are non-empty strings (length above zero, no trimming, because the runtimes disagree on whitespace). An invalid record is the same as no key: no exemption and no new message. `dependency` resolves through each layer's existing reference index, and the exemption covers only the edge that resolves to the same feature. Every other edge runs today's code.

**Back-compat.** No checkpoint written before this stage carries the key, so every older epic checkpoint, including any epic still running, takes today's path in both layers with byte-identical results. The proof is that `tests/fixtures/epic_wave_barrier/layer2-parity-edge-cases.json`, `tests/fixtures/epic_wave_barrier/start-guard-matrix.json`, and every existing suite that reads them stay unedited, pass, and keep their [P0-T2] to [P0-T4] test counts.

**Layer 2** (`validate_wave_barrier_ordering`, `validateWaveBarrierOrdering`, `Get-EpicWaveBarrierViolation`). Before the edge loop each started feature computes its exempt folder, null without a valid record. The exempt edge skips both existing checks, because an early-started dependent always has a `worktree_created_at` before the upstream's `merge_confirmed_at`, and takes this table instead:

| Dependent `merge_status` | Upstream `merge_status` | `synced_at` | Result |
| --- | --- | --- | --- |
| `not_started` or `worktree_created` | any | any | No error |
| anything else, including absent and non-string | not `merged` or `worktree_removed` | any | Message A |
| anything else | `merged` or `worktree_removed` | not a non-empty string | Message B |
| anything else | `merged` or `worktree_removed` | non-empty string | No error |

An absent or unknown dependent status counts as `pr_open` or later, the fail-closed rule of `feature_has_started`. One error per edge; `{f}` and `{d}` render as the existing messages render them. Byte-identical in three runtimes:

- A: `EPIC_WAVE_BARRIER_VIOLATION: {f} is at pr_open or later while early_start dependency {d} is not merged`
- B: `EPIC_WAVE_BARRIER_VIOLATION: {f} is at pr_open or later without a string synced_at for early_start dependency {d}`

The validators compare no timestamps on this edge; the ancestry check of procedure step 9 proves the sync.

**Layer 1.** No denial text changes. New pure sibling `epic-wave-barrier-early-start.ps1`, byte-identical at `.claude/hooks` and `.codex/hooks`, that defines functions only and dot-sources and imports nothing. `Get-EpicWaveEarlyStartReference -Feature` returns `dependency` of a valid record, or null. `Test-EpicWaveEarlyStartEdge -ExemptRecord -DependencyRecord` is true only when both are non-null, their `feature_folder` values are non-empty and equal (ordinal), and the upstream `merge_status` is one of `worktree_created`, `pr_open`, `ci_green`, `merge_conflict`. `ConvertFrom-Json` turns an ISO-8601 string into `[datetime]`, so `interface_settled_at` is accepted as a non-empty string or a `[datetime]`; the key test uses `-ccontains` because `PSObject.Properties` ignores case; records are compared by `feature_folder`, not identity. A merged upstream makes the predicate false and today's merged check passes the edge. Gate edits are insertions only: `Test-EpicWaveBarrierDependenciesMerged` computes the exempt record through `Find-FeatureFolderRecord` before its loop and skips the edge, right after the record null check, when the predicate is true; `Test-CodexWaveDependenciesReady` does the same through `Find-CodexWaveFeature`, whose key is the basename or issue number, so a lifecycle-prefixed `dependency` finds no record on Codex and fails closed.

**Opt-in.** A merged skill edit reaches running epics, so nothing reads as a new default. A feature opts in only through a new manifest field `early_start_on: <upstream issue_num>`, which must be one of its `depends_on` values; `epic.md` is human-authored and `epic_wave_computation.py` takes a parsed `depends_on` mapping, so no parser rejects the field. No committed manifest carries it. The new skill section opens by stating that without this field the section does not apply and every other section governs unchanged. No existing sentence of any skill or agent file is edited.

**Who records what.**

| Value | Writer | Source |
| --- | --- | --- |
| `early_start` on the epic feature, with `interface_settled_at` and `interface_evidence` | `epic-orchestrator`, the only writer of `features[]` | The manifest field and the evidence file on the pushed upstream branch |
| `<upstream FEATURE>/evidence/other/interface-settled.<timestamp>.md` with `Timestamp:`, `Upstream-Head:`, `Interface-Paths:` | The upstream child (a plan task, otherwise its `orchestrator` after S5), asked by a prompt line only when a dependent names that upstream | The pushed upstream head and repository-relative paths |
| `early_start_synced_at`, a tolerated top-level key of the child checkpoint | The child, reading the clock | Procedure step 8 |
| `early_start.synced_at` on the epic feature | `epic-orchestrator`, in the write that moves the feature to `pr_open` or later | The child key, after the ancestry check |

The bounded child return keeps its eight fields; the parent reads the child key from the checkpoint under `worktree_path`.

**Procedure**, stated once as `## Early Dependent Starts (early_start)`, before `## Worktree Cleanup` in the Claude skill and before `## Fan-In and Conflict Handling` in the `.agents` skill. Parent: (1) while an armed dependent waits, look for the evidence file on `origin/<upstream_branch>` every 30 seconds for at most 90 minutes, else keep the barrier; (2) write `early_start`, `merge_status: "worktree_created"`, and `worktree_created_at`, then validate through the D9 route (Claude: `poetry run python -m scripts.dev_tools.validate_orchestration_artifacts epic-orchestrator-state <path>`; Codex: installed MCP). An `EPIC_WAVE_BARRIER_VIOLATION` naming the feature means the route lacks the rule (installed MCP, or an integration branch older than this reduction), so the parent removes the three values and keeps the barrier; the same fallback applies when the sibling is absent or layer 1 denies; (3) launch with the literal `Epic mode: true` line plus `Early start: true. dependency: <dep_issue_num>. upstream_branch: <branch>. interface_evidence: <path>. Run the child procedure of ## Early Dependent Starts (early_start) before S7 and S8.`, and the dependency's line `Upstream context for <issue_num>: early start on <dep_issue_num> (spec: <path>; plan: <path>; upstream_branch: <branch>; not merged).` Child: (4) branch from `origin/<integration_branch>`, then `git fetch origin <upstream_branch>` and `git merge --no-ff origin/<upstream_branch>` before the first plan task; (5) after S6, wait for the upstream merge (`gh pr list --head <upstream_branch> --base <integration_branch> --state merged --json number,mergeCommit`, every 30 seconds for at most 90 minutes, then `git merge-base --is-ancestor <merge commit> origin/<integration_branch>`), else stop with `blocked_reason: "policy_hold"`; (6) `git diff --name-only <Upstream-Head> <merge commit> -- <Interface-Paths>`; any path stops the child with `blocked_reason: "premise_falsified"`, unsynced and with no PR; (7) `git merge --no-ff origin/<integration_branch>`, a conflict entering `## Merge-Conflict Handling (Fan-In)` (in the `.agents` skill, `## Fan-In and Conflict Handling`); (8) re-run the local gate, commit, push, record `early_start_synced_at`, and only then start S7 or S8. Parent: (9) before the `pr_open` write, check `git merge-base --is-ancestor <upstream merge_commit_sha> origin/<child branch>`; write `synced_at` only when it passes and the child key exists, otherwise layer 2 reports message B; (10) after a stop in step 5 or 6, read the diff against the child's plan; when no task cites a changed symbol or the stop was the wait bound, record fresh `interface_settled_at` and `interface_evidence` and delegate once more on a branch `<child branch>-r<n>` from the pushed child branch, resuming at step 5; otherwise the edge stops with `premise_falsified`. `early_start` stays recorded, because removing it from a started feature would turn a truthful record into a barrier violation.

**Chain rule for derived created paths ([P2-T3]).** `Invoke-ProcessReductionPatchStep` skips every path that `Get-ProcessReductionDerivedSource` reports as derived, because revert step 2 re-creates a derived copy from its source. When the patch also creates the source, the source is absent at that step, so the copy is absent too. The fix: for a derived path whose hunk group holds a create hunk, the step sets the state absent and records the touch with an empty pre-image, with no comparison against the hunk text; modify and delete hunks on derived paths stay skipped. No create hunk of entries `0001` to `0009` lies on a derived path, so their results cannot change.

## Open Questions / Notes

- The opt-in is a new manifest field, `early_start_on`; without a human-authored source a running epic could adopt the behavior from the skill alone.
- Installed MCP rejects a truthful early start, and the rejection persists after the upstream merges, so on Claude the feature uses the Python CLI route and the agent gains a `Bash` grant; on Codex it is unavailable until a release. An owner who wants no grant can take the unavailable rule on both runtimes.
- The child waits inside its run, by the 30-second, 90-minute bound of merge confirmation; the stop values `policy_hold` and `premise_falsified` need no new vocabulary member.
- "Interface changed" is defined by paths, not symbols, so a harmless edit can stop the child; step 10 then clears it.
- `synced_at` is proved by the parent's ancestry check; the validators test only that it is a non-empty string, so a child that opens its PR early is caught at the parent's stop, not prevented.
- Layer 1 refuses an early start on a `not_started` or halted upstream, which is narrower than research section 8, because such an upstream has no usable branch.
- A Codex wave launches whole, so one member lacking both a merged dependency and a valid record holds the wave; relaxing that is a launcher change outside this stage.
- Spec D10 and owner condition 3 are unaffected: no merge gate is touched.
