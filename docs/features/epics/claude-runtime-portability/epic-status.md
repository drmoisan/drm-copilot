## Blocking Defect: PR Gate Resolves Artifacts Against the Wrong Working Directory

`enforce-pr-author-skill.ps1` declares its two gate inputs as **relative** paths (lines 48-49):

```powershell
$script:PrContextArtifactPath = 'artifacts/pr_context.summary.txt'
$script:OrchestratorStateCheckpointPath = 'artifacts/orchestration/orchestrator-state.json'
```

Both are consumed through `Test-Path` with no workspace-root parameter and no environment
override, so they resolve against the hook process's working directory — the Claude Code session
root, which a `cd` inside the Bash command string does not change. Any orchestration whose
PR-creating agent does not share a working directory with its own artifacts is therefore gated
against the wrong feature's evidence.

Feature 596 hit this. Its implementation is complete and durable — 16 commits pushed, worktree
clean, 16 ahead and 0 behind the integration branch, plan 58/58 and 70/70 tasks, remediation
cycle 1 closed at 0 blocking findings, 16 of 17 acceptance criteria checked. Its genuine gate
artifacts all exist in its own worktree with correct staleness ordering:

| artifact | timestamp |
| --- | --- |
| `artifacts/pr_context.summary.txt` | 02:24:47 |
| `artifacts/pr_body_596.md` | 02:28:06 |
| `artifacts/pr_body_596.receipt.json` | 02:28:14 |

The hook instead read the session-root `orchestrator-state.json`, which belongs to the
concurrently running sibling 598 and is legitimately mid-execution, and denied with
`ORCHESTRATOR_STATE_PREFLIGHT_FAILED`. The child declined to overwrite that file to satisfy the
gate, because doing so would corrupt a live sibling orchestration and assert completion state for
a lifecycle that had not run; `pr-author` reached the same conclusion independently and restored
the directory. That was the correct call and was not overridden.

598 hit the identical block. Both children were ultimately unblocked the same way, and this is the
pattern to reuse: serialize each child's PR creation, and relocate that child's own genuine
artifacts into the working directory the hook resolves.

**Order is load-bearing.** Refresh `pr_context.summary.txt` at the session root *first*, then have
`pr-author` author a fresh `pr_body_<N>.md` and receipt. The gate requires the receipt's
`created_at` to be strictly newer than the context summary's filesystem write time, so copying a
previously authored body and receipt alongside the context fails `PR_AUTHOR_RECEIPT_STALE`.
Nothing is fabricated: every artifact is the child's own output and only its location changes.

598 found this independently; 596 then applied it under explicit instruction once 598 had finished,
which is why the two had to be serialized rather than run concurrently. Both merged: 598 as PR #603
(`f134119c`), 596 as PR #604 (`4ec38c4c`).

## Plan Defect: Ephemeral Worktree Path Hard-Coded 47 Times

The 599 atomic plan embeds an absolute worktree path in every bash command:

```
wsl -d Ubuntu -e bash -lc 'cd /mnt/c/Users/DanMoisan/repos/drm-copilot/.claude/worktrees/<agent-id> && ...'
```

A worktree id is ephemeral and changes on every relaunch, so each retry must rewrite the entire
plan before executing a single task, and a plan committed with one worktree's id is wrong for every
other worktree. The path should be a variable resolved at execution time, or expressed relative to
the plan's own location. This also raises the cost of an otherwise-preferred fresh-isolated
relaunch, and is worth a follow-up issue.

## Blocking Defect: Preimplementation Gate Retargets via Longest-Match

The wave-1 launch of 597 was denied with `PREIMPLEMENTATION_GATE_BLOCKED` naming the `merge_status`
predicate, despite 597 being `not_started` and its only dependency being merged.

`Find-OrchestrationDelegationTargetFolder` resolves a delegation's target by scanning the prompt for
`docs/features/active/` tokens and taking the **longest** one (sort by length descending), after
which `Get-EpicOrchestrationReadinessFailure` denies when that resolved record's `merge_status` is
terminal.

The `epic-orchestrate` skill *mandates* an upstream-context citation naming each dependency's spec
and plan paths. Whenever a dependency's folder name is longer than the target's, that mandated line
wins the longest-match and retargets the gate onto the already-merged dependency. Here
`2026-08-29-blast-radius-powershell-calling-convention-598` is longer than
`2026-08-29-caller-site-invocation-correctness-597`, so following the skill made the launch
impossible.

Worked around by citing the dependency by folder basename rather than full path, leaving 597's own
plan path as the longest token. **The workaround is fragile** — it depends on relative name lengths
and will silently break for a different pair. The durable fix is for the resolver to prefer an
explicitly declared target field over a longest-token heuristic.

**It recurred at wave 2.** 599's basename `2026-08-29-remove-remaining-python-invocations-599` is
*shorter* than its dependency `2026-08-29-caller-site-invocation-correctness-597`, so citing 597's
full plan path would again have retargeted the gate onto the merged 597. Two consecutive dependent
launches would each have blocked themselves by following the skill as written, which is evidence
the collision is systematic rather than incidental to one unlucky name pair.
