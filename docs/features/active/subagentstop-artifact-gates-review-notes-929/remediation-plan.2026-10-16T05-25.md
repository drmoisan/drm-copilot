## Governing Rules

**Fail-closed evidence rule:** Every baseline, targeted-verification, and final-QA step writes its own artifact under `docs/features/active/subagentstop-artifact-gates-review-notes-929/evidence/<kind>/`. A task is not checked off until its artifact exists with every required field. A missing artifact or field makes the cycle INCOMPLETE, never PASS.

**Evidence fields:** Every command artifact carries `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`. Script-route artifacts also carry `Script:` quoting the script body verbatim. The first `Command:` and `EXIT_CODE:` in an artifact form its parsed record, so the gate an artifact is named for is recorded first. Script output is copied verbatim into a fenced block, one output line per artifact line.

**Evidence filenames and locations:** Artifacts are named `<name>.<timestamp>.md`; the stamp is the UTC write time read from the host clock immediately before the write (`date -u +%Y-%m-%dT%H-%M`). A task that consumes an artifact selects the lexicographically greatest file matching `<name>.*.md` in the named folder. Phase 0 writes to `evidence/remediation-baseline/`; Phase 1 writes to `evidence/regression-testing/`; Phases 2 and 3 write to `evidence/qa-gates/`. Names written in this cycle carry the prefix `rc1-`, except `phase0-instructions-read` and `coverage-repo-wide` (the name the remediation inputs fix), so no cycle-1 selection can pick up an artifact of the original plan. No evidence is written under `artifacts/`. PoshQC writes `artifacts/pester/pester-junit.xml` and `artifacts/pester/powershell-coverage.xml` (gitignored by `/artifacts`); those are tool output, not evidence.

**No host paths:** Artifacts never record a host absolute path. The worktree root is recorded as the literal token `WORKTREE_ROOT`. Coverage XML `package` names (which carry absolute paths) are never copied; only `counter` elements are copied.

**Scratch location:** Every scratch file lives directly under the untracked worktree-root directory `SCRATCH/929/` (it exists; it is not in `.gitignore`). Script names carry the prefix `RC1-` so they do not overwrite the original plan's scripts. Nothing under `SCRATCH/` is staged or committed: every `git add` names explicit paths (`git add -A` and `git add .` are never used), and every clean-tree check uses the pathspec `":(exclude)SCRATCH"`. Artifacts record scratch paths in the form `SCRATCH/929/<file>`. Scratch scripts live in `SCRATCH/929/` inside the worktree rather than in the session scratchpad because each is run as `sh SCRATCH/929/<file>.sh` from the worktree root and must resolve its relative paths (the wrapper's `cd "$(dirname "$0")/../.."` and every repository-relative path in the script body) against the worktree root; `SCRATCH/` is untracked, and `929` scopes the directory to this item. The merge-base tar `SCRATCH/929/main-base.tar` and its extract `SCRATCH/929/main-base/` (P2-T4, conditional) are scratch files under the same rule: they stay untracked under `SCRATCH/`, are never staged or committed, and are not a registered worktree.

**Script route (every PowerShell command):** The executor has no PowerShell tool, and the Bash tool in an agent-isolated worktree refuses command text containing `pwsh`, `bash`, `wsl`, or a heredoc. For the script `SCRATCH/929/<NAME>.ps1` named in a task, the executor (1) writes that file with the Write tool, containing exactly the script body quoted in the task; (2) writes `SCRATCH/929/<NAME>.sh` with the Write tool, containing exactly two lines: `cd "$(dirname "$0")/../.." || exit 97` and `pwsh -NoProfile -NonInteractive -File SCRATCH/929/<NAME>.ps1` (with `<NAME>` replaced by the same concrete name); (3) runs `sh SCRATCH/929/<NAME>.sh` with the Bash tool from the worktree root. The wrapper's exit status is the `pwsh` exit status. Every task names its concrete script; no task uses a placeholder name. The two long-running full-suite tasks (P2-T2 and P2-T5) use the background wrapper form defined in their task text instead of the two-line form. PoshQC MCP tools (`mcp__drm-copilot__run_poshqc_format`, `mcp__drm-copilot__run_poshqc_analyze`, `mcp__drm-copilot__run_poshqc_test`) are direct tool calls; `git` and `sh` commands run directly in the Bash tool.

**Verification policy (Option A):** Local verification uses the PoshQC MCP tools plus CI evidence. Counts, named-test results, analyzer findings, and coverage come from (a) the Pester runner scripts below, which print `<Result> | <name>` lines and `FAILED=`, `FAILED_BLOCKS=`, `FAILED_CONTAINERS=`, `PASSED=` totals and exit with `FailedCount + FailedBlocksCount + FailedContainersCount`; (b) direct `Invoke-ScriptAnalyzer` per file; and (c) the self-hosted PoshQC module's `artifacts/pester/powershell-coverage.xml` and `artifacts/pester/pester-junit.xml`. **Full-run mechanics (F1):** `Invoke-PoshQCTest` without `-ScanFolders` reads `config/poshqc-scan.json` (`scripts`, `tests/powershell`, `tests/scripts`; the same set as `Run.Path` in `scripts/powershell/PoshQC/settings/pester.runsettings.psd1` line 3), and the coverage population from `config/poshqc-coverage.json` (`.claude/hooks`, `.claude/lib`, `.codex/hooks`, `.codex/scripts`, `scripts`). `SCRATCH/` is in neither set. `Run.Exit = $true` (runsettings line 4) ends the `pwsh` process with a non-zero code when any test, block, or container fails, after the JUnit and coverage files are written, so the run script prints its markers before the call and a separate read script reads the results. The scoped run of the original plan took 135 s of discovery and 1016 s of execution for 5358 tests; the full run covers more folders and is expected to take tens of minutes. It therefore runs in the background (Bash tool `run_in_background: true`) and writes its output to a scratch log; completion is the appearance of a line beginning `PWSH_EXIT=` in its `.exit` file. While a full run is in progress, the executor starts no other PoshQC, Pester, or format command. The background wrapper runs `pwsh` under `timeout --verbose --kill-after=60 180m`, so the run is bounded at 180 minutes (plus a 60-second grace before `KILL`) and the wrapper always writes `PWSH_EXIT=`. When the timeout fires, GNU `timeout` writes a line beginning `timeout: sending signal` to the log (its stderr is redirected into the log by the same `2>&1`) and exits 124 (or 137 after `KILL`). The timeout has fired when the read script output contains a line beginning `LOG | timeout: sending signal`, or when the `PWSH_EXIT=` value is 124 or 137 and the output contains no `LOG | Tests completed in` line. In that case the reading task records `FULL-RUN-INCOMPLETE` in its artifact and stays unchecked; the F1 evidence is incomplete and is not treated as complete by any later task (see P2-T3 and P2-T6). If no `PWSH_EXIT=` line appears within 190 minutes of the start (the wrapper itself did not complete), the executor records `FULL-RUN-INCOMPLETE` in the same way.
