## Resolver semantics (pinned; identical in all three runtimes)

Inputs: the checkpoint, the selected `route_id`, the route's `required_mcp_tools` after promotion-type resolution (`resolved`), and the harvested successful-receipt set (`successful`). When the key `issue_adoption` is absent the resolver returns no errors and no waived tools. Otherwise the rules of `spec.md` "Validation rules" run in order and errors accumulate:

1. Not an object (including `null`): E1, and evaluation stops.
2. `issue_num` is not a string matching Python `re.fullmatch(r"[1-9][0-9]*", s)` / TypeScript `/^[1-9][0-9]*$/` / PowerShell `-cmatch '\A[1-9][0-9]*\z'` (a JSON number is invalid): E2a. Only when `issue_num` is valid and the checkpoint `issue-num` is a string that is not ordinally equal: E2b.
3. `issue_url` is not a string ending (ordinal) with `/issues/` plus `issue_num`, or `issue_num` is invalid: E3.
4. `origin` not in the three values: E4. 5. `verified_via` not in the three values: E5.
6. `verified_at` absent, `null`, or a string that is empty or whitespace-only: E6. Any other present value, including a PowerShell `System.DateTime`, passes.
7. `evidence` not a string with non-whitespace content: E7.
8. Shape check: `waived_tools` must be a list whose elements are all strings with non-whitespace content, and non-empty; otherwise E8a and no further rule-8 or rule-9 check runs. When the shape passes, each entry in list order gets the first matching error of E8dup (seen earlier), E8cannot (not in the ordinal set `potential_to_issue`, `new_potential_entry`, `new_potential_bug_entry`), E8notreq (not in `resolved`), E8receipt (in `successful`). Then, if `potential_to_issue` is not in the list: E8include.
9. Only when the rule-8 shape check passed: for each distinct entry equal to `new_potential_entry` or `new_potential_bug_entry`, in first-occurrence order, when `potential_record` is not a string that starts with `docs/features/potential/` and ends with `.md` (ordinal): E9 for that tool.

Result: when the error list is empty, the waived-tool set is the set of `waived_tools` entries; otherwise it is empty. In the routing contract, the receipt loop skips a resolved tool only when it is in the waived set, and the adoption errors are appended after the receipt loop and before the `local_execution_overrides` errors. The declared `required_mcp_tools` equality check is unchanged.
