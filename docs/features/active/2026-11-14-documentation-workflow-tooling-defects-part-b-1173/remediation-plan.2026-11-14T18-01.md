## Design Decisions

- D-1 (cycle removal): a new lower-level module `EXT/src/mcp-tool-inputs-docs-grammar.ts` receives exactly the symbols the batch module needs and their private dependencies: `DOCS_RELATIVE_PATH_PATTERN`, `DOCS_IDENTIFIER_PATTERN`, `DOCS_REVISION_PATTERN`, `DOCS_ELEMENT_ID_PATTERN`, `DOCS_TEXT_PATTERN`, `DOCS_LIMIT_PREFIX`, `DOCS_LEDGER_OPERATIONS`, `DOCS_DISPOSITIONS`, `DOCS_DIMENSIONS`, `DOCS_DIMENSION_STATES`, `DOCS_LEDGER_COMMON_FIELDS`, the `DocsGrammar` type, `DocsInputError`, `matchesDocsGrammar`, and the private `LINE_SEPARATOR_ESCAPES`, `PATH_SEGMENT_CLASS`, `GRAMMAR_PATTERNS` and `splitPageReference`. It imports no project module. `mcp-tool-inputs-docs-ledger-batch.ts` imports them from the grammar module; `mcp-tool-inputs-docs.ts` imports what it uses locally and re-exports every moved exported symbol by name (`export type` for `DocsGrammar`, because `tsconfig.jest.json` sets `isolatedModules`). Resulting edges: docs inputs to batch, docs inputs to grammar, batch to grammar; no cycle.
- D-2 (rejected alternatives): moving the shared vocabulary into `mcp-tool-inputs-docs-ledger-batch.ts` would keep the file inventory but make the general resolver of all six tools depend on the batch-specific module for its grammar, which inverts the layering; `docs-command-envelope.ts` (the existing lower-level dependency) is the envelope parser and does not own input grammar; moving the batch logic into `mcp-tool-inputs-docs.ts` would take that file to about 700 lines against its spec limit. The spec limit on `mcp-tool-inputs-docs.ts` (table rows and requiredness only) is read, as the remediation input states, as: this cycle changes that file only by removing the moved definitions and adding import and re-export statements. Its table rows, `DOCS_LEDGER_OPERATION_RULES`, `checkLedgerOperation`, `resolveDocsToolInput` and the `checkDocsLedgerInput` call are unchanged, so `update_docs_ledger` behavior (`operation` and `operations` exclusivity, per-item validation, serialization, `-Operations -` emission, standard-input forwarding) is unchanged.
- D-3 (why the cycle was not caught): the extension has no architecture-boundary stage for TypeScript. No `.dependency-cruiser.cjs` exists in the repository root or in `EXT`, `EXT/package.json` has no dependency-cruiser dependency or script, and `EXT/eslint.config.mjs` loads only `@eslint/js` and `typescript-eslint`, so no `import/no-cycle` rule runs. `tsc` and Jest accept the cycle because neither module reads the other's bindings at load time. The regression test of `[P1-T1]` is therefore the stage-4 check for these modules; adding dependency-cruiser is out of scope (new dependency).
- D-4 (gate scope): the change set is TypeScript under `EXT` only. No test under `tests/` names either module (searched for `mcp-tool-inputs-docs`: no hit), so the Pester and pytest suites import no changed file. The `[P1-T5]` phase gate and the final loop run the TypeScript stages and one Jest run; Pester and pytest run in CI on the pushed head. This is a one-off scope decision for this cycle, not a process reduction.
- D-5 (coverage comparison): moving covered code shrinks the denominator of `mcp-tool-inputs-docs.ts`, so its percentage can move without any coverage loss. No-regression is judged by uncovered counts: the uncovered lines (and branches) of `mcp-tool-inputs-docs.ts` plus `mcp-tool-inputs-docs-grammar.ts` after the change are at most the uncovered lines (and branches) of `mcp-tool-inputs-docs.ts` in the `Phase 0 baseline`; `mcp-tool-inputs-docs-ledger-batch.ts` has no more uncovered lines or branches than its baseline; each of the three files is at least 85% line and 75% branch.
- Bundle mirrors: TypeScript sources under `EXT/src/` have no bundle copy under `EXT/resources/` (no `.ts` file exists there), so no mirror task is needed.
