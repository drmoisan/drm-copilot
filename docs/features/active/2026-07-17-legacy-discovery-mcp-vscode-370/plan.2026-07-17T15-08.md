## Scope Summary

Expose seven discovery operations as MCP tools in the drm-copilot MCP server and as VS Code commands, wrapping the epic's `dev.discovery.*` Python CLI commands without re-authoring any of them. The exposure layer is domain-neutral. All changes live under `extensions/drm-copilot/` (Jest 30 + ts-jest; per-file coverage thresholds `{ lines: 85, branches: 75 }` in `jest.config.cjs`).

The seven tools, their VS Code command ids, and the landed wrapped entry points (Poetry console scripts in `pyproject.toml` `[tool.poetry.scripts]`, each mapping a `dev.discovery.*` console name to `module:function`; package root is `scripts.dev_tools.discovery`, with the validators and scenario generator in `scripts.dev_tools`):

|---|---|---|
| `validate_discovery_artifacts` | `drmCopilotExtension.validateDiscoveryArtifacts` | `scripts.dev_tools.validate_discovery_artifacts` — per-kind entry: `main_profile`, `main_feature_contract`, `main_coverage_ledger`, `main_runtime_scenario`, `main_parity_matrix`, `main_unspecified_behavior`, `main_product_decision`, `main_evidence_reference`, and `main` for `all` |

Per-tool CLI-arg composition (landed, verified):

- `validate_discovery_artifacts`: exactly one positional `path` per kind entry (all nine entries, including `main` for `all`). `artifact_type` enum is exactly `["profile", "feature-contract", "coverage-ledger", "runtime-scenario", "parity-matrix", "unspecified-behavior", "product-decision", "evidence-reference", "all"]`.
- `run_discovery_init`: positional `target_dir` (REQUIRED), `--template-root <path>` (optional), `--force` (optional flag).
- `run_discovery_repo_inventory` / `run_discovery_dotnet_analyzer` / `run_discovery_vsto_analyzer`: positional `profile` (optional; CLI default filename applies when omitted), `--output-dir <path>` (optional), `--json` (flag). The wrapper always passes `--json` and parses artifact paths from the stdout JSON `written_paths` field.
- `run_discovery_scenario_generation`: `--feature-contract <path>` (REQUIRED), `--parity-matrix <path>` (REQUIRED), `--runtime-characterization <path>` (REQUIRED), `--output <path>` (optional; when given, stdout prints `ok: wrote <path>`, which the wrapper parses), `--check` (optional flag).
- `run_discovery_report`: `coverage`/`parity` → `--input <path>` (REQUIRED), `--output <path>` (optional); `completion` → `--coverage-input <path>` (REQUIRED), `--parity-input <path>` (REQUIRED), `--output <path>` (optional). None of the report scripts print the output artifact path to stdout, so no artifact-path parsing is available on the report path (documented limitation).

**Substrate design (reconciled against the landed CLI):** the MCP server bundles no Python (feature #240; `RuntimeKind` is currently PowerShell-only; `.vscodeignore` excludes `**/*.py`). The service layer therefore spawns the WORKSPACE discovery CLI as a Python subprocess with `cwd = workspace_root`, reusing `runCommandWithOutput` / `CommandExecutionError` from `extensions/drm-copilot/src/command-runtime.ts`. **Invocation mechanism:** interpreter `-c` import of the exact console-script entry — argv `[pythonExe, "-c", "import sys; from <module> import <function>; sys.exit(<function>())", ...cliArgs]`. Rationale: uniform `python -m` invocation is NOT viable — `dev.discovery.dotnet`, `dev.discovery.vsto`, and `dev.discovery.init` have no `if __name__ == "__main__"` guard and no dedicated `__main__.py`, so `python -m` cannot reach them; `poetry run dev.discovery.<name>` would add a Poetry-on-PATH dependency. The `-c` mechanism reaches every landed `module:function` entry uniformly (including `main_dotnet`, `main_vsto`, and the guard-less init) and preserves the existing subprocess semantics. The central mapping table therefore carries, per wrapped invocation: the dotted module path, the function name, and the CLI-arg composition. No VSIX bundling change; `resources/` mirroring is #9012's responsibility and out of scope. The issue.md wording "shells out to the bundled Python script" is superseded by the spec's substrate correction.

**Upstream substrate status (reconciled):** all upstream discovery waves (0/1/2) are MERGED on the integration branch. The mapping table targets the real landed console-script names, module paths, entry functions, and flags verified in `pyproject.toml` (`[tool.poetry.scripts]`, `dev.discovery.*` entries). The earlier design-against-planned assumption set is retired; any future upstream rename remains a single-table change. Tests still fake or mock the subprocess spawn boundary, so no live CLI execution occurs in the automated test suite. Schemas live in `schemas/discovery/v1/` and artifacts self-declare their `$schema` URI, so the wrapper hardcodes no schema path.

**File-size constraints (measured):** `extensions/drm-copilot/src/repo-automation-service.ts` is 498 lines and `extensions/drm-copilot/src/mcp-repo-automation-tool-definitions.ts` is 489 lines; both would exceed the 500-line cap if extended in place, so Phases 3 and 5 include unconditional extraction tasks. `extensions/drm-copilot/src/extension.ts` is 489 lines; registration logic must live in a new module.

**Evidence locations (non-overridable):** all evidence artifacts resolve under `docs/features/active/2026-07-17-legacy-discovery-mcp-vscode-370/evidence/<kind>/` (`baseline`, `qa-gates`). No `artifacts/` evidence path is used. `<TS>` below denotes an ISO-8601 `yyyy-MM-ddTHH-mm` timestamp captured at execution time.
