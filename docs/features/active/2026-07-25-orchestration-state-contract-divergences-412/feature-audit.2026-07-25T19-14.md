### Acceptance criteria

From `spec.md` — Divergence 1 — step-status vocabulary:

1. The Python validator (`scripts/dev_tools/validate_orchestrator_state.py`) accepts `step9_status` values `passed`, `failed_remediation_required`, and `blocked_ci_loop_limit` in plain validation mode.
2. The Python validator accepts `step6_status: "blocked_remediation_loop_limit"` in plain validation mode.
3. The Python validator rejects each per-key extra value when written to any step-status key other than its owning key, with the error `Checkpoint has invalid <key>: <value>`.
4. The shared `VALID_STEP_STATUS` set in `scripts/dev_tools/validate_orchestrator_state.py` is unchanged; the new values are carried in a per-step-key additive map.
5. The Python `--require-complete` gate fails with a completion-validation error when any step status is `failed_remediation_required`.
6. The Python `--require-complete` gate fails with a completion-validation error when any step status is `blocked_ci_loop_limit`.
7. The Python `--require-complete` gate fails with a completion-validation error when any step status is `blocked_remediation_loop_limit`.
8. The Python `--require-complete` gate does not fail on `step9_status: "passed"` in an otherwise-complete checkpoint.
9. The Python `--require-pr-creation-ready` gate fails when `step6_status` is `blocked_remediation_loop_limit`.
10. The TypeScript mirror (`extensions/drm-copilot/src/lib/validate/orchestrator-state-core.ts`) implements the same per-key acceptance and rejection behavior with error strings byte-identical to the Python validator, verified by Jest cases.
11. The TypeScript completion check rejects `failed_remediation_required`, `blocked_ci_loop_limit`, and `blocked_remediation_loop_limit` with error strings byte-identical to the Python validator, and does not reject `step9_status: "passed"`.
12. `.claude/lib/orchestrator-state/OrchestratorState.psm1` implements the same per-key acceptance and rejection behavior, verified by Pester cases in `tests/scripts/claude-lib/orchestrator-state/OrchestratorState.Tests.ps1`.
13. A checkpoint with `epic_mode: true` and `step9_status: "passed"` passes plain validation and satisfies `.claude/hooks/enforce-epic-merge-gate.ps1` with zero edits to that hook (regression scenario).
14. All pre-existing step-status validator tests (Python, Pester, Jest) pass without fixture modification, demonstrating that no previously valid checkpoint is newly rejected in plain mode.

From `spec.md` — Divergence 2 — complexity-floor semantics:

15. `compute_complexity_floor` returns `C1` for each single-element list containing a `"floor": false` signal (`single_file_localized_edit`, `mechanical_rename_or_move`, `docs_or_comment_only`) and for a single-element list containing an unknown signal name.
16. `compute_complexity_floor` returns `C3` for each single-element list containing a `"floor": true` signal and for any mixed list containing at least one floor signal, returns `C1` for `[]`, and never returns `C4`.
17. `Get-ComplexityFloor` in `.claude/lib/model-routing/ModelRouting.psm1` produces outputs identical to `compute_complexity_floor` for the same truth table, verified by Pester cases in `tests/scripts/claude-lib/model-routing/Get-ComplexityFloor.Tests.ps1`.
18. `tests/scripts/dev_tools/test_compute_complexity_floor.py` contains a static parity assertion that the embedded `FLOOR_SIGNAL_NAMES` set equals the set of names flagged `"floor": true` in `config/orchestration-routing.json`.
19. `tests/scripts/claude-lib/model-routing/ModelRouting.Parity.Tests.ps1` contains a static parity assertion pinning `$script:FLOOR_SIGNAL_NAMES` to the config's `"floor": true` names.
20. The complexity validator accepts a recorded `complexity_assessments` entry whose `signals_present` contains only non-floor signals and whose `floor` is `"C1"`.
21. The complexity validator rejects the same entry with `floor: "C3"`, producing a floor-mismatch error that names the recomputed value `C1`.
22. `scripts/dev_tools/compute_complexity_floor.py` docstrings no longer claim caller pre-filtering, the module performs no file I/O, and the file remains under 500 lines.
23. `.claude/lib/model-routing/ModelRouting.psm1` performs no file reads at runtime.
24. The PR body records the divergence-2 backward-compatibility statement: zero stored assessments invalidated (paths and counts per the research), and pre-change checkpoints with non-floor-only assessments require re-recording via the documented resume reconciliation.

From `spec.md` — Cross-cutting:
