## Scope and summary

Four defects in the Claude and Codex copies of `enforce-completion-consistency.ps1` are fixed together: (1) the Codex Edit branch reads the checkpoint from a relative literal; (2) both copies apply `String.Replace`, which replaces every occurrence and ignores `replace_all`; (3) the two copies disagree on a missing, empty, or unreadable targeted checkpoint (Claude allows, Codex denies) and Claude lets a reader exception escape; (4) the Claude suite runs the default reader against a relative path and no test drives the default reader against a real file. The fix is fail-closed on both surfaces (spec D1), implemented as two pure helpers in each tree's `enforce-completion-helpers.ps1` (spec D3). The module tier for `.claude/hooks` and `.codex/hooks` in `quality-tiers.yml` is T3, so there is no property-test obligation; line coverage must be at least 85 percent and PowerShell has no branch gate.

Planning decisions beyond the spec: (PD1) the cause for an empty Write is `write-content-empty`; (PD2) the deny builder is named `ConvertTo-CompletionDenyDecision`, with a verb that does not trigger the state-changing-function analyzer rule; (PD3) the Codex helper and all four mirrors are produced by `Copy-Item` so that the three Edit-tool production paths stay within the batch budget; (PD4) the transport suite loses five resolver rows (the spec cites six; the tree has five); (PD5) `Get-CheckpointFileContent` returns the raw text, substituting `''` when `Get-Content -Raw` yields `$null` (under pwsh 7.6.6 `Get-Content -Raw` on a zero-byte file yields `$null`, and a bare `[string]` cast of that result is also `$null`, which would resolve an empty checkpoint to `checkpoint-missing`), so that an empty file yields `''` and the causes `checkpoint-missing` and `checkpoint-empty` stay distinct; (PD6) a helper-pair byte-parity Pester test is left to C5b (#737), and byte identity is verified here by hash commands in `[P2-T2]`, `[P2-T13]`, and `[P5-T12]`; (PD7) the Claude entrypoint cannot be driven with an unreadable file without a temporary file, so AC-8 is verified at decision level, as the spec permits.

## Execution conventions

- **Shell route.** A command shown as `pwsh -NoProfile -Command '...'` is run with the PowerShell tool when it is available. When only the Bash tool is available and it refuses command text containing `pwsh`, write the exact line, unchanged, as the only line of a `.sh` file in the session scratchpad directory (outside the repository) and run `sh <that file>` from the worktree root. `Command:` records the `pwsh` line and `EXIT_CODE:` records the exit status of the run. No command body contains a single quote inside its outer single-quoted string. Commands shown as `grep`, `wc`, `git`, or `poetry` run in the Bash tool. This is the `sh` route.
- **Base anchor.** `[P0-T2]` records the starting commit as `BaseSha:` (a 40-hex value). Every later `git diff` uses that value, written below as BASE_SHA; substitute the recorded 40-hex value before running. `origin/main` is never a diff operand.
- **Region location.** Edits are located by function name and by literal text, not by line number. Line numbers in the spec are advisory.
- **Batch budget.** `.claude/hooks/enforce-powershell-batch-budget.ps1` denies the 4th distinct production PowerShell path written through Write or Edit. This plan writes exactly three production paths through Edit (`.claude/hooks/enforce-completion-helpers.ps1`, `.claude/hooks/enforce-completion-consistency.ps1`, `.codex/hooks/enforce-completion-consistency.ps1`); the other five production paths are produced by `Copy-Item` through the `sh` route. Test files are never counted. If any write is denied with `POWERSHELL_LARGE_PATH_REQUIRED`, stop and report BLOCKED; do not work around the hook.
- **PoshQC MCP route steps.** `mcp__drm-copilot__run_poshqc_format`, `mcp__drm-copilot__run_poshqc_analyze`, and `mcp__drm-copilot__run_poshqc_test` return a pre-composed summary with no counts, percentages, or findings. Each is called as the policy route step and only its call disposition (`returned` or `error`, plus the summary sentence) is recorded. Every asserted count, per-test result, finding count, and coverage percentage is derived from a source the plan's own commands print or write: the direct commands below, `artifacts/pester/pester-junit.xml`, or `artifacts/pester/powershell-coverage.xml`.
- **Observed output shapes.** Every value asserted below is a line that the stated command composes itself on a successful run: `PASSED=`, `FAILED=`, `FAILED_BLOCKS=`, `FAILED_CONTAINERS=`, `FAILED_TEST=` (PESTER_RUN), `SUITE_TESTCASES` and `FAILED_CASE=` (JUNIT_EXTRACT), `COV` and `LINE_PCT_BELOW_85` (COVERAGE_EXTRACT), `CHANGED_LINES` (CHANGED_LINES_EXTRACT), `FORMAT_UNCHANGED=`, `PSSA_FINDINGS`, `SHA256=`, and `MIRROR_IDENTICAL=`. The single-file forms of PESTER_RUN, JUNIT_EXTRACT, COVERAGE_EXTRACT, the format check, and the analyzer command were exercised on successful runs in the completed #708 work on the same hook. The planning session had no shell tool, so the multi-file `COV` loop, `CHANGED_LINES`, `MIRROR_IDENTICAL`, and `HELPERS_IDENTICAL` compositions were not executed before this plan was written; their first executions are `[P0-T13]` (`COV`), `[P0-T17]` (`CHANGED_LINES`, as a dry run against an unchanged tree), `[P2-T2]` (`HELPERS_IDENTICAL`), and `[P2-T13]` (`MIRROR_IDENTICAL`), and a command that fails to print its composed line fails its task and stops execution instead of being replaced by a different observation. Two tool outputs are not composed by the plan's commands and are used only for exit status and a recorded summary line: `Invoke-PoshQCTest` (`pester.runsettings.psd1` sets `Run.Exit = $true`, so a failing run exits the child process before the module's replayed summary is printed) and pytest (a passing run prints a final line containing `passed`).
- **Pass counts are derived, not guessed.** Wherever a task states `PASSED=` as a sum of recorded values, the executor computes the sum from the named earlier artifacts and records the arithmetic.

## Design contract (what Phase 2 implements and Phases 1 and 3 test)

Names quoted here are the exact literals the executor creates: `Get-EditReplaceAllFlag`, `Invoke-SingleOccurrenceEdit`, `ConvertTo-CompletionDenyDecision`, and the cause identifiers `no-old_string`, `checkpoint-missing`, `checkpoint-empty`, `checkpoint-unreadable`, `old_string-not-found`, `old_string-ambiguous`, and `write-content-empty`.

1. **`Get-EditReplaceAllFlag -ToolInput`** (both helper files, identical): returns `$false` when `ToolInput` is null or has no `replace_all` property; returns the value when it is the boolean type; returns `$true` for a string whose trimmed, case-insensitive value is `true`; returns `$false` for every other value. No `[bool]` cast is used, because `[bool]'false'` is `$true` in PowerShell.
2. **`Invoke-SingleOccurrenceEdit -Text -OldString -NewString -ReplaceAll`** (both helper files, identical, pure, no I/O): normalizes `\r\n` to `\n` in all three strings; an empty `OldString` yields `Failure = 'no-old_string'`; zero ordinal occurrences yield `Failure = 'old_string-not-found'`; with `ReplaceAll` true every occurrence is replaced by ordinal `String.Replace`; otherwise a second ordinal search starting at the first index plus the length of `OldString` (non-overlapping count) that finds a match yields `Failure = 'old_string-ambiguous'`, and no match yields a single splice by `Substring` (no regex, so `$` in `NewString` stays literal). Returns `[pscustomobject]@{ Content; Failure }` with `Content` null on failure and `Failure` null on success.
3. **`Get-CheckpointFileContent`** (each hook): keeps returning `$null` for a path that is not a file; for an existing file it returns the raw text, substituting `''` when `Get-Content -Raw` yields `$null`, so an existing zero-byte file yields `''` and never `$null`. This keeps `checkpoint-missing` and `checkpoint-empty` distinct, because `Get-Content -Raw` on a zero-byte file yields `$null` under pwsh 7.6.6 and a bare `[string]` cast of `$null` is also `$null`. The planned final lines are `$text = Get-Content -LiteralPath $Path -Raw -ErrorAction Stop`, `if ($null -eq $text) { return '' }`, and `return [string]$text`.
4. **`Resolve-EditedCheckpointContent -ToolInput -CheckpointReader -CheckpointPath`** (each hook; `CheckpointPath` mandatory on both): returns `[pscustomobject]@{ Content; Failure }`. Order: absent or empty `old_string` gives `no-old_string`; the reader is called with the raw, unmodified `CheckpointPath` inside `try/catch`, and a throw gives `checkpoint-unreadable`; a `$null` result gives `checkpoint-missing`; an empty string gives `checkpoint-empty`; otherwise the result of `Invoke-SingleOccurrenceEdit` using `Get-EditReplaceAllFlag` is returned.
5. **`ConvertTo-CompletionDenyDecision -Reason`** (each hook): returns the existing ordered `hookSpecificOutput` deny shape (`hookEventName = 'PreToolUse'`, `permissionDecision = 'deny'`, `permissionDecisionReason = $Reason`).
6. **`Invoke-CompletionConsistencyDecision`** (each hook): gate order unchanged (Claude envelope check; empty `file_path` allows; non-checkpoint path allows), and the reader is never invoked before those gates pass. For a checkpoint target, a `content` property that is present (including empty or null) is a Write: empty content denies with cause `write-content-empty`; non-empty content follows the existing path. Otherwise the call is an Edit: it calls the resolver with `-CheckpointPath` set to the parsed `file_path` unchanged (raw spelling, including backslashes), and any `Failure` denies. The deny reason is exactly `COMPLETION_CONSISTENCY_BLOCKED: the canonical checkpoint cannot be deleted, emptied, or replaced through an unresolved patch (<cause>).` with the cause identifier in the parentheses, on one source line so the phrase `replaced through an unresolved patch` stays searchable. Invalid-JSON patched or written content keeps its current per-surface behaviour (Claude allows, Codex denies with `must remain valid JSON`).
