Issue #936's own Expected Behavior accepted "the cause of the non-attribution is documented with a test that covers the line", so documentation was the requested outcome; this item's AC-27 states a threshold. Issue #936 also produced the decisive single-suite coverage run before relying on the mechanism (`isolated-coverage-attribution.2026-10-16T01-28.md`: every affected line `ci=1` in a run scoped to `tests/scripts/codex-hooks`). This item has no such run (`LOCAL_COVERAGE_RUN=NOT-PERFORMED`, `MECHANISM=LIKELY-NOT-VERIFIED`).
3. No autonomous change raises the measured figure within the constraints already set for this item. The likely effective change, `UseBreakpoints = $false`, is a repository-wide coverage-configuration change that the #936 research and Record 4 reserve for the operator. Making the first-compiling suite execute the lines, or reordering suites, was rejected by the #936 research as dependent on discovery order and script-cache occupancy.

The finding is therefore classified `human_decision_required`. The operator question is stated in `remediation-inputs.2026-10-16T21-30.md` R1.

The issue #936 scoped run was produced without a launcher, through `mcp__drm-copilot__run_poshqc_test` with `scan_folders=["tests/scripts/codex-hooks"]`, which writes `artifacts/pester/powershell-coverage.xml` (`docs/features/active/2026-10-15-hook-coverage-attribution-gaps-936/evidence/qa-gates/test-scoped.2026-10-16T01-28.md`). - **PA-N4 / CR-16 (Info):** the M1 URL rule uses ordinal `Contains('/pull/')`, while `ConvertFrom-EpicMergeGateSelector` matches `/pull/(\d+)` case-insensitively (`-match`). A selector such as `https://github.com/o/r/PULL/5` resolves to 5 and is not refused by M1. The gh CLI URL pattern for pull requests appears to be case-sensitive, in which case gh treats that token as a branch name in the session repository and no cross-repository merge results; this was not verified in this review. Using `IndexOf('/pull/', OrdinalIgnoreCase)` would align the two checks.
