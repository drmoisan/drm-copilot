## Design

**Constants.** In `scripts/dev_tools/plan_gate_document.py` and `extensions/drm-copilot/src/lib/validate/plan-gate-document.ts`: `PLAN_TASK_GUIDELINE` becomes 20 and `PLAN_LINE_GUIDELINE` becomes 250; new `LEGACY_PLAN_TASK_GUIDELINE` (40), `LEGACY_PLAN_LINE_GUIDELINE` (400), and `PLAN_GUIDELINE_CUTOFF`, a string in the `yyyy-MM-ddTHH-mm` shape the feature-folder tooling uses for plan files. No new production module and no new `coverageThreshold` entry is needed; the existing per-file entries for `plan-gate-document.ts`, `plan-gate-discrimination.ts`, and `orchestration-artifacts.ts` in `extensions/drm-copilot/jest.config.cjs` gate the changed files.

**Cutoff value (D2, corrected).** The cutoff is the plan-file stamp of the minute the reduction commit is made, in America/New_York. A plan whose stamp sorts strictly before it keeps 40 and 400; a stamp equal to it or after it uses 20 and 250. A day-boundary cutoff would retroactively change plans written earlier on the commit day, before the rule existed. Derivation: a helper script under `SCRATCH` reads the host clock in UTC, converts it to America/New_York through the system time-zone database, and formats `yyyy-MM-ddTHH-mm`; the value is never composed by hand. [P1-T2] writes a provisional value derived that way; [P2-T4] derives a check value and runs the result check under it; [P2-T5] derives the final value in the same helper run that commits. A later cutoff never moves a plan from the legacy pair to the new pair, so every file that keeps its result under the check value keeps it under the final value; the helper asserts the final value sorts at or after the check value.

**Stamp reading (K4).** `plan_file_stamp` and `planFileStamp` split a path on both `/` and `\`. With `STAMP` the pattern `[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}-[0-9]{2}`, the file name fully matches `plan.STAMP.md`, `plan.remediation-cycle-N.STAMP.md` with `N` digits, or `remediation-plan.STAMP.md`; or the name is `remediation-plan.md`, its parent segment fully matches `STAMP`, and the segment above it is `remediation`. Any other name, an empty path, and no path yield no stamp. Matching is case-sensitive.

**Guideline selection.** `plan_size_guideline(stamp, *, cutoff=PLAN_GUIDELINE_CUTOFF)` and `planSizeGuideline(stamp, cutoff = PLAN_GUIDELINE_CUTOFF)` return the legacy pair when a stamp exists and sorts strictly before `cutoff`, and the new pair otherwise. The `cutoff` parameter is the test seam: boundary tests inject a fixed cutoff, and only the doc-parity test of [P2-T1] reads the committed value.

**Path parameter (K5).** Python `evaluate_document_gates(report, text, *, plan_path=None)`, `evaluate_plan_gates(text, *, context=None, plan_path=None)`, `validate_plan_text_with_warnings(text, *, context=None, plan_path=None)`, and `_plan_channels` passing `args.path`; TypeScript `evaluateDocumentGates(report, text, planPath?)`, `evaluatePlanGates(text, context?, planPath?)`, and `validateArtifactWithWarnings` passing `input.artifactPath` beside `buildPlanGateContext(input)`, which still returns `undefined` when any wiring field is absent. `validate_plan_text` keeps its signature and uses the new pair.

**Message.** `plan_size_message(tasks, lines, *, guideline=(PLAN_TASK_GUIDELINE, PLAN_LINE_GUIDELINE))` and `planSizeMessage(tasks, lines, guideline = [PLAN_TASK_GUIDELINE, PLAN_LINE_GUIDELINE])` render the pair that applied in the existing format, so the legacy message is byte-identical to today's and the new one reads `exceeds the guideline of 20 tasks or 250 lines`.

**D9 for G13.** The installed MCP validator applies 40 and 400 until a release carrying this change is installed, so the planner's MCP self-check does not report a plan between the two pairs; the contract tells the planner to hold a new plan to 20 and 250 itself, and preflight applies the new pair through the Python CLI route of `## Validator Gate`.

**Result check.** In scope: every plan file under `docs/features/active/` (a file directly in a feature folder whose name starts with `plan` or `remediation-plan` and ends with `.md`, plus each `remediation/<stamp>/remediation-plan.md`; files under `evidence/` and `research/` are not plan files), and every plan path listed by the Epic #1019 kickoff: the folder under `docs/features/epics/` whose `epic.md` names `#1019`, read at the `refs/remotes/origin/epic/*` ref that holds it, each plan read at that ref or else at the remote branch that holds the path. A file's G13 outcome is whether the Python CLI output for it carries a `plan size` finding. A file keeps its result when its outcome at its own path under the check value equals its outcome under the legacy pair (an identical copy under `SCRATCH` named `plan.2000-01-01T00-00.md`) and, for files recorded at [P0-T5], the recorded outcome. Copies of #1019 plans keep their repository-relative path under `SCRATCH`. If any file does not keep its result: stop and report each path with its stamp, counts, and outcomes; no plan is changed, nothing is committed, and the uncommitted work stays in the worktree for the coordinator.

**Ledger entry and revert order.** `0008` carries `## Stored Patch`: `git diff --cached --binary --no-renames HEAD` over the paths of `## Files Changed` other than the ledger folder, generated in [P2-T5] after the final cutoff is written, so its hunks hold the final value and its two create hunks hold the new test files. Under README `## Revert Order`, `0008` is the highest number, so `Invoke-ProcessReductionChain` reverts it first, against the live tree, and then `0007` to `0001`. `0008` changes text in recorded regions of two older entries: the `**Size guideline.**` bullet of the six contract copies is a context line of hunks in `patches/0001-parallel-only-test-gates.patch`, and the planner clause `a plan above 40 tasks or 400 lines` of `.claude/agents/atomic-planner.md` and its bundle is a context line of hunks in both `patches/0001-parallel-only-test-gates.patch` and `patches/0006-test-suite-baseline-restored.patch`. No `Current` fence of `0001` to `0007` holds either line (the adjacent `0004` `**Task target.**` fence and the `0005` planner fence end before them and are left byte-identical). Those hunks stay valid without regeneration: reverting `0008` first restores both lines byte-for-byte before the `0006` and `0001` turns, so each hunk's context matches again. Regenerating them to carry `0008` text would instead fail after `0008` is reverted, which is why the README rule on edits inside a recorded region applies to an edit with no entry of its own, not to a newer entry that records the edit. Step 1 of `0008` states this, and the [P2-T5] replay proves it with the full chain and with the stop-before replays of `0006` and `0001`.
