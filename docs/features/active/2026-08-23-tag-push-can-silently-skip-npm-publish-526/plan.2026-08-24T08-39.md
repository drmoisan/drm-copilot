## Governing Rules for This Plan

**Fail-closed evidence rule.** Every evidence-producing task names its artifact path. Each command-step artifact records `Timestamp:`, `Command:`, `EXIT_CODE:`, and `Output Summary:`. A missing or field-incomplete artifact makes the outcome BLOCKED or INCOMPLETE, never PASS.

**Evidence location.** All evidence resolves under `docs/features/active/2026-08-23-tag-push-can-silently-skip-npm-publish-526/evidence/` in the kind-specific subdirectories `baseline/`, `regression-testing/`, `qa-gates/`, and `other/`. Any `artifacts/`-rooted evidence path is rejected. `EVIDENCE_LOCATION_OVERRIDE_REJECTED` does not apply: no non-canonical evidence path was supplied to this planner.

**Evidence filename timestamps.** Every evidence filename below ends with `.2026-08-24T13-10.md`. If the executor runs on a different date or minute, it substitutes its own `yyyy-MM-ddTHH-mm` stamp in that same position and records the substitution in the artifact's `Timestamp:` field. The path prefix and base name are fixed.

**Coverage tooling note.** `artifacts/pester/powershell-coverage.xml` and `artifacts/pester/pester-junit.xml` are the Pester runner's own configured output paths declared in `scripts/powershell/PoshQC/settings/pester.runsettings.psd1`. They are tool outputs, not evidence artifacts. Evidence artifacts summarizing them live under the feature `evidence/` tree.

**Coverage allow-list.** `scripts/powershell/PoshQC/settings/pester.runsettings.psd1` declares `CodeCoverage.Path` as an explicit per-file allow-list. A production PowerShell file absent from that list is outside the coverage denominator, which the Coverage Exclusion Policy in `.claude/rules/general-unit-test.md` forbids. Every production `.ps1` this plan adds is registered in that list by an explicit task. `scripts/dev-tools/Invoke-ReleaseTagPush.ps1` is already registered.

**Toolchain commands.** `.claude/rules/powershell.md` requires the MCP entry points. This plan names them verbatim: `mcp__drm-copilot__run_poshqc_format`, `mcp__drm-copilot__run_poshqc_analyze`, `mcp__drm-copilot__run_poshqc_test`. The workflow linter is `pwsh ./scripts/dev-tools/run-actionlint.ps1`.

**Per-file coverage measurement route — binding on every coverage-reading task in this plan.** `mcp__drm-copilot__run_poshqc_test` resolves its Pester runsettings from the *installed* VS Code extension, not from `scripts/powershell/PoshQC/settings/pester.runsettings.psd1` and not from the bundled mirror under `extensions/drm-copilot/resources/powershell/PoshQC/settings/`. A `CodeCoverage.Path` entry added by P2-T8 or P5-T2 is therefore invisible to the MCP runner, which emits no coverage row at all for the newly registered file. A missing row is a tooling-path artifact, not a coverage failure, and must not be read as one.

Accordingly, every task in this plan that reads a *per-file* coverage figure out of `artifacts/pester/powershell-coverage.xml`, or that asserts a per-file coverage row is present in it — P2-T23, P5-T2, P7-T3, P7-T6, and P7-T7 — must produce that XML by invoking the self-hosted PoshQC module directly. The already-executed P2-T8 asserted the same presence through the MCP tool; that clause is reconciled retroactively by this rule, and the row it names is present in the document produced by the direct invocation.

```
pwsh -NoProfile -Command "Import-Module ./scripts/powershell/PoshQC/PoshQC.psd1 -Force; Invoke-PoshQCTest -Root (Get-Location).Path"
```

`PoshQC.psm1` sets its Pester settings path from its own module root, so the self-hosted module reads the self-hosted runsettings and honours entries added by this change in the same run. This direct invocation is *in addition to*, never instead of, the MCP toolchain-loop runs the policy requires; the MCP run remains the pass/fail gate for the test stage and the direct run is the source of the per-file coverage rows. Per-file rows are parsed by keying on the enclosing `package` element (the full directory path), never on the bare `sourcefile` name. Where a task runs both, the direct invocation runs last, so the parsed document is the one carrying the per-file rows.

**Known constraint — file-size headroom on the verification module.** `scripts/dev-tools/Invoke-ReleaseVerification.ps1` stands at 499 lines against the 500-line cap in `.claude/rules/general-code-change.md`. It reached that figure only because comment-based help was condensed during Phase 2. Phases 3 through 7 add no code to that file, and the tasks appended in this revision add test code only, so the cap holds for this plan as written. Any later remediation that adds a line to that file breaches the cap immediately. The recorded remedy for that future case is to extract the five pure helpers — `ConvertFrom-JsonSafely`, `Resolve-PublishStepConclusion`, `Get-RecoveryInstruction`, `ConvertTo-VerificationResult`, and `Get-CodexPinnedMcpVersion` — into a sibling module. That split is deliberately **not** performed by this plan: it would require a new `CodeCoverage.Path` registration in both in-repo runsettings copies plus the bundled-parity check, a new test file, and a re-partitioned coverage denominator that invalidates every per-file figure this plan records. The cost is disproportionate to a plan whose remaining phases add nothing to the file. If the Phase 7 formatter changes this file, the authorized remedy inside this plan is condensing comment-based help further so the file returns to at most 500 lines; the helper-extraction split remains out of scope. The executor records the pre-format and post-format line counts in the P7-T8 artifact.

**Hard prohibitions, binding on every task below.** No task may run, or instruct the executor to run, a release, a publish, a tag creation, a tag push, a tag deletion, `npm publish`, `npm version`, `npm deprecate`, `npm unpublish`, or any `git push` of a tag. Read-only registry queries and read-only `gh` queries are permitted and are the only network operations this plan authorizes. Every acceptance condition in this plan is reachable without consuming an npm version number.

**Acceptance-condition authoring.** Per `.claude/rules/plan-acceptance-gates.md`, every acceptance condition below is either (i) a named Pester test in a named file whose pass or failure is asserted, (ii) a named command whose exit code is asserted, or (iii) a named evidence artifact whose required fields are enumerated. No acceptance condition is a prose-phrase search. No coverage argument is expressed as a filesystem path, and no asserted token contains a placeholder or interpolation marker.

**Fail-before exit-code declaration.** The `[expect-fail]` evidence artifacts written by P1-T2 and P1-T4 deliberately omit the optional `ExpectedExitCode` field. The exact exit code the Pester runner returns on test failure is not confirmed anywhere in this repository, and declaring `ExpectedExitCode: 1` against an unconfirmed value would normalize a correct fail-before run to `fail` whenever the runner exits with any other non-zero code. Those two tasks therefore assert a non-zero exit code plus the named failing test in their acceptance wording, which is decidable without knowing the exact value.

**Blocking protocol.** No task below instructs a mid-plan halt. The executor may block during preflight only; once execution begins it completes every remaining task, marks any task whose precondition failed as INCOMPLETE rather than PASS, and escalates in the completion report.
