## Design being implemented (research §11, spec `## Proposed Fix`)

In each hook entry point, the cwd-relative checkpoint binding is replaced by **one resolution step
executed before any decision logic**, returning exactly three outcomes:

1. target resolved, checkpoint path known — proceed with that **absolute** path; all existing
   decision logic runs unchanged;
2. target resolved, checkpoint genuinely absent or unreadable there — deny with the **existing**
   reason (`ORCHESTRATOR_STATE_PREFLIGHT_FAILED` for pr-author, `MODEL_ROUTING_RECEIPT_BLOCKED` for
   model-routing), unchanged;
3. target not identifiable — deny with F1's ambiguity reason code. This is the only new deny path.

There is no fourth outcome and no `else { use cwd }` branch. Keeping outcomes 2 and 3 separately
identifiable in the reason text is the substance of this feature.

Ordering, which must not otherwise change:
- pr-author: Case A -> Case B -> `gh pr edit` no-body allow -> Case C (`PR_CONTEXT_MISSING`) ->
  orchestrator-state preflight -> receipt checks 1-6. The ambiguity deny sits **after** the scope
  filter at `.claude/hooks/enforce-pr-author-skill-helpers.ps1:181` and **before** the
  orchestrator-state preflight at `.claude/hooks/enforce-pr-author-skill-helpers.ps1:240`.
- model-routing: `:136` anomaly -> `:153` scope filter -> `:157` checkpoint read -> `:158` presence
  -> `:162` deny. The ambiguity deny sits between `:155` and `:157`.
