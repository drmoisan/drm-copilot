## Verified Facts Fixed Before Planning

These were observed by running the commands in this worktree on 2026-08-28. They are not re-derived during execution.

1. The scoped Python coverage command below exits 0 and prints `44 passed`, with the module row reporting 58 statements, 0 missed, and a Cover value of 100 percent. The dotted coverage argument resolves and collects data.
2. Branch measurement is not enabled by default in the project configuration. Adding the branch flag adds `Branch` and `BrPart` columns (observed 22 and 0) but the table still prints one combined `Cover` percentage. No separate branch percentage is ever printed, so no acceptance condition in this plan reads one.
3. The project pytest `addopts` value supplies an LCOV reporter only. Every coverage command in this plan therefore passes `--cov-report=term-missing` explicitly.
4. On PowerShell 7.6.5, for a two-key hashtable whose `conflict` value is false, the `conflict` key reads false while boolean coercion of the whole hashtable reads true; the object is a `System.Collections.Hashtable`, implements `IDictionary`, and does not implement `IList`. The divergence is real and a single Pester assertion covering both halves can genuinely fail.
5. All three source-and-bundled pairs are byte-identical today by SHA-256 comparison taken on 2026-08-28.
6. The Pester run settings already register the blast-radius module for coverage, and the PoshQC scan folders already cover the Pester test directory used here. No run-settings edit is planned, and that file is out of scope.
7. The `hypothesis` package is not an approved dependency and is not added. The parametrized matrix over the existing ten-entry radius-pair fixture is used instead.
8. No tier map exists at the repository root, so tier-dependent property-density, mutation-score, and golden-test gates are exempt. The uniform 85 percent line threshold applies to both languages; the 75 percent branch threshold applies to Python only.
9. `.claude/lib/blast-radius/BlastRadius.psm1` is 482 lines today, so the comment-based-help addition has a budget of 17 lines before the 500-line limit binds.
10. The PoshQC MCP tools return a result payload carrying only an ok flag, a tool name, a workspace root, and a fixed summary string. They return no exit code, no diagnostic count, no severity breakdown, no test counts, and no coverage value. No acceptance condition in this plan reads any such value from an MCP PoshQC result.
11. The self-hosted PowerShell invocation does print observable numbers: a `Tests Passed:` line carrying passed, failed, skipped, inconclusive, and not-run counts, and a `Covered` line carrying the repository-wide combined percentage. Per-file PowerShell line coverage is derivable only from the JaCoCo `LINE` counter under the sourcefile element named for the module in the Pester coverage XML, which records missed 0 and covered 109 for the blast-radius module today.
12. The full Python suite currently reports one failing node ID, in the push-down Claude resource-contract module under tests/scripts/dev_tools, because a state file under .claude/state is absent from the bundle. That file is gitignored by the .gitignore entry .claude/state/ and is therefore not a repository file. This is repository issue #510, a known local-only condition that is green in CI. It is not caused by this change and is not remediated by this plan.
13. The single current Pester failure is in the Codex PreToolUse integration suite and is caused by the orchestration checkpoint's route identifier. It is environmental and checkpoint-dependent, so it is captured as a baseline at execution time rather than hardcoded here.
14. The combined two-file Python run prints one total, currently 98 passed, and prints no per-module figure. The per-file conflicts figure is therefore read from a separate single-file run.
15. `Invoke-PoshQCTest` overrides Pester's output verbosity to `Normal` regardless of the run settings, so the console output prints one container line per test file plus the names of failing tests only, and never prints the name of a passing `It`. Per-`It` pass status is read instead from the `testcase` elements of the Pester JUnit XML under artifacts/pester, each carrying a `name`, a `status`, and a `classname` naming the test file.

## Execution Notes

- Phase ordering is load-bearing. The deliberately-failing regression at P1-T2 runs before the fix at P2-T1, and every gate that requires the new tests to pass runs at P2-T2 or later. No phase-6 gate executes a test path containing a test that a later task makes pass.
- The phase 0 lint and format baselines use read-only invocations so a pre-existing drift is observed rather than silently repaired, which keeps the phase 6 write-mode gates meaningful.
- Coverage arguments are importable dotted module names supplied with the equals form. A filesystem-path spelling collects no data and is not used anywhere in this plan.
- No acceptance condition in this plan reads a separate branch-coverage percentage, because the coverage table prints one combined column and never prints a separate branch percentage.
- Every `git diff` in this plan is anchored to `origin/main`, and the single name-listing diff is paired with a porcelain-status span in the same task.
- No acceptance condition reads a value the PoshQC MCP tools do not return. Their result payload carries an ok flag and a fixed summary string only, so every PowerShell count and every PowerShell coverage figure in this plan is read from the self-hosted invocation captured at P0-T11 and from the JaCoCo counter in the Pester coverage XML.
- Two gates are judged against a captured baseline rather than against zero, because the repository carries a pre-existing failure in each language that this change does not cause and does not remediate. P6-T4 is judged against the P0-T10 Python baseline, and P4-T5 and P6-T8 are judged against the P0-T11 PowerShell baseline. In both cases the failing set may not grow and no new failing identifier may appear.
- Phase 6 is numbered sequentially but written in the order P6-T1 through P6-T8, then P6-T10, then P6-T12, then P6-T9, then P6-T11, because the loop-outcome task reports on P6-T12 and the sign-off task reports on both.
- Formatting in this document is load-bearing for scheduling, not only for readability. Blast-radius derivation harvests whitespace-free tokens out of single-backtick inline-code spans, and the whitespace split exposes an embedded path fragment even when the surrounding span is a command. It does not harvest fenced code blocks. The three self-hosted PoshQC invocations at P0-T11, P4-T5, and P6-T8 therefore sit in fenced blocks immediately under their task lines: the command text is preserved byte-for-byte for the executor while the PoshQC manifest path it contains is kept out of the declared radius. For the same reason, every out-of-scope path cited in this plan is written as plain prose with no code formatting, while every in-scope production path, test path, and evidence path keeps its inline-code formatting so the declared radius still claims it.
- No acceptance condition in this plan reads the name of a passing `It` from PowerShell console output, because that output is produced at Pester's Normal verbosity. Per-`It` pass status is read from the `testcase` elements of the Pester JUnit XML under artifacts/pester; per-file pass status is read from the container line the run prints for each test file.
- Do not restore inline-code formatting on those commands or on any out-of-scope path citation. This item is scheduled into a concurrent parallel run keyed on blast-radius contention. A token under scripts/powershell or a declared shared surface such as the blast-radius truth table would resolve to a shared surface and a module that this item does not write, creating a conflict edge against nearly every other item and forcing the run to execute serially. The Blast-Radius Contention Doctrine in .claude/rules/parallel-orchestration.md records this failure mode and the obligation it leaves in place: when a task genuinely writes such a path, the planner appends that exact concrete path to the declared radius rather than relying on a citation.
