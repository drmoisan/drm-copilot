## Design

**Key.** `features[].early_start` on the dependent, in the shape of research section 8: `dependency`, `upstream_branch`, `interface_settled_at`, `interface_evidence`, `synced_at`. A record is valid only when it is an object under the exact key `early_start`, `dependency` is a non-empty string or a number (never a boolean), and `upstream_branch`, `interface_settled_at`, and `interface_evidence` are non-empty strings. Non-empty means length above zero with no trimming, because Python, TypeScript, and .NET disagree on which characters are whitespace. An invalid record is the same as no key: no exemption and no new message, so today's rule reports the edge. `dependency` resolves through each layer's existing reference index, and the exemption is the one edge that resolves to that same feature. Every other edge runs today's code.

**Layer 2** (`validate_wave_barrier_ordering`, `validateWaveBarrierOrdering`, `Get-EpicWaveBarrierViolation`). Before the edge loop each started feature computes its exempt folder, which is null without a valid record. An edge that resolves to it takes the branch below and skips both existing checks; every other edge is unchanged. The existing timing check must be skipped on this edge: an early-started dependent always has a `worktree_created_at` before the upstream's `merge_confirmed_at`, so it would otherwise fail forever.

| Dependent `merge_status` | Upstream `merge_status` | `synced_at` | Result |
| --- | --- | --- | --- |
| `not_started` or `worktree_created` | any | any | No error |
| anything else, including absent and non-string | not `merged` or `worktree_removed` | any | Message A |
| anything else | `merged` or `worktree_removed` | not a non-empty string | Message B |
| anything else | `merged` or `worktree_removed` | non-empty string | No error |

Treating an absent or unknown dependent status as "pr_open or later" follows the fail-closed rule of `feature_has_started`. One error per edge, with A before B. `{f}` and `{d}` render as the existing messages render them. Byte-identical in three runtimes:

- A: `EPIC_WAVE_BARRIER_VIOLATION: {f} is at pr_open or later while early_start dependency {d} is not merged`
- B: `EPIC_WAVE_BARRIER_VIOLATION: {f} is at pr_open or later without a string synced_at for early_start dependency {d}`

The validators compare no timestamps on this edge, as the spec states; the ancestry check in the parent's mirror step (Procedure, step 9) is what proves the sync.

**Layer 1.** No denial text changes. New pure sibling `epic-wave-barrier-early-start.ps1`, byte-identical at `.claude/hooks` and `.codex/hooks`, in the shape of stage C's merge-guard sibling: it defines functions only, dot-sources nothing, and imports nothing.

- `Get-EpicWaveEarlyStartReference -Feature` returns `dependency` of a valid record, or null.
- `Test-EpicWaveEarlyStartEdge -ExemptRecord -DependencyRecord` is true only when both are non-null, their `feature_folder` values are non-empty and equal (ordinal), and the upstream `merge_status` is a string in `worktree_created`, `pr_open`, `ci_green`, or `merge_conflict`.

Three facts shape these functions:

- Both gates parse with `ConvertFrom-Json`, which turns an ISO-8601 string into `[datetime]`, so `interface_settled_at` is accepted as a non-empty string or a `[datetime]`. A string-only test would reject every real value.
- `PSObject.Properties` lookups ignore case, so the key test uses `-ccontains` to match layer 2's ordinal rule.
- Records are compared by `feature_folder`, not object identity, because identity of `PSCustomObject` values through a .NET call is not a safe test.

A merged upstream makes the predicate false, and the existing merged check then passes the edge. The upstream-status test is a layer 1 start condition only, because an upstream with no branch or a halted branch offers nothing to start on. Layer 2 stays as the spec states.

Gate edits are insertions only, so no existing statement changes. `Test-EpicWaveBarrierDependenciesMerged` computes the exempt record through `Find-FeatureFolderRecord` before its loop and, right after the record null check, skips the edge when `Test-EpicWaveEarlyStartEdge` is true. `Test-CodexWaveDependenciesReady` does the same through `Find-CodexWaveFeature`, whose key is the basename or issue number, so a lifecycle-prefixed `dependency` finds no record on Codex and fails closed. With no key the reference is null, the record is null, and the predicate is false before it reads anything.

**Opt-in.** A merged skill edit reaches running epics, so nothing may read as a new default. The source of opt-in is a new manifest field on one feature, `early_start_on: <upstream-issue_num>`, which must be one of its `depends_on` values. `epic.md` is static and human-authored, and `epic_wave_computation.py` takes a parsed `depends_on` mapping, so no parser rejects the field. No manifest carries it today, and #1019's will not. The new skill section opens by stating that without this field the section does not apply and every other section governs unchanged. No existing sentence of any skill or agent file is edited, proven by zero deleted lines in [P1-T5].

**Procedure**, stated once as `## Early Dependent Starts (early_start)`, placed before `## Worktree Cleanup` in the Claude skill and before `## Fan-In and Conflict Handling` in the `.agents` skill. Parent side:

1. While a manifest-armed dependent waits, `epic-orchestrator` looks for the evidence file on `origin/<upstream_branch>` every 30 seconds for at most 90 minutes. If the bound ends, the dependent waits for the barrier as usual.
2. Availability. `epic-orchestrator` writes `early_start`, `merge_status: "worktree_created"`, and `worktree_created_at` read from the clock, then validates through its route (D9): on Claude `poetry run python -m scripts.dev_tools.validate_orchestration_artifacts epic-orchestrator-state <path>`, MCP where the repository has no such CLI, and on Codex `validate_orchestration_artifacts`. An `EPIC_WAVE_BARRIER_VIOLATION` naming that feature means the route lacks the rule, from installed MCP or from an integration branch that predates this reduction. The parent removes the three values and keeps the barrier. No child has run, so the record stays true. The same fallback applies when the sibling file is absent or layer 1 denies. Installed 1.1.22 would report this violation on every early start, and a timing violation after the upstream merges, so a run that skipped this step could not pass its completion validation.
3. Launch. The prompt keeps the literal `Epic mode: true` kickoff line and adds `Early start: true. dependency: <dep_issue_num>. upstream_branch: <branch>. interface_evidence: <path>. Run the child procedure of ## Early Dependent Starts (early_start) before S7 and S8.` The dependency's `Upstream context` line becomes `Upstream context for <issue_num>: early start on <dep_issue_num> (spec: <path>; plan: <path>; upstream_branch: <branch>; not merged).` Other dependencies keep their line. The evidence path cites the upstream folder, and `Select-FeatureFolderTarget -DependencyAware` prunes it, which [P1-T3] proves.

Child side:

4. Start. The child stays branched from `origin/<integration_branch>` as the lifecycle states, then runs `git fetch origin <upstream_branch>` and `git merge --no-ff origin/<upstream_branch>` before its first plan task. Commits are never rewritten, because `validate-bash.ps1` denies forced pushes.
5. After S6 and before S7 and S8, the child waits for the upstream merge. `gh pr list --head <upstream_branch> --base <integration_branch> --state merged --json number,mergeCommit`, every 30 seconds for at most 90 minutes, then `git fetch origin <integration_branch>` and `git merge-base --is-ancestor <merge commit> origin/<integration_branch>`. If the bound ends, the child stops with `blocked_reason: "policy_hold"`.
6. Interface check. `git diff --name-only <Upstream-Head> <merge commit> -- <Interface-Paths>`. Any listed path means the interface changed: the child stops with `blocked_reason: "premise_falsified"`, unsynced and with no PR.
7. Sync. `git merge --no-ff origin/<integration_branch>`. A conflict enters the existing `## Merge-Conflict Handling (Fan-In)`, which stage D keeps off the light path.
8. Gate and record. The child re-runs its local gate, commits, pushes, records `early_start_synced_at`, and only then starts S7 or S8.

Parent side:

9. Mirror. Before the write that moves the feature to `pr_open` or later, the parent checks `git merge-base --is-ancestor <upstream merge_commit_sha> origin/<child branch>`. If that passes and the child key is present, it writes `synced_at`. Otherwise it writes none, and layer 2 reports message B and halts as it does today.
10. Re-evaluation, after a stop in step 5 or 6. The parent reads the diff against the child's plan. If no plan task cites a changed symbol, or the stop was the wait bound, it records fresh `interface_settled_at` and `interface_evidence` where the interface changed, and delegates once more after the upstream merges. The new run starts a branch `<child branch>-r<n>` from the pushed child branch, because the stopped worktree still holds the old one and the removal gate denies its removal, updates `branch_name`, and resumes at step 5. Otherwise the edge stops with `premise_falsified`, as `blocked_conflict_loop_limit` stops one. `early_start` stays recorded, because removing it from a started feature would turn a truthful record into a barrier violation.

## Open Questions / Notes

These are choices this plan makes where the spec is silent or a premise did not hold. A reviewer should confirm them.

- The opt-in is a new manifest field, `early_start_on`. The spec defines the checkpoint key but not what arms it; without a human-authored source, a running epic could read the skill and adopt the behavior.
- Installed MCP rejects a truthful early start, and the rejection persists after the upstream merges. So on Claude the feature needs the Python CLI route, and the agent gains a `Bash` grant for it. On Codex it is unavailable until a release. An owner who wants no grant can take the unavailable rule on both runtimes, at the cost of no early starts until a release.
- The child waits inside its run, by the same 30-second, 90-minute bound as merge confirmation, rather than returning and being relaunched. This avoids a second delegation in the usual case. The stop values are `policy_hold` for the wait bound and `premise_falsified` for an interface change, because the twelve-member vocabulary needs no new member.
- "Interface changed" is defined by paths, not symbols: any diff to a listed path stops the child. That can stop on a harmless edit, and the parent's re-evaluation then clears it.
- `synced_at` is proved by the parent's ancestry check, not by the validators, which test only that it is a non-empty string as the spec states. Layer 2 runs at the parent's stop, so a child that opens its PR early is caught retrospectively, not prevented.
- The upstream-status test in layer 1 is narrower than research section 8. It refuses an early start on a `not_started` or halted upstream, which has no usable branch.
- A Codex wave launches whole, so a wave with one member lacking both a merged dependency and a valid record cannot start early. Relaxing that is a launcher change outside this stage.
- Spec D10 and owner condition 3 are unaffected: this stage does not touch a merge gate.
