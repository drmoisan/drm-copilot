### R3 — `mutate-parallel-run.sh` command-line grammar

Exit-code contract identical to `remove-parallel-item.sh`: exit 0 prints one compact JSON object on stdout; exit 1 prints the Python reference's exact rejection message as one stderr line; exit 2 prints one stderr line beginning `PARALLEL_MUTATION_ERROR: usage error:`. Option grammar identical to `remove-parallel-item.sh` (every option takes one value; unknown option, abbreviation, `--name=value`, repeated option, and missing value are usage errors). Integer tokens match `-?(0|[1-9][0-9]*)`. `--at` matches `[0-9A-Za-z:.+-]+` and defaults to the current UTC minute `yyyy-MM-ddTHH-mm`.

| Subcommand | Options | Library function | Success stdout shape |
| --- | --- | --- | --- |
| `admit` | `--candidate <k>` (required), `--edges "<a>:<b> ..."` (optional), `--in-flight "<k> ..."` (required, may be empty), `--current-cohort-members "<k> ..."` (required, may be empty) | `pm_decide_admission` | `{"candidate":<k>,"outcome":"admit_current_cohort","triggers_recompute":false}` or `{"candidate":<k>,"outcome":"defer_and_recolor","triggers_recompute":true}` |
| `recolor` | same options as `remove-parallel-item.sh recolor` | `pm_recolor_unstarted` (reused, unchanged) | `{"cohort_assignments":{...},"generation":<g+1>}` |
| `add-entry` | `--item <k>`, `--deferred true\|false`, `--generation <g>` (all required), `--at` (optional) | `pm_build_add_entry` | `{"op":"add","item_key":<k>,"at":"<at>","prior_state":null,"new_state":"scheduled","disposition":null,"recolor_generation":<g or g+1>}` |
| `close` | `--items "<k>:<state> ..."` (required, may be empty; a duplicate key or a token not of the form integer, colon, `[A-Za-z_]+` is a usage error; an out-of-enum state is a library rejection, exit 1) | `pm_decide_close` | `{"close_permitted":true}` |
| `close-entry` | `--generation <g>` (required), `--at` (optional) | `pm_build_close_entry` | `{"op":"close","item_key":null,"at":"<at>","prior_state":null,"new_state":null,"disposition":null,"recolor_generation":<g>}` |
| `requeue-entry` | `--item <k>`, `--generation <g>` (required), `--at` (optional) | `pm_build_requeue_entry` | `{"op":"requeue","item_key":<k>,"at":"<at>","prior_state":"in_flight","new_state":"blocked","disposition":null,"recolor_generation":<g+1>}` |

Rejection rules reproduced from the Python engine (validation order is part of the contract): entries check the stamped `recolor_generation` (negative rejects) before `item_key` (non-positive rejects), using `Parallel mutation entry rejected: <field> <value> violates the F3 mutations[] contract for op '<op>'.`; `close` validates each `<k>:<state>` token in supplied order (non-positive key gives the `UnknownItemError` text, out-of-enum state gives the `UnknownEnumMemberError` state text), then rejects with `Parallel mutation rejected: close requires no item in flight; still in flight: [<k1>, <k2>].` listing every in-flight key ascending; `admit` has no rejection branch. The op-specific contract message reuses `pm_entry_contract_message`, which gains an optional third argument naming the op and defaulting to `remove`, so every existing call site is unchanged.
