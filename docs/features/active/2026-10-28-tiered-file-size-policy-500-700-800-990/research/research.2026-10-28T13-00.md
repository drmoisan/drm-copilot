## 2. Existing mechanical enforcement and counting method

- No hook, CI step, validator, or feature-review rule enforces file size today. Confirmed: `.claude/agents/feature-review.md` has no size rule (it covers coverage thresholds and evidence locations only); `.github/workflows/*.yml` contains no line-count step; no file under `.claude/hooks` or `.codex/hooks` counts lines. The only mechanical checks are the file-scoped Pester assertions in 1b, and they do not scan the repository. This is consistent with the observed state: about 23 files already exceed 500 lines (section 3), so the 500 limit was unenforced in practice.
- Counting method in the assertions: physical lines via `@(Get-Content -LiteralPath <path>).Count` (and `ClaudeLibModuleConvention.Tests.ps1` states that `Measure-Object -Line` counts non-empty lines only and would under-report). The execution-environment brief (`## Preflight Defect Classes the Validator Cannot See`) states the same: physical counts use `wc -l` or `@(Get-Content ...).Count`. The policy text itself says "500 physical lines" only in the brief.
- Counting-convention hazard: `wc -l` counts newline characters and `Get-Content` counts logical lines, so a file whose last line has no trailing newline differs by one. One boundary file shows the hazard (section 3). The new gate must define one convention (recommended: logical lines, equal to `Get-Content` count, a trailing terminator does not add a line) and the spec must state it.
- Plan-gate G13 and related numbers are plan-size limits and are unrelated: `.claude/agents/atomic-planner.md` and `.claude/skills/atomic-plan-contract/SKILL.md` state "a plan above 40 tasks or 400 lines carries a `## Size Justification` section" and the Pre-Mortem bullet label `File size` (a plan-review label, no figure). `docs/features` Markdown plans are exempt from the file-size policy. ## 4. Home for the 800 check, the hook, and the Warning

### 4a. Candidate approaches (brief)

1. Shared PowerShell policy module plus a Pester repo-gate suite and a PowerShell PreToolUse hook (recommended).
2. Python test (`tests/scripts/dev_tools/`) plus a Python-based hook. Rejected: enforcement hooks must not invoke Python (`tests/scripts/claude-runtime/enforcement-hooks-no-python-invocation.Tests.ps1`; repo preference is bash, PowerShell acceptable) and a Python gate would be a second implementation of the policy.
3. A new CI workflow job running a script. Rejected: a new job changes required status contexts and the CI facts in the execution-environment brief (six-copy update plus ruleset refresh), for no benefit over a Pester suite that the existing `poshqc` shards run automatically.

### 4b. Recommended design

Single source of truth: a pure, entrypoint-free module, for example `.claude/lib/file-size-policy/FileSizePolicy.psm1` (with Codex and bundle twins), exposing pure functions (tier classification for a line count: below 500, 500-699, 700-799, 800 and above; covered-path test using the extension allowlist and the exemption rules; ratchet comparison of a current size against a baseline entry; the hook decision for a Write or Edit). It follows `.claude/lib` conventions pinned by `ClaudeLibModuleConvention.Tests.ps1` (`Set-StrictMode -Version Latest`, the `$ErrorActionPreference = 'Stop'` guard line directly after it, `-ErrorAction Stop` on sibling imports, the fixed convention sentence in the help block). The module must itself stay well under 800 lines (target under 500, to follow the policy it enforces).

Repo-wide check (AC3): a Pester suite under `tests/scripts/ci/` (for example `FileSizePolicy.RepoGate.Tests.ps1`), discovered by `config/poshqc-scan.json` scan folders and assigned to a shard automatically (verify that `tests/scripts/ci` is a scan folder, since `CiChangeScope.Tests.ps1` lives there). It discovers covered files on disk with `Get-ChildItem` over the repository excluding fixed directory names, reads the baseline with `Get-Content`, and applies the module. This mirrors the existing disk-discovery precedent (`ClaudeLibModuleConvention.Tests.ps1`) and avoids a git subprocess in a unit test (test purity forbids `Start-Process`; real `git` calls in tests are disallowed by the wrapper-seam rule). Unit tests of the pure functions use in-memory file lists and sizes, which satisfies the issue's "fixture-free in-memory file list" example and the no-temp-file rule.

Local-versus-CI discovery risk: `Get-ChildItem` sees untracked and gitignored files that CI does not (for example the stray `render.py,cover`, `testResults.xml`, `artifacts/`, `coverage/`). Mitigation: an include-by-extension allowlist (the `,cover` file would not match) plus a fixed exclude list of directory names (`.git`, `node_modules`, `artifacts`, `coverage`, `dist`, `out`, `virtual`, `docs`, virtualenv and cache directories). A suite that depends on gitignored local state is a documented CI-only failure class in the brief (`## CI-Only Failure Classes`).

Covered-file definition (stated once in the policy module and the spec, not per surface): production code, test code, and reusable scripts by extension allowlist (`.py`, `.ps1`, `.psm1`, `.ts`, `.tsx`, `.js`, `.cjs`, `.mjs`, `.cs`, `.sh`, `.bats`); everything else is outside the covered set: Markdown, JSON, YAML, TOML, text fixtures, lock files. This keeps "existing exemption list unchanged" (Markdown, raw text fixtures, throwaway scripts) while making the exemption mechanical: throwaway scripts are not committed so no rule is needed for them, raw language-processing text fixtures are non-code extensions. Planner should confirm whether `.psd1` (data files) is covered; none exceeded 500 lines in the observed set.

PreToolUse hook (AC4): a PowerShell hook named `enforce-file-size-limit.ps1` following the evidence-locations pattern (`.claude/hooks/enforce-evidence-locations.ps1` and `.claude/hooks/check-powershell-test-purity.ps1`):

- Dot-sources `hook-dependency-guard.ps1` inside the `$script:HookDependencyGuardLoadFailed` try, imports `../lib/hook-payload/HookPayload.psm1` with `Add-HookDependencyFailure` on failure, and imports the policy module the same guarded way; every dependency load failure returns `Get-HookDependencyFailureDecision` (deny, fail closed). `hook-dependency-guard-completeness.Tests.ps1` (claude-runtime) pins this guarded dot-source pattern, so the new hook must follow it exactly.
- Reads the envelope through `Read-ClaudeHookRawPayload`, `Resolve-ClaudeHookToolInput`, and `Get-ClaudeHookToolInputString` (`file_path`, plus `content` for Write or `new_string`/`old_string` for Edit); returns the deny shape (`hookSpecificOutput.permissionDecision = 'deny'` with `permissionDecisionReason`), exit 0; unreadable envelope denies.
- Resulting-size computation: a Write supplies the full file content, so the logical line count of `content` is the result. An Edit supplies only `old_string`/`new_string`, so the hook must derive the resulting size. Precedent: `enforce-completion-consistency.ps1` applies the `old_string` to `new_string` replacement in memory through an injectable reader seam and treats absent, empty, ambiguous, or not-found `old_string` explicitly (also `replace_all`). Reuse that approach with an injectable file-reader seam (tests supply in-memory content, no temp files). Failure to read or apply (file unreadable, `old_string` not found) should fail closed for covered paths per hook convention, with the not-found case matching what the Edit tool itself would reject.
- Baseline-free ratchet in the hook (recommended): the hook already reads the pre-edit file for an Edit; it denies only when the resulting size is over 800 and (the file is new, or the resulting size is greater than the pre-edit size). A shrinking or equal edit to an already-large file is allowed, which realizes AC4's "baselined files may shrink or stay equal" without the hook reading the repo-specific baseline. This matters because the hook ships to consumer repositories through push-down, where `config/file-size-baseline.json` would not exist; a baseline-reading hook would either fail or deny every edit to a consumer's legacy file. The CI check is the baseline-aware gate; the hook is the early, baseline-independent gate. The two layers overlap safely (a file grown past its baseline by a non-hook path, such as a Bash write, is still caught by CI, because the hook only sees `Write` and `Edit`).
- Deny message names the tiers and the split requirement (500 guidance, 700 advisory, 800 enforced regardless of separability) and the path and resulting count.

## 5. Baseline list: format, location, ratchet semantics

Location and format (recommended): `config/file-size-baseline.json`, beside `config/poshqc-scan.json` and `config/ci-docs-only-paths.json`. Content: `{ "schemaVersion": 1, "hardLimit": 800, "files": { "<repo-relative forward-slash path>": <recorded line count>, ... } }` with keys sorted by ordinal comparison, 2-space indent, LF endings, trailing newline. Rationale: JSON is already the repository's config format for CI-read data, it is machine-comparable, and a sorted, path-keyed map gives clean one-line diffs for review. Sizes are recorded (not just paths) so the ratchet can detect growth without a git base reference, and so CI does not need `origin/main` (the `_shell-coverage.yml` job checks out at depth one; a base-ref diff is unreliable in CI).

Deterministic generation (AC6): a generator script (for example `scripts/ci/New-FileSizeBaseline.ps1`, using the shared module and an `Invoke-GitExe` wrapper seam) lists tracked files at the merge base (`git ls-tree -r --name-only <merge-base>`, never `origin/main` itself), reads each blob's logical line count through the module, keeps covered files over 800, sorts ordinally, and writes the JSON. Running it twice at the same ref yields byte-identical output. The Pester suite does not run the generator (no subprocess in unit tests); the generator's pure core (list plus sizes to JSON text) is unit-tested in memory, and the one-off run that produces the committed file is recorded as evidence under `<FEATURE>/evidence/` with the ref and command.

Ratchet rules (CI check, evaluated per covered file with current size S and baseline entry B if present):

- S <= 800 and no entry: pass.
- S <= 800 and an entry exists: fail with "stale baseline entry; remove it" (the file has been split; the list must shrink).
- S > 800 and no entry: fail "new file over the hard limit" (applies to new files and to files that grew past 800).
- S > 800 and entry B with S > B: fail "baselined file grew".
- S > 800 and entry B with S == B: pass.
- S > 800 and entry B with S < B: fail with "tighten the baseline to S" (recommended) so the ratchet is monotone without a git base. The alternative (accept S < B silently) leaves a loophole: shrink to 810, then regrow to B without detection. The cost of the recommended rule is that a PR that shrinks a baselined file also edits one number in the baseline; a bundled generator mode that only lowers entries makes this mechanical. This is the one semantic choice not stated by the user; surface it to the orchestrator or user during planning.
- Baseline entry for a path with no file on disk: fail "stale baseline entry" (covers deletion and rename).
- Baseline growth (a new key, or a raised number) is not detectable by the check alone; it is a reviewer and feature-review concern (the baseline file is one line per entry, so the diff is directly reviewable). Add a feature-review instruction that any added or increased baseline entry is a blocking policy finding.

Rename and move: a moved or renamed file is a new path, so it is absent from the baseline. If it is over 800 it fails as "new file over the hard limit" and the old entry fails as stale; the author must either split the file or move the entry in the same change. Moving an entry while keeping the recorded size (S == B) is allowed and visible in the diff. This is deliberate: a move must not be a way to reset the ratchet upward, and because the recorded size must match, it cannot be.

The hook does not read the baseline (see 4b); its rule is the pre-edit-size ratchet. A baselined file edited through Write that is rewritten at a smaller or equal size is allowed; a Write that grows it is denied.

## 7. Risks

- Gate file size: the new policy module, hook, repo-gate suite, generator, and their tests must each stay under the policy they enforce (target under 500 each, with the hook and the module split so no file approaches 700). The hook's test suite and the policy module's test suite need separate files. The bundle twins are production files counted by the repo-gate itself.
- Line-ending and counting: the repository rule `* text=auto eol=lf` normalizes checkouts, so CI sees LF; a Windows worktree with CRLF files must count identically. Count logical lines (split on `\r?\n`, a trailing terminator adds no line), never rely on `wc -l` in PowerShell code, and never use `Measure-Object -Line`. The 800-versus-801 boundary file (section 3) shows the count can differ by one between conventions. Test with fixtures that are in-memory strings carrying explicit `\r\n` and `\n`, because a committed CRLF fixture would be normalized to LF by CI.
- CI-only behavior: (a) disk discovery sees untracked local files that CI does not (stray `render.py,cover`, `testResults.xml`); mitigated by the extension allowlist and directory excludes. (b) The Linux hook-suite job runs `tests/scripts/claude-hooks` and `tests/scripts/codex-hooks` on a case-sensitive file system; the hook suites must use forward slashes and exact case. (c) Shard completeness: the aggregator verifies a Pester discovery count, so a new suite under a scanned folder is assigned automatically; a suite outside `config/poshqc-scan.json` folders would not run in CI. (d) Docs-only PRs skip the `poshqc` jobs at job level, which is acceptable because Markdown is exempt and a docs-only PR cannot change a covered file.
- Existing 500-based tests: leaving `<= 500` assertions passes; loosening them is a policy decision and risks a silent regression of file discipline. Rewording test names can break name-based references; search before renaming.
- Hook false denies: an Edit whose resulting size cannot be computed (unreadable file, `old_string` missing or ambiguous) must produce a clear, specific deny or defer to the tool's own rejection; a hook that denies legitimate edits to large non-covered files (Markdown, JSON, lock files) would be a regression, so the covered-path test is the first decision in the hook and every non-covered path returns allow with no read.
- Push-down to consumer repositories: the shipped hook applies to legacy files in repositories that have no baseline; the baseline-free growth rule keeps those repositories usable (edits that do not grow an over-800 file pass; any new file over 800 is denied).
- Hook proving: hook changes on a branch are not exercised by isolated subagents until they merge (brief, `## Hook Execution Context`); acceptance for AC4 rests on Pester suites that import the hook, not on a live subagent run.
- Brief maintenance: failing to update all six brief copies breaks `test_brief_copies_are_byte_identical`; failing to update the brief at all breaks the maintenance rule that preflight checks.
- Required-context drift: adding a CI job would change the required contexts; the recommended design adds none.
- Ratchet semantics decision: strict "tighten on shrink" (section 5) is an addition to the user's decision and needs confirmation; the alternative is the shrink-allowed loophole.
