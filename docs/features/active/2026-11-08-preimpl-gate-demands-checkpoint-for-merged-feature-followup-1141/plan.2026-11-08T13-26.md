## Design Summary

All new logic lives in the existing pure file `hook-epic-fan-in.ps1` (byte-identical at `.claude/hooks/`, `.codex/hooks/`, `extensions/drm-copilot/resources/claude-customizations/.claude/hooks/`, and `extensions/drm-copilot/resources/codex-and-agents-customizations/.codex/hooks/`); no fan-in code is duplicated and no hook file is added.

- Generalization ([P2-T1]): `Get-EpicFanInShapeDetail` and `Test-EpicFanInCommitShape` gain an optional `-PathPredicate [scriptblock]`. Without it the predicate is case-sensitive equality with `-StatusDocPath`, and a blank `-StatusDocPath` still yields no shape, so every #1136 row keeps its result. `git [-C <abs>] add [--] <p...>` and `git [-C <abs>] commit <opts> -- <p...>` accept one or more operands, every one satisfying the predicate; zero operands after `--` yields no shape; commit options stay `-m`, `--message`, `-F`, `--file`, `--trailer`. `Test-EpicFanInStagedIndex` gains the same optional predicate: `ExitCode` 0, NUL-terminated, at least one name, every name satisfying it. `Get-EpicFanInAllowance` gains optional `-PathPredicate` (path leg; default `Test-EpicFanInWriteRelativePath`) and `-OperandPredicate` (shape operands and index names; default status-doc equality) and passes them through.
- New functions ([P2-T2]): `Get-EpicMergedFeatureRoots -Checkpoint` returns the allowed roots: for each `features[]` entry whose `merge_status` is in `$script:EpicFanInTerminalMergeStatuses`, whose `feature_folder` basename after stripping one optional `docs/features/active/` or `docs/features/completed/` prefix matches `$script:EpicFanInSlugPattern`, whose `merge_commit_sha` is a string matching 40 or 64 lowercase hex characters, and whose `pr_number` is a parsed JSON integer (`[int]` or `[long]`, never `[bool]`, `[double]`, string, or null) greater than 0, the roots `docs/features/active/<basename>/` and `docs/features/completed/<basename>/`; plus the `Get-EpicFanInStatusDocRelativePath` result when it is non-null and at least one feature qualifies. `Test-EpicMergedFeaturePath -RelativePath -Root` is true only for a path that contains no backslash, no glob character (`*`, `?`, `[`), no `.` or `..` segment, and no leading `/`, and that either equals the status-doc root or starts with a trailing-slash root and has a non-empty remainder (so `<basename>-x/` never matches). `Get-EpicMergedFeatureFollowUpAllowance -Scope -FilePath -Command -StagedIndexReader` returns `Allowed = $false` unless `route_id` is `epic`, `integration_branch` equals `Scope.Branch`, and the roots are non-empty; otherwise it returns `Get-EpicFanInAllowance` called with both predicates bound to `Test-EpicMergedFeaturePath` over those roots. Fan-in completeness is not required. Its body is wrapped so any error answers `Allowed = $false`, and the disjunct runs only on a call that is already denied, so no call admitted today can become denied. No function reads a file, starts a process, or reads `artifacts/orchestration/orchestrator-state.json`.
- Plug-in ([P3-T1]): in each surface's `Get-OrchestrationEpicScopeDecision`, the `-ReadinessFailure` scriptblock keeps the #1136 conjunction and adds a second disjunct under the same `$failure -ceq 'merge-in-progress'` guard calling `Get-EpicMergedFeatureFollowUpAllowance` with the same arguments the #1136 call receives (Claude: `@($FilePath)` and `$epicScopeText`; Codex: `$legPaths` and `$legCommand`) and the same reader. Any other failure returns unchanged, so every deny text is unchanged. The allowance is allow-side only.
- Premise correction: AC-9 cites "an in-progress merge" as an example of another readiness failure, but `Get-EpicCommandLegReadinessFailure` returns no failure while a merge is in progress. The plan proves AC-9 with a blank `epic_manifest_path`, which fails with `'epic_manifest_path'`, as the #1136 suites do.
