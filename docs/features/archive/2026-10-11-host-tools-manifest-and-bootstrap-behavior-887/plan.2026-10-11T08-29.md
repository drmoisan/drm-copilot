- **SCRATCH:** `SCRATCH` abbreviates the absolute directory `<executing worktree root>/SCRATCH`; every executor command and tool call uses the absolute form. The directory is untracked and not gitignored and is never staged. The parallel-orchestrator supplies the absolute executing worktree root with every delegation of this plan, passes the absolute form to `gh run download -D` in preconditions (a) and (b), and runs every delegation of this plan (Phase 0 through P2-T14) in that same worktree.
- **PowerShell verification route (Option A only):** the PoshQC MCP tools `mcp__drm-copilot__run_poshqc_format`, `mcp__drm-copilot__run_poshqc_analyze`, `mcp__drm-copilot__run_poshqc_test`, each called with `workspace_root` = the absolute root of the executing worktree and the `scan_folders` array stated in the task. No task runs Pester, PSScriptAnalyzer, bats, or kcov through `sh`, `bash`, `pwsh`, a wrapper script, or `pwsh -Command`.
- **MCP result semantics:** a PoshQC MCP result carries only a pass/fail status and a summary line composed before the child process runs (for example `Ran bundled PoshQC test against '<root>' with 2 selected scan folder(s).`). No acceptance condition in this plan reads a count, percentage, or finding list from an MCP result. In every MCP command-step artifact, `EXIT_CODE:` records `0` for a passing MCP result and `1` for a failing MCP result; `Command:` records the tool name and the exact `scan_folders` array. A failing `run_poshqc_test` result is meaningful because the Pester settings set `Run.Exit = $true`.
- **Scan-folder entries naming a file:** `scan_folders` entries are resolved with `Resolve-Path` and enumerated with `Get-ChildItem -Recurse`, both of which accept a single file path, so a file-scoped scan runs exactly that suite. A file-scoped scan that finds no test file logs a message and returns without failing; that is why every file-scoped pass in this plan is paired with a failing run of the same scan before the fix.
- **Installed-extension settings:** the MCP test runner reads the installed extension's settings. Each test task therefore passes an explicit `scan_folders` array; no task relies on a default scan to discover the new suite. No `sorted-scan-folders.json` file exists in this repository (search of the tree for `sorted-scan-folders` returned no match); `config/poshqc-scan.json` already lists `tests/scripts`, so no scan-configuration edit is in scope.
- **Coverage source:** PowerShell numeric coverage comes only from the CI `PowerShell QC` job artifact `poshqc-test-results` (file `powershell-coverage.xml`, JaCoCo XML: `package` elements named by directory, `sourcefile` elements named by file name, a `counter type="LINE"` child with `missed` and `covered`, and `line` children with `nr`, `mi`, `ci`). Baseline coverage is read from the latest successful `ci.yml` push run on `main`; post-change coverage is read from the PR run after the parallel-orchestrator reports that PR CI completed.
- **Commit message files:** each phase-boundary commit uses `git commit -F` with its named file (`SCRATCH/887/commit-phase0-887.txt`, `SCRATCH/887/commit-phase1-887.txt`, `SCRATCH/887/commit-phase2-887.txt`, `SCRATCH/887/commit-phase2-ci-887.txt`), and the P2-T11 remediation merge, when required, uses `git merge --no-ff -F` with `SCRATCH/887/merge-main-887.txt`. Each file holds a conventional subject line naming `887`, a blank line, a one-paragraph body, a blank line, and the trailer line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Staging always names explicit paths. No force push. Nothing is deleted. No GitHub issue is created.
- **Delegation:** atomic-executor owns every checkbox and every evidence artifact and performs every Phase 1 edit task directly; atomic-executor has no Agent tool, so no task is delegated onward (see P1-T1). The planner does not delegate.
