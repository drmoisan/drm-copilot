## Recorded Interpretations (documented deviations and decisions)

- **I1 — Fail-before mechanism.** `spec.md:236` asks for fail-before capture "by running the new process-level cases against the pre-fix hooks." Committing a failing Pester file before the fix would break the mandatory per-phase PoshQC loop for every intermediate phase. Instead, Phase 1 executes the identical process-level cases (same payloads, same ProcessStartInfo pattern, same assertions) as a non-committed throwaway probe script stored OUTSIDE the repository working tree (session scratchpad) and stores the failing table as the fail-before artifact. The committed Pester cases (Phase 7) then serve as pass-after proof. Payload identity between probe and Pester cases is required.
- **I2 — Governed-path reconstruction failure.** For the checkpoint hooks, on-disk Update reconstruction failure for the GOVERNED checkpoint path (`artifacts/orchestration/orchestrator-state.json`) must never exit 2 (stdin is well-formed); it routes through the hooks' existing fail-closed deny for un-validatable checkpoint content. Reconstruction failure for UNGOVERNED paths is an allow (latent defect at `enforce-checkpoint-monotonic.ps1:364-367,391-392`).
- **I3 — `enforce-completion-consistency` dot-source.** No rename. It may continue to dot-source `enforce-checkpoint-monotonic.ps1` for shared checkpoint policy logic; its transport goes through the shared module with `-HookName 'enforce-completion-consistency'` so every exit-2 stderr message names itself.
- **I4 — Deny reachability per tool name.** Process-level deny cases are required for each (handler, tool name) pair where the preserved policy can produce a deny deterministically without depending on mutable on-disk state. Where the preserved policy cannot deny for a tool name (e.g., `enforce-checkpoint-monotonic` on a partial `Edit`, per its documented design at lines 37-39), the test asserts allow and carries a comment citing the policy site. Batch-budget forbidden cases remain unit-level via injected state (`spec.md:263`). Preimplementation-gate deny cases are likewise unit-level: `Invoke-OrchestrationPreimplementationGateDecision` accepts an injected `-CheckpointRaw`, so deny coverage dot-sources the hook and injects a non-ready checkpoint instead of depending on the repository's live `artifacts/orchestration/orchestrator-state.json`.
- **I5 — AC4 scope narrowing (missing/null `tool_input`).** Spec AC4 originally required exit 2 on missing/null `tool_input` for EVERY registered handler. Preflight measurement across all ten non-implicated registered PreToolUse handlers: empty stdin → exit 2 for all 10; `{not-json` → exit 2 for all 10; but missing or null `tool_input` → exit 0 / empty stdout / empty stderr for seven of them (`enforce-epic-merge-gate`, `enforce-epic-worktree-removal-gate`, `enforce-epic-root-invocation`, `enforce-codex-model-routing`, `enforce-epic-planning-only`, `enforce-epic-wave-barrier`, `enforce-epic-child-worktree-binding`). Making those exit 2 would behaviorally change non-implicated handlers, violating `spec.md:79` and `spec.md:119`. Therefore: empty-stdin and invalid-JSON exit-2 assertions apply to every registered handler; the missing/null-`tool_input` exit-2 assertion applies only to the eight `^(apply_patch|Edit|Write)$`-group handlers. `spec.md` AC4 has been corrected to this scope.
- **I6 — Spec handler undercount (recorded, corrected at authorized sites).** The spec originally counted SEVEN handlers in the `^(apply_patch|Edit|Write)$` group; `.codex/config.toml:186-234` registers EIGHT. The orchestrator adopted preflight B1 option (a): `enforce-orchestration-preimplementation-gate.ps1` is an eighth production rewire unit (root + bundle mirror). The undercount was corrected in `spec.md` at the authorized locations only (`spec.md:12`, `:14`, `:95`, `:100`, plus the AC4 scope and the 421/426→420/425 line-count constants). Remaining spec occurrences of "seven handlers" (e.g., in-scope bullet, design summary, files-to-change list, test-strategy case 1) were not edited and are READ as the eight-handler scope of this plan. The gate's pre-fix behavior differs from the seven legacy handlers: it already exits 0 on `apply_patch` (mapped or unmapped) and on `Bash`; only its `Edit`/`Write` rows are fail-before rows, and its existing `Bash`/`apply_patch` outcomes are policy to preserve (Hard Constraint 3).
