## Decisions (fixed here; no optional file or open choice remains)

1. New Pester tests are split across two files. `Invoke-FullReleaseFlow.ChecksWait.Tests.ps1` receives the function-level behavior tests of `Wait-ForPullRequestChecks`. A new file `tests/scripts/dev-tools/Invoke-FullReleaseFlow.CheckClassification.Tests.ps1` is created and receives the direct unit tests of the two new helpers. `Invoke-FullReleaseFlow.Tests.ps1` receives in-place string and wording edits only. Every file stays at or under 500 lines.
2. Helper contracts (names fixed by the plan contract and the research):
   - `function Get-CheckSetVerdict` takes `-Checks` (`[object[]]`, empty collection allowed) and returns `[pscustomobject]@{ Verdict = <string>; Detail = <string> }`. `Verdict` is one of `pass`, `fail`, `unknown`, `pending`, `empty`. Precedence: an empty set returns `empty`; otherwise any `fail` or `cancel` bucket returns `fail`; otherwise any bucket outside `pass`, `skipping`, `pending`, `fail`, `cancel`, or a check with an absent `bucket` property, or a null or blank bucket value, returns `unknown`; otherwise any `pending` bucket returns `pending`; otherwise `pass`. `Detail` is the first unrecognized bucket value in array order, or `(missing)` for an absent, null, or blank bucket, and an empty string for every other verdict. Bucket comparison is exact and case-sensitive. An all-`skipping` set returns `pass`.
   - `function ConvertFrom-CheckPollOutput` takes `-Output` (`[object[]]`, empty collection allowed) and returns `[pscustomobject]@{ Succeeded = <bool>; Checks = <object[]> }`. It joins the lines with a newline, treats blank text as `Succeeded = $false`, parses with `ConvertFrom-Json -ErrorAction Stop` inside a `try` whose `catch` names `[System.ArgumentException]` (no bare catch), and returns `Succeeded = $false` when parsing throws or when any parsed element is not a `[pscustomobject]` (a `null` or scalar element). A parsed empty array returns `Succeeded = $true` with `Checks = @()`.
3. `Wait-ForPullRequestChecks` keeps its name, parameters, defaults, Phase A, and the two timeout messages. New behavior: the poll is `gh pr checks <PrNumber> --json bucket` with no `--required`. The first successful poll that is unparsable returns 1 with stderr message `Could not parse the check results for PR #<n>.`. In Phase B the verdict drives the loop: `fail` returns 1 with `A check failed for PR #<n>.`; `unknown` returns 1 with `A check reported an unrecognized bucket for PR #<n>: <value>.`; `pass` returns 0; `pending` and `empty` sleep and re-poll within `CompletionMaxAttempts`, then return 1 with "did not complete within the timeout". A completion re-poll whose exit code is non-zero, or whose output is unparsable, consumes an attempt and is treated as an empty set (`$checks = @()`), so the budget bound still applies and nothing is read as green.
4. Evidence for the Pester additions: a failing-before run is not capturable (the MCP tools return status only and cannot target a subset), so a `fail-before-exception` dossier with an absence-of-test proof from Phase 0 is written. The Python pin is a genuine `[expect-fail]` then pass-after pair.
5. Coverage: Pester measures line coverage only (no PowerShell branch gate applies per `.claude/rules/general-unit-test.md`). Every new branch has its own test, and the no-regression comparison is CI-dependent.
