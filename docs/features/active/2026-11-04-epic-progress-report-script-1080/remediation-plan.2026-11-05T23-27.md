## Design

Finding 1 (inclusive 2-minute boundary). Test-only. `Describe 'Get-EpicProgressRecentVelocityInterval'` gains `It 'counts a pair exactly two minutes apart'`: samples `ts 0, done 0` and `ts 120, done 1` return one interval whose rate is 30 within 1e-9. Both `120 / 3600.0` and `2 / 60` are the correctly rounded double of 1/30, so the pair sits exactly on the boundary: the `-ge` comparison counts it, and a `-gt` mutant returns zero intervals and fails the test.

Finding 2 (negative elapsed time). Chosen behavior: clamp. `Get-EpicProgressSummary` sets `ElapsedHours` to `[math]::Max(0.0, ($NowUtc - $StartUtc).TotalHours)`, so a `-StartUtc` after now reports `0 h 00 min` elapsed, zero average velocity, and the existing n/a estimates; no terminating error is added. Rationale: the logic stays pure and the report stays usable when a clock or time-zone mistake puts the start slightly ahead. `Format-EpicProgressHour` is unchanged (its only elapsed-time input is now non-negative). Comment-based help: `.PARAMETER StartUtc` of `Get-EpicProgressSummary` states the clamp; the main script's `.PARAMETER StartUtc` states it in P2-T9. New test in the `Get-EpicProgressSummary, Get-EpicProgressTldrLine, and Get-EpicProgressFullLine` Describe, `Context 'non-finite values print n/a'`: `It 'clamps elapsed time at zero when the start is after now'` (start 30 minutes after `$script:nowUtc`; asserts `ElapsedHours` is 0 and the second TL;DR line equals `**Elapsed:** 0 h 00 min, with about n/a hours left on the wave-parallel estimate. **Weekly** quota is at 42.5%.`). Before the change that line starts `**Elapsed:** -1 h 30 min`.

Finding 3 (kickoff row parsing). `ConvertFrom-EpicProgressKickoffRow` matches a row with `^\|\s*(\d+)\s*\|` (any whitespace, including none, around the issue cell; cells are already trimmed). A wave cell that is not all digits raises a terminating error with the text `The kickoff row for issue #<issue> has a non-numeric wave cell '<cell>'.`; a numeric cell is parsed with the invariant culture. Chosen over skipping because a silently dropped feature row would understate the epic's task total. Help `.DESCRIPTION` states both rules. New tests: `It 'parses a feature row with variable whitespace around cells'` (row `|  12345|Beta|  2 |large|docs/b/plan.md|` gives Issue `12345`, Wave 2, Band `large`, PlanPath `docs/b/plan.md`) and `It 'throws a clear error for a non-numeric wave cell'` (row `| 12 | Alpha | two | small | docs/a/plan.md |`; asserts a throw matching `*#12 has a non-numeric wave cell 'two'*`).

Finding 4 (unreported fetch failure). New one-statement seam in the main script, `Get-EpicProgressLastExitCode` (comment-based help, `[OutputType([int])]`, returns `$LASTEXITCODE`). `Invoke-EpicProgressReport` keeps the `fetch -q origin` call through `Invoke-GitExe` unchanged, then reads the seam and, when the value is not 0, calls `Write-Warning` with `git fetch -q origin failed with exit code <n>; the report uses the last fetched state of <IntegrationBranch>.` The report continues (AC7 forbids a terminating error for degraded inputs). The seam starts no native command, so the `confines native commands to their wrappers` count of 3 is unchanged. Tests: the `Describe 'Invoke-EpicProgressReport'` `BeforeEach` sets `$script:fetchExitCode = 0` and mocks `Get-EpicProgressLastExitCode` to return it; `It 'warns when git fetch fails'` (exit code 128; captures the warning stream with `-WarningVariable`; asserts one warning matching `git fetch -q origin failed with exit code 128;*` and that the report lines are still returned) and `It 'does not warn when git fetch succeeds'` (zero warnings); `Describe 'I/O seams without side effects'` gains `It 'returns the last native exit code'` (unmocked seam equals the current `$LASTEXITCODE` value, read without assignment).
