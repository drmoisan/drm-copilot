## Design Decisions

- CR1 split boundary: `Get-EpicProgressCriticalChain` moves with the four named functions, because `Get-EpicProgressCriticalPathReport` is its only production caller. This brings `Get-EpicProgressReport.Schedule.ps1` below 500 lines (graph, cap, cycle, closure, longest path, priority, list schedule), and the new file holds the chain, tail, remaining-time, range, and composition functions.
- CR4 premise correction: the inputs state the pruning cutoff as the oldest stored tick anchor. A span between the stored start and the oldest anchor is still subtracted from the aggregate elapsed time (`Get-EpicProgressAggregateVelocity`) and can overlap a stored sample interval, so pruning at the anchor alone would change the printed average; the existing case `writes version 3 with the task baseline, task samples, and pauses` stores exactly such a span (it ends after the start and before the anchor) and would fail. The cutoff is therefore the earliest stored instant that any later calculation reads: the minimum of `startUnixSeconds`, the oldest sample `ts`, and the oldest `lastTickUnixSeconds`. When the oldest anchor is that minimum, the inputs' rule holds exactly (before the anchor dropped; at or after kept). With no start, sample, or anchor, nothing is pruned.
- CR2 rule: the average is non-finite (prints `n/a`) whenever the returned interval count is 0, including when every interval is dropped for overlapping a pause; otherwise it is computed as before.
