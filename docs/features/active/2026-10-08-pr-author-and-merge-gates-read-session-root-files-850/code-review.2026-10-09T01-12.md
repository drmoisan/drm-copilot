Classification: correct fix, Non-blocking, no finding. The removal-gate helpers that use the `.Properties.Name` form are not under strict mode, so the same issue does not arise there.

## Design Observations (no action required)

- Precedence on the `--body-file` path is as specified: resolution reason, then `PR_CONTEXT_MISSING` (now naming the worktree), then the preflight, then Checks 1 to 6. Commands without `--body-file` return before `Resolve-PrAuthorArtifactRoot` is called.
- In epic scope, `RelativeBodyAllowed` compares the epic checkpoint's worktree with `EpicScope.WorktreeRoot`; for the pr-author call `-MatchWorktreeHead` is not set, so that value is the session root, which is the intended comparison.
- `Get-PrAuthorBodyPathBindingReason` matches the absolute form with case-insensitive `-match` and then decides equality with `Test-PrAuthorBodyPathEqual`, so a case-differing POSIX path is still denied, and a case-differing drive or UNC path is accepted and read through the canonical composed path.
- A stale session-root copy of another worktree's checkpoint that records N produces `Ambiguous` and a deny, which is the fail-closed outcome the spec requires (AC-20). An operator who copied checkpoints during the 2026-10-07 workaround will see that deny until the copy is moved; the ambiguity detail names the remedy.
- `Resolve-EpicMergeGateItemTarget` adds one live-worktree enumeration per explicit-number merge decision, consistent with the spec's performance constraint.
